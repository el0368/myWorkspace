Of course. The following Go code demonstrates how a variable "escapes" to the heap when the compiler determines it must outlive the function in which it was created.

### Escaping to the Heap 逃

The most common way to cause a variable to be allocated on the heap is to return a pointer to it from a function. Since the function's stack frame is destroyed upon its return, the variable must be placed in a more persistent location—the heap—for the pointer to remain valid.

This program defines a function `createMessage` that creates a string variable and returns a pointer to it. The `main` function then uses this pointer.

```go
package main

import "fmt"

// createMessage creates a string and returns a pointer to it.
// Because the pointer is returned, the Go compiler knows the data
// must "escape" to the heap to survive this function's return.
func createMessage() *string {
	message := "This message lives on the heap."
	fmt.Printf("    [In createMessage] Address of local 'message' var: %p\n", &message)
	return &message
}

func main() {
	// Call the function and get a pointer to the data on the heap.
	heapPtr := createMessage()

	fmt.Printf("[In main] Pointer received from function:              %p\n", heapPtr)
	fmt.Printf("[In main] Value at that pointer:                       \"%s\"\n", *heapPtr)
}

```

-----

### Proving it with Compiler Flags ⚙️

We can prove this behavior by building the program with the `-gcflags="-m"` flag, which tells the compiler to print its optimization decisions, including escape analysis.

**Command:**

```sh
go build -gcflags="-m" ./your_program_name.go
```

**Compiler Output (will be printed in your terminal):**

```
# command-line-arguments
./your_program_name.go:9:9: message escapes to heap
```

This output from the compiler explicitly confirms that the `message` variable was moved to the heap.

**Program Output (when you run the executable):**

```
    [In createMessage] Address of local 'message' var: 0xc00008e018
[In main] Pointer received from function:              0xc00008e018
[In main] Value at that pointer:                       "This message lives on the heap."
```

As you can see, the memory address is the same both inside and outside the function, and we can still access the data in `main` long after `createMessage` has finished. This is only possible because the data resides on the heap.

Finally, once the `main` function finishes and the `heapPtr` variable no longer exists, there are no more references to the string on the heap. The **garbage collector** will eventually detect this and automatically free the memory, preventing memory leaks without any manual effort from the programmer.
