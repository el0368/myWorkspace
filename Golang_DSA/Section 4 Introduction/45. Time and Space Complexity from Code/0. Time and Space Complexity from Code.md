To explain how to find complexity from program code, I'd split the answer into **four parts**. This way, we can build the ideas one step at a time, making it much easier to understand.

Here is how I would structure it:

---

### Part 1: The Basic Idea and Constant Time - O(1)

First, I'll explain the basic rule we'll use: we assume every simple line of code (like an assignment or a simple math operation) takes one "unit" of time. Then, I'll show the simplest case: a function that has no loops. Because it just has a few lines that run once, the total time is always constant, no matter what the input is. We call this **constant time**, or **$O(1)$**.

---

### Part 2: Looking at a Single Loop - Linear Time - O(n)

Next, we'll look at the most common situation: a single `for` loop that goes through a **slice** of `n` items. I'll break down how to count the operations for the whole loop. We'll see that the total time depends directly on `n`, giving us a time function like `f(n) = 2n + 3`. I'll then explain the most important step: simplifying this to just **$O(n)$**, because we only care about how the time _grows_ with `n`.

---

### Part 3: Looking at Nested Loops - Quadratic Time - O(n²)

In this part, we'll look at what happens when you put a loop inside another loop. This is called a nested loop. I'll explain how the costs multiply, because for _each_ time the outer loop runs, the _entire_ inner loop runs again. This leads to a time function with $n^2$ in it, which we simplify to **$O(n^2)$**. This type of code gets slow very quickly as $n$ gets bigger.

---

### Part 4: The Cost of Calling Other Functions

Finally, I'll cover a very important and tricky point. When one function calls another function, that line of code is **not** just one unit of time. Its true cost is the complexity of the function it calls. So, if your function calls another function that has a loop ($O(n)$), then your function's complexity is also $O(n)$. This is a common mistake, so we'll make sure to understand it well.
