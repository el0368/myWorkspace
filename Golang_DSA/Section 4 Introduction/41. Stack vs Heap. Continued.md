## The Stack and Function Calls 🥞

### The Instructor's Explanation

* **How the Stack is Built:** When there is a sequence of function calls, the stack grows in a "Last-In, First-Out" manner. When `main` calls `fun1`, an **"activation record"** for `fun1` is created on top of `main`'s. When `fun1` calls `fun2`, an activation record for `fun2` is created on top of `fun1`'s.

* **The Currently Executing Function:** The function that is currently running always corresponds to the block of memory at the top of the stack. As the instructor says, "this **topmost activation record belongs to which function? Currently executing function**."

* **How the Stack Unwinds:** When a function finishes, its memory is removed from the stack, and control returns to the function that called it. In his words, "when fun2() has finished, terminated, then...This will be deleted." This process continues until the `main` function's record is removed and the program ends.

* **Automatic Memory Management:** This entire process is automatic. The memory size is "decided by compiler only," and the memory for each function "is **automatically created, and automatically destroyed** when the function ends." The programmer simply has to declare the variables.

---

### The Golang Explanation

Go's stack operates on the same fundamental LIFO principle, but with a key difference for concurrency.

* **Goroutine-Specific Stacks:** In Go, **every goroutine gets its own independent stack**. Unlike the single, large stack in a traditional C/C++ program, Go can efficiently run hundreds of thousands of concurrent goroutines because each one has its own small, lightweight stack that grows and shrinks as needed.

* **Automatic Management:** Just as the instructor described, memory management on the stack is completely automatic in Go. The compiler determines what local variables can live on a function's stack frame, and that memory is automatically reclaimed when the function returns. The developer does not need to manage this.

## The Heap and Dynamic Allocation HEAP

### The Instructor's Explanation

* **What is the Heap?:** The instructor describes the heap as **"unorganized memory,"** unlike the neatly organized stack.

* **The Heap as a Resource:** He emphasizes that heap memory must be managed explicitly, stating, "**Heap memory should be treated like a resource**." This means you must request it when you need it and release it when you're done.

* **Accessing the Heap:** A program "cannot access heap memory directly." Instead, it must use a **pointer**. The pointer variable itself lives on the stack, inside its function's activation record, but it holds the address of the memory block on the heap.

* **Manual Allocation and Deallocation:** To get memory from the heap, you must explicitly ask for it using functions like `new` (in C++) or `malloc` (in C). Crucially, you must also explicitly release it. As the instructor warns, "when you don't need the memory, you should de-allocate it...**Heap memory should be explicitly requested, and explicitly released**."

* **Memory Leaks:** Forgetting to release heap memory causes a problem called a **"memory leak."** The program holds onto memory it no longer needs, which "cannot be used again." If this happens repeatedly, the program can run out of available heap space.

---

### The Golang Explanation

Go's approach to the heap is fundamentally different and is designed for safety and simplicity.

* **Automatic Allocation via Escape Analysis:** In Go, you do not manually decide to use the heap. The Go compiler performs a process called **escape analysis**. If the compiler determines that a variable must live longer than the function that created it (for example, if you return a pointer to it), the variable "escapes" and is automatically allocated on the heap. Otherwise, it stays on the stack.

* **Automatic Deallocation via Garbage Collection:** This is the most significant difference. **Go does not have a `delete` or `free` keyword.** Instead, the Go runtime has an automatic **garbage collector (GC)**. The GC periodically runs in the background, finds which objects on the heap are no longer being used by any part of the program, and automatically reclaims that memory.

* **Elimination of Memory Leaks:** Because of the automatic garbage collector, the type of memory leak the instructor describes (forgetting to release memory) **is impossible in Go**. This automatic management of heap memory is a core feature that makes Go a safer and more productive language. The developer's responsibility is simply to stop referencing data they no longer need (e.g., by setting a pointer to `nil`), and the GC will handle the cleanup.
