### Linear Time Complexity - `Order(n)` ➡️

The instructor introduces the first type of complexity using a common data structure, an array (or a slice in Go), that contains 'n' elements. He stresses the importance of understanding what 'n' represents: "**n means, some number of elements...maybe 10, or 10,000, or 10,000,000, We don't know.**" It's a variable that represents the size of the input.

He then explains how to determine the time complexity by analyzing the work being done on these 'n' elements.

  * **For summing all elements:** You have to **"go through all of them, one by one you have to take the element and go on adding it."**
  * **For searching for an element:** In the worst case, you have to **"Check for all"** the elements to see if the one you're looking for is present.

In both scenarios, the conclusion is the same. The instructor asks, "**utmost how much time is it taking? It depends on the number of elements...So, what is the time taken? n.**" This means if you have a list of 'n' elements and your procedure involves visiting each element once, the time complexity is 'n'.

He then introduces the formal notation for this: "**So this n, we represent it as a degree. So, we can say Order(n).**"

This procedure corresponds to a very common code structure. In Go, a single `for` loop is used to iterate through all 'n' elements:

```go
// This Go code iterates through 'n' elements, representing Order(n) time.
for i := 0; i < n; i++ {
    // ... logic to process one element comes here ...
    // This could be adding to a sum, searching, or finding a maximum.
}
```

The instructor emphasizes that there are two ways to determine complexity: "**either you can measure the time based on the work that you are doing...or else from the code, program code also you can find the time complexity.**" He advises that the easiest way to analyze code is to understand the work it's performing. If you see a single loop going through all 'n' elements, you can confidently say the time complexity is `Order(n)`.
