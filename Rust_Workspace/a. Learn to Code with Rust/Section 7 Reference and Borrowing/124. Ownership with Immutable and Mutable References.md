### In-Depth Study Guide: `Copy`, `Move`, and References

This guide explores the crucial difference in behavior between immutable and mutable references when they are assigned to new variables, a behavior dictated by the `Copy` trait.

---

### The `Copy` Trait Revisited

First, a quick recap:

- The **`Copy`** trait is a special marker for types whose values can be safely and cheaply duplicated with a simple bit-for-bit copy.
    
- Types that are stored entirely on the **stack** and have a fixed size, like `i32`, `bool`, and `f64`, implement this trait.
    
- When a `Copy` type is assigned to a new variable, a **copy** is made, and the original variable remains valid.
    
- Types that manage data on the **heap**, like `String`, do not implement `Copy`. When they are assigned, ownership is **moved**.
    

---

### Immutable References (`&T`) Implement `Copy` 👯

The first key rule to understand is that **immutable references implement the `Copy` trait**.

**Why is this safe and desirable?**

1. **It aligns with the "multiple readers" rule:** Rust's borrowing rules already allow you to have any number of immutable references to a value at the same time. Since none of them can modify the data, having multiple copies of the reference itself is completely safe.
    
2. **It's cheap:** A reference is just a memory address (like a `u64`), which is small, fixed-size, and lives on the stack. Copying it is extremely fast.
    

What happens in code:

When you assign an immutable reference to another variable, Rust creates a copy of the reference. Both the original reference variable and the new one are valid and point to the same original data.

Rust

```Rust
fn main() {
    let coffee = String::from("Mocha"); // `coffee` owns the String data on the heap.
    let a = &coffee; // `a` is an immutable reference to `coffee`.

    // Because `&String` implements the `Copy` trait, `a` is COPIED to `b`.
    // We now have two independent references pointing to the same `coffee` data.
    let b = a;

    // Both `a` and `b` remain valid and can be used.
    println!("We have {} and {}", a, b);
}
```

Functionally, `let b = a;` is the same as writing `let b = &coffee;`.

---

### Mutable References (`&mut T`) Do NOT Implement `Copy` 🚚

The second, and critically important, rule is that **mutable references do not implement the `Copy` trait**.

**Why is this a necessary safety feature?**

1. **It enforces the "one writer" rule:** Rust's core safety guarantee is that you can only have **one mutable reference** to a piece of data in a given scope.
    
2. **Prevents data races:** If mutable references could be copied, you could easily create two `&mut T` references. This would mean two parts of the code would have permission to write to the same data at the same time, leading to data races and undefined behavior.
    

What happens in code:

Since &mut T is not a Copy type, it follows move semantics. When you assign a mutable reference to a new variable, ownership of the reference itself is moved. The original reference variable is immediately invalidated.

Rust

```Rust
fn main() {
    let mut coffee = String::from("Mocha");
    let a = &mut coffee; // `a` is a mutable reference to `coffee`.

    // Because `&mut String` does not implement `Copy`, ownership of the
    // reference is MOVED from `a` to `b`.
    let b = a;

    // `a` is now invalidated and can no longer be used.
    // This line would cause a compile error: "value borrowed here after move"
    // println!("{}", a);

    // Only the new owner of the reference, `b`, is valid.
    println!("{}", b);
}
```
