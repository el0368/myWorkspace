# Error handling (Rust) — detailed study guide

---

## Recoverable vs. Unrecoverable errors

- **Recoverable errors**: operations that _can_ fail but the program can handle the failure and keep running (e.g., file not found, user typed invalid input).
    
    - Rust models these with the **`Result`** enum (`Ok(T)` / `Err(E)`), letting your code decide how to react.
        
- **Unrecoverable errors**: bugs or conditions that prevent the program from continuing; these are _panics_.
    
    - A panic will unwind (or abort) the program and print a **backtrace** showing the call chain at the moment of failure.
        

---

## Panic and backtrace

- A **panic** is a runtime abort of execution caused by a logic error or irrecoverable condition.
    
- Panic output typically shows an error message and a **backtrace** — a stack of function calls that led to the panic — which helps you debug where the problem originated.
    
- Use panics sparingly in production code; they’re useful for programmer errors, assertions, or prototypes.
    

---

## Exiting the process & exit codes

- You can terminate the program explicitly with `std::process::exit(code: i32)`.
    
    - Convention: `0` means success; non-zero (commonly `1`) means an error.
        
- Example:
    

```rust
use std::process;

fn main() {
    eprintln!("Fatal error, exiting");
    process::exit(1);
}
```

- `process::exit` immediately terminates the process with the provided code (no normal stack unwinding).
    

---

## Standard output vs standard error

- `println!` → writes to **standard output** (stdout).
    
- `eprintln!` → writes to **standard error** (stderr).
    
    - Use `eprintln!` for error messages, so logs can be separated or redirected independently from normal output.
        
- `eprintln!` accepts the same formatting options as `println!`:
    

```rust
let err_msg = "file missing";
eprintln!("Error: {}", err_msg);
```

## `Result<T, E>` — the recoverable error type

- `Result` models operations that may succeed or fail:
    
    - `Ok(T)` — success, carrying some value of type `T`.
        
    - `Err(E)` — error, carrying data of type `E`.
        
- `T` and `E` are **generics**; the function author chooses what types to use. Typical examples:
    
    - `std::fs::File::open(path)` returns `Result<File, std::io::Error>`.
        
    - `io::stdin().read_line(&mut buf)` returns `Result<usize, std::io::Error>`.
        
        - Note: the `Ok(usize)` is the number of bytes read; the actual text is placed into the `String` you passed in.
            

### Inspecting and handling `Result`

- **`match`**: exhaustive, forced handling for every variant — safe and explicit.
    

```rust
use std::fs::File;

match File::open("foo.txt") {
    Ok(file) => println!("Opened file: {:?}", file),
    Err(e)   => eprintln!("Could not open file: {}", e),
}
```

- **`if let`**: concise when you only care about one variant.
    

```rust
if let Ok(file) = File::open("foo.txt") {
    println!("Opened: {:?}", file);
} else {
    eprintln!("Could not open file");
}
```

## Common `Result` helper methods (scope-limited to transcript)

- **`unwrap()`**
    
    - Extracts the success value from `Ok(T)` but **panics** if `Err`.
        
    - Quick-and-dirty; useful in tests or when you are absolutely sure a failure is impossible.
        
- **`expect("message")`**
    
    - Like `unwrap()` but allows a custom panic message — helps debugging where something failed.
        
- **`unwrap_or(default)`**
    
    - Returns the success value if `Ok`; otherwise returns the provided `default` value — safer fallback without panicking.
        
- **`?` (question mark operator)** — powerful propagation tool (see below).
    

> **Rule of thumb:** prefer explicit handling (`match` / `if let`) for recoverable errors or propagate with `?` inside functions that return `Result`. Use `unwrap`/`expect` sparingly.

---

## Propagating errors with `?` (question mark operator)

- The `?` operator is used inside a function that returns a `Result` (or `Option`) to propagate errors upward automatically.
    
- Behavior:
    
    - If the expression yields `Ok(value)`, `?` extracts `value` and execution continues.
        
    - If the expression yields `Err(e)`, `?` returns early from the current function with that `Err(e)`.
        
- Example: reading a file and processing it with `?` to bubble-up errors:
    

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> Result<String, io::Error> {
    let mut file = File::open(path)?;           // returns Err early if open fails
    let mut contents = String::new();
    file.read_to_string(&mut contents)?;        // propagate read errors
    Ok(contents)
}
```

- The `?` operator is shorthand for a pattern that would otherwise require a `match` returning `Err(e)`.
    

### When to use `?` vs `match`

- Use `?` when you want to **propagate** the error unchanged to the caller.
    
- Use `match` (or `if let`) when you need to **handle** the error locally or convert it into another result.
    

---

## `Option<T>` and `?`

- `Option` represents presence (`Some`) or absence (`None`).
    
- The `?` operator also works with `Option` inside functions returning `Option<T>`:
    

```rust
fn find_first_even(nums: &[i32]) -> Option<i32> {
    let x = nums.get(0)?;        // returns None if out of bounds
    if *x % 2 == 0 { Some(*x) } else { None }
}
```

- In that context, `?` returns early with `None` if the operand is `None`.

## Useful patterns and idioms

### Read line from stdin (Result example)

```rust
use std::io;

fn read_user_line() -> io::Result<String> {
    let mut buf = String::new();
    io::stdin().read_line(&mut buf)?; // returns Err early if I/O fails
    Ok(buf.trim().to_string())         // trim newline, return owned String
}
```

- Note: `read_line` returns `Result<usize, io::Error>` (the Ok value is number of bytes read). The read string is appended to the `String` you passed.
    
- Use `trim()` to remove the trailing newline the user typed.
    

### Opening a file with explicit handling

```rust
use std::fs::File;
use std::io;

fn try_open(path: &str) {
    match File::open(path) {
        Ok(f) => println!("File opened successfully: {:?}", f),
        Err(e) => eprintln!("Failed to open {}: {}", path, e),
    }
}
```

## Design advice (from the transcript)

- **Propagate errors from low-level helpers**: functions with a single responsibility should `return Result` rather than decide global error policy. That keeps helpers simple and gives callers flexibility.
    
- **Library APIs should return `Result`** so application code can choose the reaction (log, retry, convert to panic, or exit).
    
- **Use `?` for concise propagation** when no local handling is required.
    
- **Use `match` or `if let` when you must handle failure locally** (custom fallback, logging, recovery logic).
    
- **Avoid overusing `unwrap()`** — it can convert recoverable errors into panics unexpectedly.
    

---

## `Result` and `Debug` / printing errors

- `Result` implements `Debug`, so `println!("{:?}", result)` prints the variant and data.
    
- When printing errors for users, use `{}` or `{}` on the error object if it implements `Display`, or `{:?}` for debugging output.

## Quick reference table

|Concept|Type / Example|Behavior|
|---|---|---|
|Recoverable error|`Result<T, E>`|`Ok(T)` or `Err(E)` — handle or propagate|
|Unrecoverable error|`panic!()`|Aborts and prints backtrace|
|Panic trace|—|Stack of calls; helps debug where panic occurred|
|Fail with code|`process::exit(code)`|Terminates process with code (0 success, >0 error)|
|Print error|`eprintln!()`|Writes to stderr|
|Extract `Result`|`unwrap()` / `expect()`|Panics on `Err`|
|Safe fallback|`unwrap_or(default)`|Returns default on `Err`|
|Propagate|`?`|Returns `Err` to caller if present|
|Exhaustive handling|`match result { Ok(v) => .., Err(e) => .. }`|Guaranteed coverage|
|Conditional|`if let Ok(v) = result { .. }`|Simple branch for one case|

## Short examples recap

**Propagation using `?`:**

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_to_string(path: &str) -> io::Result<String> {
    let mut f = File::open(path)?;
    let mut s = String::new();
    f.read_to_string(&mut s)?;
    Ok(s)
}
```

**Explicit handling with `match`:**

```rust
use std::fs::File;

fn main() {
    match File::open("config.toml") {
        Ok(file) => println!("Got file: {:?}", file),
        Err(err)  => eprintln!("Config missing: {}", err),
    }
}
```

**Using `unwrap_or` for default:**

```rust
let content = read_to_string("data.txt").unwrap_or(String::from("default content"));
```

**Using `expect` for helpful panic message (debugging):**

```rust
let file = File::open("critical.txt").expect("critical.txt must exist for this demo");
```

---

## Final practical rules

1. Model recoverable operations with `Result`.
    
2. Use `match`/`if let` to **handle** errors when you need to react locally.
    
3. Use `?` to **propagate** errors concisely from functions that return `Result`.
    
4. Prefer returning `Result` from small, focused helpers to let the caller decide error policy.
    
5. Use `eprintln!` for error logging and `process::exit` to terminate with status codes if necessary.
    
6. Avoid `unwrap()` except in examples/tests or when you truly know failure is impossible.
