### In-Depth Study Guide: Defining a Struct in Rust

This guide explains what a struct is, why you would use one over a tuple, and the precise syntax for defining your own custom data types.

---

### 1. What is a Struct?

A **struct** (short for structure) is a **custom, compound data type** that allows you to group together related data. The individual pieces of data within a struct are called **fields** (or members).

If you have experience with object-oriented programming, a Rust struct is comparable to an object's data attributes. It allows you to create more complex and meaningful types than the built-in primitives like `i32` or `bool`.

Rust has three kinds of structs, but this guide focuses on the most common type: a **named-field struct**.

---

### 2. Why Use a Struct Over a Tuple?

Both structs and tuples can hold multiple values of different types. However, they serve different purposes.

- **Tuples:** Group data by **position**. You access elements with an index (e.g., `my_tuple.0`). This is useful for simple groupings where the order is obvious and you don't need named fields. The downside is a lack of context—`my_tuple.1` doesn't tell you what that value represents.
    
- **Structs:** Group data by **name**. You access elements with their field name (e.g., `my_coffee.price`). This provides clear context and makes the data's meaning self-evident. The order in which you define the fields does not matter for accessing them.
    

**Conclusion:** For any complex data that you want to model, a struct is superior because the named fields make your code more readable and less error-prone.

---

### 3. Defining a Struct: The Blueprint

When you define a struct, you are creating a **blueprint** or a template for a new data type in your program. You are not creating a concrete value yet, just as defining what an `i32` is doesn't create the number `5`.

#### Syntax Breakdown

Rust

```Rust
struct Coffee {
    // field_name: Type,
    name: String,
    price: f64,
    is_hot: bool,
}
```

1. **`struct` keyword:** This begins the definition of a struct.
    
2. **Struct Name (`Coffee`):** The name of your new custom type. The community convention is to use **`PascalCase`**, where the first letter of every word is capitalized.
    
3. **Curly Braces `{}`:** These enclose the list of fields.
    
4. **Fields (`name`, `price`, `is_hot`):**
    
    - Each field has a name, followed by a colon (`:`), and then its data type.
        
    - The convention for field names is **`snake_case`** (all lowercase, with underscores between words).
        
    - Fields are separated by commas. It is idiomatic to place a comma after the final field as well.
        

---

### 4. Ownership within Structs

The principles of ownership apply to structs in a hierarchical way.

- A variable that holds a struct instance is the **owner** of that instance.
    
- The struct instance, in turn, is the **owner** of the data stored in its fields.
    

This is especially important for fields that own heap-allocated data, like a `String`. In our `Coffee` example, when an instance of `Coffee` is created, it will own the `String` data for its `name`. When the `Coffee` instance goes out of scope, it is responsible for dropping its fields, which will deallocate the `String` data from the heap.

---

### Summary

After defining the `Coffee` struct, you have effectively added a new, custom type to your program's vocabulary. It can now be used just like built-in types such as `i32` or `bool`. The next step, covered in the following lesson, is to create concrete instances (values) from this blueprint.

---
Here are the key ownership concepts with simple examples:

## 1. **Basic Ownership Hierarchy**

```rust
let my_coffee = Coffee { name: String::from("Latte"), ... };
```

- **Variable** `my_coffee` owns the **Coffee instance**
- **Coffee instance** owns its **String fields**
- When `my_coffee` goes out of scope, everything gets cleaned up automatically

## 2. **Nested Ownership Chain**

```rust
let customer = Person {
    name: String::from("Alice"),
    favorite_coffee: Coffee { ... }
};
```

**Ownership flows like this:**

- `customer` (variable) → `Person` (struct) → `favorite_coffee` (Coffee) → `name`/`size` (Strings)

## 3. **Moving Ownership**

```rust
let coffee1 = Coffee { ... };
let coffee2 = coffee1;  // coffee1 is MOVED to coffee2
// coffee1 is no longer usable!
```

- The entire Coffee struct (and all its owned data) moves
- Original variable becomes invalid

## 4. **Automatic Cleanup**

```rust
{
    let temp_coffee = Coffee { name: String::from("Temp"), ... };
    // Use temp_coffee...
} // <- Everything gets dropped here automatically
```

When a struct goes out of scope, Rust automatically:

1. Drops the struct
2. Drops all its fields
3. Frees any heap memory (like String data)

## 5. **Key Memory Locations**

**Stack data** (like `f64`, `i32`):

- Stored in the struct directly
- Copied when struct is moved

**Heap data** (like `String`):

- Struct stores a pointer to heap data
- When struct is dropped, heap memory is freed
- When struct is moved, ownership of heap data transfers

## 6. **Why This Matters**

- **Memory safety**: No memory leaks or dangling pointers
- **Clear ownership**: Always know who's responsible for cleanup
- **Performance**: No garbage collector needed
- **Predictability**: Cleanup happens at predictable times (end of scope)

The hierarchical ownership means that dropping one variable can trigger a cascade of cleanup, but it all happens automatically and safely!

```rust
#[derive(Debug)]
struct Coffee {
    name: String,    // Owns heap-allocated String data
    price: f64,      // Owns stack-allocated number
    size: String,    // Owns heap-allocated String data
}

#[derive(Debug)]
struct Person {
    name: String,           // Person owns this String
    favorite_coffee: Coffee // Person owns this entire Coffee struct
}

fn main() {
    println!("=== BASIC OWNERSHIP HIERARCHY ===");
    
    // Variable `my_coffee` owns the Coffee instance
    let my_coffee = Coffee {
        name: String::from("Latte"),     // Coffee owns this String
        price: 4.50,
        size: String::from("Large"),     // Coffee owns this String too
    };
    
    println!("Coffee: {:?}", my_coffee);
    
    // When my_coffee goes out of scope at the end of this block:
    // 1. my_coffee (the variable) drops
    // 2. Coffee instance drops 
    // 3. Coffee drops its String fields ("Latte" and "Large")
    // 4. Heap memory for those Strings is deallocated
    
    println!("\n=== NESTED OWNERSHIP ===");
    
    // `customer` owns Person, Person owns Coffee, Coffee owns Strings
    let customer = Person {
        name: String::from("Alice"),
        favorite_coffee: Coffee {
            name: String::from("Cappuccino"),
            price: 3.75,
            size: String::from("Medium"),
        }
    };
    
    println!("Customer: {:#?}", customer);
    
    // Ownership chain:
    // customer → Person → favorite_coffee (Coffee) → name/size (Strings)
    
    println!("\n=== WHAT HAPPENS WHEN WE MOVE ===");
    
    let coffee1 = Coffee {
        name: String::from("Espresso"),
        price: 2.00,
        size: String::from("Small"),
    };
    
    println!("Before move: {:?}", coffee1);
    
    // This MOVES coffee1 to coffee2
    let coffee2 = coffee1;
    
    // coffee1 is no longer valid! Uncommenting this would cause a compile error:
    // println!("After move: {:?}", coffee1); // ERROR!
    
    println!("After move: {:?}", coffee2);
    
    println!("\n=== DEMONSTRATING AUTOMATIC CLEANUP ===");
    
    {   // New scope block
        let temp_coffee = Coffee {
            name: String::from("Temporary Coffee"),
            price: 1.00,
            size: String::from("Tiny"),
        };
        
        println!("Inside block: {:?}", temp_coffee);
        
        // When this block ends, temp_coffee goes out of scope
        // Rust automatically:
        // 1. Drops temp_coffee
        // 2. Drops temp_coffee.name String ("Temporary Coffee")  
        // 3. Drops temp_coffee.size String ("Tiny")
        // 4. Frees the heap memory used by those Strings
    } // <- temp_coffee and its String fields are cleaned up here
    
    println!("After block - temp_coffee no longer exists");
    
    println!("\n=== BORROWING INSTEAD OF MOVING ===");
    
    let original_coffee = Coffee {
        name: String::from("Mocha"),
        price: 5.00,
        size: String::from("Large"),
    };
    
    // Borrow instead of move
    print_coffee_info(&original_coffee);
    
    // original_coffee is still usable because we borrowed it
    println!("Still have access: {:?}", original_coffee);
}

// This function borrows a Coffee instead of taking ownership
fn print_coffee_info(coffee: &Coffee) {
    println!("Coffee info - Name: {}, Price: ${}, Size: {}", 
             coffee.name, coffee.price, coffee.size);
    // coffee reference goes out of scope here, but original Coffee remains owned by caller
}
```
