# Rust Option and Result Enums - In-Depth Study Guide

## The Option Enum

### Core Concept

The Option enum addresses the fundamental problem of representing data that may or may not exist. In many programming languages, this is handled with null pointers or similar concepts, but Rust uses the type system to make the possibility of missing data explicit and safe.

### Structure and Variants

```rust
enum Option<T> {
    Some(T),
    None,
}
```

**Some(T) Variant:**

- Contains actual data of any type T (generic)
- Represents the presence of a value
- The wrapped value can be extracted and used

**None Variant:**

- Contains no associated data
- Represents the complete absence of a value
- Equivalent to "null" in other languages, but type-safe

### Mental Model

Think of Option as representing something that is "optional" - it might be there, or it might not. This forces you to explicitly handle both cases in your code, preventing null pointer exceptions and similar runtime errors.

### Common Methods for Data Extraction

#### unwrap()

```rust
let some_value = Some(42);
let value = some_value.unwrap(); // Returns 42

let none_value: Option<i32> = None;
let value = none_value.unwrap(); // PANICS at runtime!
```

- **Behavior**: Extracts the value from Some variant
- **Risk**: Causes program to panic and crash if called on None
- **Use Case**: Only when you're absolutely certain the Option contains Some
- **Generally Discouraged**: Due to potential for runtime crashes

#### expect()

```rust
let none_value: Option<i32> = None;
let value = none_value.expect("Expected a number but got None");
// Panics with custom message: "Expected a number but got None"
```

- **Behavior**: Identical to unwrap() but with custom error message
- **Advantage**: Provides better debugging information when panic occurs
- **Risk**: Still causes panic on None variant

#### unwrap_or()

```rust
let some_value = Some(42);
let none_value: Option<i32> = None;

let result1 = some_value.unwrap_or(0);  // Returns 42
let result2 = none_value.unwrap_or(0);  // Returns 0 (fallback)
```

- **Behavior**: Returns the wrapped value or a provided default
- **Safety**: Never panics - always returns a value
- **Use Case**: When you have a reasonable default value

### Safer Approaches

**Match Statement:**

```rust
let option_value = Some(42);
match option_value {
    Some(value) => println!("Got value: {}", value),
    None => println!("No value present"),
}
```

**If Let Statement:**

```rust
let option_value = Some(42);
if let Some(value) = option_value {
    println!("Got value: {}", value);
}
```

## The Result Enum

### Core Concept

The Result enum represents the outcome of operations that can either succeed or fail. Instead of using exceptions or error codes, Rust makes error handling explicit through the type system. This forces developers to consciously decide how to handle potential failures.

### Structure and Variants

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

**Ok(T) Variant:**

- Contains the successful result data of type T
- Represents successful completion of an operation
- The success value can be extracted and used

**Err(E) Variant:**

- Contains error information of type E
- Represents failure of an operation
- The error can be different type than success value

### Generic Type Flexibility

The two generic types (T and E) allow for maximum flexibility:

- T and E can be completely different types
- T might be an integer while E is a string error message
- Both T and E could be the same type if needed
- The specific types depend on what the function/method returns

### Debug Trait Implementation

Result automatically implements the Debug trait, allowing you to print its contents:

```rust
let result: Result<i32, String> = Ok(42);
println!("{:?}", result); // Prints: Ok(42)

let error_result: Result<i32, String> = Err("Something went wrong".to_string());
println!("{:?}", error_result); // Prints: Err("Something went wrong")
```

### Extraction Methods (Mirror Option)

#### unwrap()

```rust
let success: Result<i32, String> = Ok(42);
let value = success.unwrap(); // Returns 42

let failure: Result<i32, String> = Err("Error!".to_string());
let value = failure.unwrap(); // PANICS at runtime!
```

- **Behavior**: Extracts value from Ok variant
- **Risk**: Panics if called on Err variant
- **Use Case**: When you're certain the Result is Ok

#### expect()

```rust
let failure: Result<i32, String> = Err("Network error".to_string());
let value = failure.expect("Failed to get network data");
// Panics with: "Failed to get network data"
```

- **Behavior**: Like unwrap() but with custom panic message
- **Advantage**: More descriptive error information

#### unwrap_or()

```rust
let success: Result<i32, String> = Ok(42);
let failure: Result<i32, String> = Err("Error!".to_string());

let value1 = success.unwrap_or(0);  // Returns 42
let value2 = failure.unwrap_or(0);  // Returns 0 (fallback)
```

- **Behavior**: Returns success value or provided default
- **Safety**: Never panics - always provides a value

## The Rust Prelude

### What It Includes

The Rust prelude is a special module that's automatically imported into every Rust program. It contains commonly used types and functions to reduce boilerplate imports.

**For Option and Result, the prelude includes:**

- The enum types themselves: `Option` and `Result`
- All variant constructors: `Some`, `None`, `Ok`, `Err`

### Usage Implications

```rust
// These are all equivalent due to the prelude:
let option1 = Option::Some(42);
let option1 = Some(42);  // Preferred - more concise

let result1 = Result::Ok(42);
let result1 = Ok(42);    // Preferred - more concise
```

You can choose either style based on preference or team conventions. Both are commonly seen in real-world Rust code.

## Pattern Matching Integration

### Why Match and If Let Are Popular

The compiler enforces exhaustiveness checking with match statements, ensuring you handle all possible variants. This prevents bugs where you forget to handle an error case or missing value.

**Match Statement Benefits:**

- Compiler verifies all cases are covered
- Forces explicit handling of both success and failure
- Prevents runtime surprises

**If Let Benefits:**

- More concise when you only care about one variant
- Still maintains type safety
- Good for simple extractions

### Practical Examples

```rust
// Comprehensive error handling with match
fn process_data(input: Option<String>) -> String {
    match input {
        Some(data) => format!("Processing: {}", data),
        None => "No data to process".to_string(),
    }
}

// Simple extraction with if let
fn maybe_print(input: Option<String>) {
    if let Some(data) = input {
        println!("{}", data);
    }
    // Silently does nothing if None
}
```

## Key Principles and Best Practices

### Error Handling Philosophy

- Make potential failures explicit in the type system
- Force conscious decisions about error handling
- Prevent silent failures and null pointer exceptions
- Encourage graceful degradation rather than crashes

### When to Use Each Method

- **unwrap()/expect()**: Only in examples, tests, or when you're absolutely certain
- **unwrap_or()**: When you have a sensible default value
- **Match/if let**: For production code where you need proper error handling
- **Result propagation (?)**: For chaining operations that can fail

### Performance Considerations

These enums are zero-cost abstractions - they compile down to efficient machine code without runtime overhead. The safety benefits come without performance penalties.
