## Rust Ownership: The `Copy` Trait

This study guide explains the `Copy` trait in Rust, a fundamental concept that dictates how certain types behave when their values are assigned or passed around, particularly in the context of stack-allocated data.

### I. Review: Traits as Contracts

- **Trait Definition:** A trait in Rust is like a **contract** that a type can agree to uphold. When a type `T` **implements** a trait, it means `T` promises to provide a specific set of behaviors or methods mandated by that trait.
    
- **Example (`Display` Trait):** A type implementing `Display` promises it can be represented as a user-friendly string.
    

### II. The `Copy` Trait: Enabling Duplication

What is the Copy trait?

The Copy trait is a marker trait in Rust that mandates that a type can be copied. This means a full, independent duplicate of a value can be created from it.

- **Automatic Copies:** When a type implements `Copy`, Rust will automatically create a full copy of its value in situations where a duplicate is needed (e.g., assignment to a new variable, passing as an argument to a function).
    

**Why do some types implement `Copy`?**

- **Efficiency:** Copying small, fixed-size data (which typically lives on the Stack) is extremely fast and cheap.
    
- **Simplicity:** For such data, a direct duplication is the most sensible behavior.
    

What types typically implement Copy in Rust?

Rust's primitive data types and other fixed-size types that are stored on the Stack generally implement the Copy trait. These include:

- **Integers:** `i8`, `u16`, `i32`, `u64`, `isize`, `usize`, etc.
    
- **Floating-point numbers:** `f32`, `f64`
    
- **Booleans:** `bool`
    
- **Characters:** `char`
    
- **Fixed-size Arrays:** If an array's elements _also_ implement `Copy`, then the array itself implements `Copy` (e.g., `[i32; 5]` is `Copy`).
    
- **Tuples:** If all elements of a tuple _also_ implement `Copy`, then the tuple itself implements `Copy` (e.g., `(i32, bool)` is `Copy`).
    

### III. `Copy` in Action: Assignment (`=`) with Stack Data

How does Copy affect variable assignment?

When you assign a value from one variable to another, and the type of that value implements Copy, Rust performs an automatic full copy of the underlying data.

- **Result:** After the assignment, both variables hold **separate, independent, duplicate copies** of the value. The original variable **remains valid** and can continue to be used.
    
- **Ownership:** Each variable then becomes the **owner** of its respective, distinct copy of the data. Both are responsible for cleaning up their own copy when they go out of scope.
    

**Example: Copying an Integer (from transcript)**

Rust

```Rust
fn main() {
    let time = 2025; // `time` owns the i32 value 2025. This value is on the Stack.

    // Assignment triggers an automatic copy because i32 implements Copy.
    let year = time; // A NEW, separate copy of 2025 is made on the Stack,
                     // and `year` becomes its owner.

    // Both variables are valid and can be used independently:
    println!("The time is {}.", time); // `time` is still valid. Output: The time is 2025.
    println!("It is the year {}.", year); // `year` holds its own copy. Output: It is the year 2025.

    // We can even modify `year` without affecting `time` (if `year` was `mut`)
    let mut current_year = 2024;
    let next_year = current_year; // Copies 2024
    current_year += 1;            // `current_year` becomes 2025
    println!("Current year: {}, Next year: {}", current_year, next_year); // Output: Current year: 2025, Next year: 2024
} // `current_year` goes out of scope, drops its 2025. `next_year` goes out of scope, drops its 2024.
  // `year` goes out of scope, drops its 2025. `time` goes out of scope, drops its 2025. (All LIFO)
```

**Memory Flow (Simplified for the `time` and `year` example):**

1. **`let time = 2025;`**:
    
    - Value `2025` is pushed onto the Stack.
        
    - Variable `time` becomes the owner of this `2025`.
        
2. **`let year = time;`**:
    
    - Because `i32` implements `Copy`, Rust creates a _new_, duplicate `2025` value.
        
    - This new `2025` is pushed onto the Stack (on top of the first `2025`).
        
    - Variable `year` becomes the owner of _this new_ `2025`.
        
3. **End of `main` function's scope:**
    
    - `year` goes out of scope (last-in). As owner, it pops its `2025` off the Stack.
        
    - `time` goes out of scope (first-in among the two). As owner, it pops its `2025` off the Stack.
        

### IV. Ownership and the `Copy` Trait: A Glimpse Forward

- **The "Unexpected" Behavior Hint:** The transcript mentions that this behavior (original variable remaining valid after assignment) might seem expected now, but it **will not always work this way** when dealing with **Heap data**.
    
- **Future Lessons:** When Rust encounters types that _do not_ implement the `Copy` trait (which often applies to types that manage Heap memory, like `String` or `Vec`), variable assignment will involve a concept called **"Move semantics"** instead of `Copy`. This is where ownership rules become even more critical and might seem less intuitive at first.
    

### V. Key Takeaways

- **`Copy` Trait:** A contract for types that allows full, independent duplicates to be created easily and cheaply.
    
- **Stack Data:** Most fixed-size, stack-allocated primitive types (integers, floats, bools, chars, fixed-size arrays/tuples of Copy types) implement `Copy`.
    
- **Automatic Duplication:** When a `Copy` type is assigned to a new variable (`let new_var = old_var;`), a full copy is made.
    
- **Original Remains Valid:** After a `Copy` operation, the original variable _remains valid_ and usable.
    
- **Separate Owners:** Both the original and the new variable own their respective, distinct copies of the data.
    
- **Contrast with Heap Data:** This behavior is distinct from how Rust handles types that manage heap memory and do not implement `Copy` (which will be covered in later lessons).
