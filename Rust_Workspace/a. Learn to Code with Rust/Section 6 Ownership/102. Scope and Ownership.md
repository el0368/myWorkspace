## Rust Ownership: Managing Stack Memory with Scope

This study guide explains Rust's fundamental concept of Ownership, focusing on its initial application to data stored on the Stack and its direct connection to blocks and scopes.

### I. Review: Blocks and Scopes

Before diving into ownership, let's briefly recall these core concepts:

- **Block**: A section of code enclosed within a pair of **curly braces `{}`**.
    
    - Examples: Function bodies (like `main`), `if` statements, `loop` bodies, or even just arbitrary curly braces placed in your code.
        
- **Scope**: The **region or boundary of code** within a program where a particular **name** (e.g., a variable name, function name) is **valid** and can be used.
    
    - Scopes are directly defined by blocks. Every block creates a new scope.
        
    - Variables are only valid within the scope where they are declared (and any nested scopes within it).
        
- **Variable Lifetime and Scope:**
    
    - When a variable is declared inside a block, it "comes into scope" at that point.
        
    - It remains valid and usable as long as the program execution is within that block (or a nested block).
        
    - When the program execution reaches the closing curly brace of the block, the variable "goes out of scope" and can no longer be used. Its memory is typically reclaimed.
        
    
    Rust
    
    ```Rust
    fn main() { // Outer block, outer scope (for `main`)
        let outer_var = 10; // `outer_var` comes into scope here
    
        { // Inner block, inner scope
            let inner_var = 20; // `inner_var` comes into scope here
            println!("Inside inner block: {}", outer_var + inner_var); // Both are valid
        } // `inner_var` goes OUT of scope here; its memory is reclaimed
    
        // println!("{}", inner_var); // ERROR: `inner_var` cannot be found (out of scope)
        println!("Outside inner block: {}", outer_var); // `outer_var` is still valid
    } // `outer_var` goes OUT of scope here
    ```
    

### II. Ownership and the Stack

**What is the core principle of Ownership (with Stack data)?**

- **Every Rust value has an owner.**
    
- When a **value is assigned to a variable**, that variable becomes the **owner** of the value.
    
- The owner is the entity **responsible for cleaning up (deallocating) the memory** that the value occupies.
    

How does the owner know when to clean up memory?

The owner knows to clean up the data when the variable (the owner) goes out of scope, which happens when its defining block ends.

- When a variable goes out of scope, Rust automatically "drops" the value. For data on the stack, this means popping its entry off the stack.
    

**Example: Ownership with Stack Data and Scopes**

Rust

```Rust
fn main() { // `main` function's block and scope start
    let age = 33; // `age` variable is declared and becomes the owner of the i32 value 33.
                  // 33 is pushed onto the Stack.

    println!("Age in main scope: {}", age); // `age` is in scope, valid.

    { // A new, nested block and scope start
        let is_handsome = true; // `is_handsome` is declared and becomes the owner of the bool value `true`.
                                // `true` is pushed onto the Stack (on top of 33).

        println!("Is handsome in inner scope: {}", is_handsome); // `is_handsome` is in scope, valid.
        println!("Age also valid in inner scope: {}", age);     // `age` is still in scope (outer scope).
    } // End of the inner block. `is_handsome` goes OUT of scope here.
      // As its owner, `is_handsome` is responsible for dropping `true`.
      // The `true` value is popped off the Stack (LIFO).

    // println!("Is handsome here? {}", is_handsome); // ERROR: `is_handsome` not found (out of scope, dropped)

    println!("Age still valid in main scope: {}", age); // `age` is still in scope, valid.
} // End of the `main` function's block. `age` goes OUT of scope here.
  // As its owner, `age` is responsible for dropping `33`.
  // The `33` value is popped off the Stack (LIFO).
  // Program ends.
```

### III. LIFO (Last-In, First-Out) for Stack Cleanup

- **Stack Data Cleanup Order:** Data stored on the stack is cleaned up (popped off) in a **LIFO (Last-In, First-Out)** order. The last value pushed onto the stack is the first one popped off.
    
- **Connection to Ownership:** This LIFO order aligns perfectly with how variables go out of scope:
    
    1. Variables declared later (pushed later) are usually in more deeply nested scopes or are the most recent declarations in the current scope.
        
    2. These variables go out of scope first as execution unwinds from inner blocks to outer blocks, or simply from the bottom of a block upwards.
        
    3. As each variable goes out of scope, its owner (the variable itself) triggers the drop, and the corresponding stack entry is popped.
        

**Example Walkthrough of LIFO Cleanup:**

Consider these two variables declared in the same scope:

Rust

```Rust
fn main() {
    let first_value = 100;    // Pushes 100 onto Stack. Owner: `first_value`
    let second_value = true;  // Pushes `true` onto Stack (on top of 100). Owner: `second_value`

    // ... program logic ...

} // End of main function scope
  // Cleanup happens here in LIFO order:

// 1. `second_value` goes out of scope first (last one in).
//    As owner, it drops `true`. `true` is popped off the Stack.

// 2. `first_value` goes out of scope second (first one in).
//    As owner, it drops `100`. `100` is popped off the Stack.
```

### IV. Summary of Ownership with Stack Data

- **Every value has an owner.**
    
- **Variables** are common owners of values.
    
- The owner is **responsible for deallocating the value's memory**.
    
- This deallocation happens **automatically** when the owner (variable) **goes out of scope**.
    
- For **Stack data**, deallocation means popping the value off the stack, which occurs in **LIFO** order.
    
- This tight integration of ownership with scopes ensures memory safety for stack-allocated data.
    

This foundation of ownership with stack data is crucial as we move on to understanding how Rust manages the more complex Heap memory, which is where ownership's power truly shines.
