This review section provides a comprehensive overview of the key concepts related to ownership in Rust. It covers the fundamental principles of ownership, memory management with the stack and heap, and how these concepts apply to different data types and operations.

### Ownership

Ownership is Rust's core feature for memory management without a garbage collector. The fundamental rules are:

1. **Each value has a single owner.** At any given time, only one variable is responsible for cleaning up the data it owns.
    
2. **Only one owner.** A value can't have more than one owner simultaneously.
    
3. **Ownership moves.** When a value is assigned to a new variable or passed to a function, its ownership can be transferred, which is called a **move**. The previous owner is then considered invalid.
    

---

### The Stack and the Heap

Rust manages memory using two main regions: the **stack** and the **heap**.

- **The Stack**: This is a fast, structured memory region for storing data of a **fixed, known size** at compile time. Data is added and removed in a Last-In, First-Out (LIFO) order. Primitive types like `i32`, `f64`, and `bool` are stored on the stack.
    
- **The Heap**: This is a flexible memory region for storing data of a **dynamic, unknown size** at compile time. Accessing data on the heap is slower than the stack. When data is allocated on the heap, a **pointer** to its location is stored on the stack. The `String` type is a primary example of a data type that stores its content on the heap.
    

---

### String Types: `str` vs. `String`

Rust has two primary string types:

- **`str` (string literal/string slice)**: This is a fixed-size string whose content is known at compile time and is embedded directly into the program's binary. It resides in the read-only memory section of the program.
    
- **`String`**: This is a mutable, heap-allocated string. Its size can grow or shrink at runtime, making it suitable for dynamic content like user input. The `String` type does **not** implement the `Copy` trait.
    

---

### The `Copy` Trait and Cloning

- **The `Copy` Trait**: Types that implement this trait can be automatically duplicated when assigned to a new variable or passed to a function. This is because creating a full copy is cheap and efficient. Primitive types (integers, floats, Booleans) implement `Copy`.
    
- **The `Clone` Trait and `clone()` Method**: For types that don't implement `Copy` (like `String`), creating a duplicate requires an explicit action. The `clone()` method is used to manually create a deep copy of the data, ensuring ownership doesn't move and both variables are valid.
    

---

### References and Borrowing

- **References**: A reference is an address that points to a value in memory. It's similar to a pointer in other languages but is guaranteed to be valid by the compiler.
    
- **Borrowing**: This is the act of creating a reference to a value. It allows you to use data without taking ownership. When you borrow a value, the original owner remains valid.
    
- **Borrowing Rules**:
    
    - You can have multiple **immutable references** to a value.
        
    - You can have only **one mutable reference** to a value.
        
    - You cannot mix mutable and immutable references.
        

These rules prevent data races at compile time. Immutable references implement the `Copy` trait, meaning you can have as many copies of a reference as you want.

---

### Ownership and Functions

When a value is passed to a function:

- If the type implements `Copy` (e.g., `i32`), a copy of the value is made for the function parameter.
    
- If the type does not implement `Copy` (e.g., `String`), **ownership is moved** to the function parameter. The original variable is then invalid. To prevent data from being deallocated at the end of the function's scope, the function must return the value, which can be cumbersome. Using **references** to pass data to functions is a common solution to this problem, as it avoids transferring ownership.
