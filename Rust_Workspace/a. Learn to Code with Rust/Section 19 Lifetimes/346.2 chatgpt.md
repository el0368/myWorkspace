# Lifetimes — in-depth study guide (detailed, example-first, in-scope)

---

## Core idea (short)

A **lifetime** describes _how long_ a value (or more precisely: the data a reference points to) is valid. Lifetimes exist so the **borrow checker** can ensure references never outlive the data they point to — preventing dangling references at compile time.

> Important: lifetimes are a _compile-time_ concept. They do not exist at runtime and have no performance cost.

---

## Scope, owner, referent, and reference

- **Scope / block**: region between `{ ... }` where names are valid. When a variable (owner) goes out of scope, its data is cleaned up.
    
- **Owner:** the binding that owns the value (e.g., a `String` variable).
    
- **Referent:** the actual data a reference points to (the thing being borrowed).
    
- **Reference:** an address to the referent, created with `&` (immutable) or `&mut` (mutable).
    
- **Reference lifetime:** the period during which following that address is valid; it must be contained inside the referent’s lifetime.
    

---

## Why lifetimes matter

Rust prevents **dangling references** by ensuring:

> every reference's lifetime is fully contained in the lifetime of the referent.

If you try to return a reference to data created inside a function, the compiler forbids it:

```rust
fn bad() -> &str {
    let s = String::from("hello");
    &s   // ERROR: returns reference to local value that will be dropped
}
```

**Fixes:** return an owned `String` or accept a reference parameter whose lifetime outlives the returned reference.

---

## Generic lifetime annotations — syntax & intent

You annotate lifetimes with a tick name (convention: `'a`, `'b`):

```rust
fn foo<'a>(x: &'a str) -> &'a str { x }
```

- The annotation `'a` declares a **generic lifetime parameter** (a placeholder lifetime).
    
- Annotations express relationships between lifetimes of inputs and outputs — **they don't extend or shorten actual lifetimes**, they only describe which lifetimes must relate to which.
    

---

## Common function examples

### Single reference parameter → elision covers it

If the function has one reference parameter and returns a reference, the compiler implicitly ties the return to that parameter (elision rule). You can omit explicit lifetimes:

```rust
fn first_word(s: &str) -> &str { s.split_whitespace().next().unwrap_or("") }
```

### Multiple reference parameters → you must annotate relationships

When there are multiple input references and you return a reference, you need to tell the compiler which input the return borrows from.

Correct pattern: return a reference with a lifetime tied to one (or the overlapping portion) of the inputs:

```rust
// explicit lifetimes: return value has lifetime 'a, tied to both inputs
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

If input lifetimes differ, the returned reference will be constrained to the **shorter (overlap)** lifetime — the compiler enforces safety.

### Example: attempt to return reference to local variable (error)

```rust
fn wrong<'a>() -> &'a str {
    let s = String::from("hello");
    &s // error: `s` doesn't live long enough
}
```

**Lesson:** lifetimes cannot make a local value live longer — return an owned value instead.

---

## Lifetime elision rules (the three rules the compiler applies)

The compiler automatically applies these rules when lifetimes are omitted:

1. **Each** reference parameter gets its own anonymous lifetime.  
    e.g., `fn f(x: &i32, y: &i32)` → `fn f<'a, 'b>(x: &'a i32, y: &'b i32)`
    
2. If there is **exactly one** input lifetime, that lifetime is assigned to **all** output lifetimes.  
    e.g., `fn f(x: &str) -> &str` → return is tied to `x`.
    
3. If there are multiple input lifetimes and the method has `&self` or `&mut self`, the lifetime of `self` is assigned to output lifetimes.  
    This is why `fn get_part(&self) -> &str` works without explicit annotations (the return is tied to `self`).
    

If none of these rules apply, you must write out lifetime annotations.

---

## Methods, `impl` blocks, and elision

Method return types are often elided thanks to rule 3. Example:

```rust
struct Book { content: String }

impl Book {
    // elision: &self -> return &str uses same lifetime as &self
    fn part(&self) -> &str {
        // returns a slice of self.content
        &self.content[..5]
    }
}
```

You rarely need explicit annotations for common patterns involving `self`.

---

## Structs that hold references — lifetime parameters required

If a struct stores a reference, the struct type must declare a lifetime parameter:

```rust
struct Excerpt<'a> {
    part: &'a str,
}

// implement methods
impl<'a> Excerpt<'a> {
    fn part(&self) -> &str { self.part } // elision ties return to &self
}
```

Key rule: the struct cannot outlive the referent. Putting a `'a` on the struct tells the compiler: _this struct borrows data valid for at least `'a`_.

---

## `'static` lifetime

- `'static` means “for the entire duration of the program.”
    
- String literals have `'static` lifetime:
    
    ```rust
    let s: &'static str = "I am static";
    ```
    
- Use `'static` when data truly must live for the whole program (e.g., certain global data), but prefer shorter lifetimes when possible.
    

---

## Non-lexical lifetimes (NLL) — practical behavior

Rust’s borrow checker uses **non-lexical lifetimes**, meaning a reference’s lifetime ends at its **last use** rather than the end of the surrounding scope.

Example where NLL helps:

```rust
let mut s = String::from("hello");
let r1 = &s;           // immutable borrow
println!("{}", r1);    // last use of r1
let r2 = &mut s;       // allowed thanks to NLL: r1 is no longer used
r2.push_str(" world");
```

Before NLL, the immutable borrow would have persisted to the end of the scope and blocked `&mut` borrow.

---

## Lifetime bounds with generics (`T: 'a`)

When generics interact with references you sometimes need to state that a generic type must live at least as long as some lifetime:

```rust
fn process<'a, T>(x: &'a T) where T: 'a { /* ... */ }
```

`T: 'a` means “any owned values inside `T` (like references held in T) must live at least as long as `'a`.” This is common when you store references inside generic structs.

---

## How the compiler chooses the effective lifetime when inputs differ

If you pass references with different concrete lifetimes into a function whose signature uses a single generic lifetime (e.g., `'a`), the compiler uses the **intersection** (overlap) — effectively the shortest lifetime that both inputs share. The returned reference must be valid within that overlapping region.

---

## Common lifetime errors and fixes

1. **`missing lifetime specifier`** (e.g., `fn foo(x: &str) -> &str { ... }` with multiple refs)  
    **Fix:** add lifetime annotations or redesign API to return owned data.
    
2. **`returns a reference to data owned by the current function`**
    
    - You tried to return a reference to a local value.  
        **Fix:** return an owned `String` or accept an input reference and return a reference tied to it.
        
3. **`borrowed value does not live long enough`**
    
    - You stored a reference with a longer expected lifetime than the referent actually provides.  
        **Fix:** ensure referent outlives the holder (reorder scopes), or make the holder own the data (use `String`), or adjust lifetime parameters.
        
4. **struct lifetime mismatch**
    
    - Struct claims a lifetime `'a` but the provided reference has a shorter lifetime.  
        **Fix:** ensure the referent lives at least as long as `'a`.
        

---

## Best practices & mental model

- **Prefer returning owned types** (`String`) when lifetime relationships are inconvenient.
    
- Use **lifetime annotations** to _express relationships_, not to change how long data lives.
    
- For simple APIs, rely on **elision rules** — they cover most method signatures.
    
- Use **`&str` parameters** for maximum flexibility (accepts `&String` and literals).
    
- When a struct stores references, annotate it with a lifetime parameter and prefer passing references that outlive the struct.
    
- Keep lifetimes short and explicit only when necessary; readers often find many explicit annotations noisy — use them when compiler asks for them.
    
- Remember: lifetimes fix **compile-time safety**, not runtime semantics.

## Quick checklist when you see lifetime errors

- Am I returning a reference to a local variable? If yes, return owned value.
    
- Is the return reference clearly tied to one of the input references? If not, annotate lifetimes.
    
- Does a struct hold references? If yes, add lifetime parameter to the struct.
    
- Could I avoid complexity by returning an owned value (`String`) instead?
    
- Are my references shorter-lived than the data they point to? Ensure the referent outlives the reference.

## Short FAQ

**Q:** Do lifetimes change how long values live at runtime?  
**A:** No. Lifetimes are compile-time checks only.

**Q:** Are lifetime names meaningful?  
**A:** No — `'a`, `'b` are conventions. The name matters only to match annotations, not semantics.

**Q:** When should I use explicit annotations?  
**A:** When elision rules don’t apply (e.g., multiple input references and returning a reference), or when defining structs that hold references.

**Q:** Is `'static` safe to use everywhere?  
**A:** Use `'static` only for truly static data (like string literals). For general references, prefer shorter lifetimes.
