

Here’s a focused, progressive study guide showing **trait bounds** vs **`impl Trait`** for function parameters, how they differ for **one vs two parameters**, and how to pick between them. Everything is in **one runnable code block** with inline comments.

```rust
use std::collections::HashMap;

// -----------------------------
// 0) A trait we’ll use in all examples
// -----------------------------
trait Accommodation {
    // Default body: any implementor can skip overriding this.
    fn get_description(&self) -> String {
        String::from("A wonderful place to stay.")
    }

    // Must be implemented by every type.
    fn book(&mut self, guest: &str, nights: u32);
}

// -----------------------------
// 1) Two concrete types implementing the trait
// -----------------------------
#[derive(Debug)]
struct Hotel {
    name: String,
    reservations: HashMap<String, u32>,
}

impl Hotel {
    fn new(name: &str) -> Self {
        Self { name: name.to_string(), reservations: HashMap::new() }
    }
}

impl Accommodation for Hotel {
    // uses default get_description()
    fn book(&mut self, guest: &str, nights: u32) {
        self.reservations.insert(guest.to_string(), nights);
    }
}

#[derive(Debug)]
struct Airbnb {
    host: String,
    guests: Vec<(String, u32)>,
}

impl Airbnb {
    fn new(host: &str) -> Self {
        Self { host: host.to_string(), guests: Vec::new() }
    }
}

impl Accommodation for Airbnb {
    // override the default
    fn get_description(&self) -> String {
        format!("Please enjoy {}'s apartment.", self.host)
    }

    fn book(&mut self, guest: &str, nights: u32) {
        self.guests.push((guest.to_string(), nights));
    }
}

// -----------------------------------------------------------
// 2) Single-parameter functions: impl Trait vs trait bounds
// -----------------------------------------------------------

// (A) Parameter as `&mut impl Accommodation`
// - “Accept a mutable reference to *some* type that implements Accommodation.”
// - This is concise and common when you don’t need to name the type `T`.
fn book_for_one_night_impl(entity: &mut impl Accommodation, guest: &str) {
    entity.book(guest, 1);
    println!("(impl) {}", entity.get_description());
}

// (B) Equivalent using a named generic with a trait bound
// - Same effect as above, just written with a generic type parameter `T: Accommodation`.
// - Useful when you need to repeat `T` in multiple positions (params/returns).
fn book_for_one_night_generic<T: Accommodation>(entity: &mut T, guest: &str) {
    entity.book(guest, 1);
    println!("(generic) {}", entity.get_description());
}

// Same as (B) but using a `where` clause for readability when bounds get long.
fn book_for_one_night_where<T>(entity: &mut T, guest: &str)
where
    T: Accommodation,
{
    entity.book(guest, 1);
    println!("(where) {}", entity.get_description());
}

// -------------------------------------------------------------------------
// 3) Two-parameter functions: do we allow the *same* or *different* types?
// -------------------------------------------------------------------------

// (A) Two independent `impl Accommodation` parameters
// - Each parameter can be a *different* concrete type.
// - Great when you want maximum flexibility.
fn mix_impl_params(
    first: &mut impl Accommodation,
    second: &mut impl Accommodation,
    guest: &str,
) {
    first.book(guest, 1);
    second.book(guest, 1);
}

// (B) One generic type `T: Accommodation` shared by both parameters
// - Forces *both* params to be the *same* concrete type.
// - The compiler monomorphizes one version per concrete `T`.
fn same_type_generic<T: Accommodation>(
    first: &mut T,
    second: &mut T,
    guest: &str,
) {
    first.book(guest, 1);
    second.book(guest, 1);
}

// (C) Two generics `T: Accommodation, U: Accommodation`
// - Lets each param be its *own* type, but you still get the benefits of named generics.
fn two_types_generic<T: Accommodation, U: Accommodation>(
    first: &mut T,
    second: &mut U,
    guest: &str,
) {
    first.book(guest, 1);
    second.book(guest, 1);
}

// ---------------------------------
// 4) Demo
// ---------------------------------
fn main() {
    // Prepare values
    let mut hotel = Hotel::new("The Luxe");
    let mut airbnb = Airbnb::new("Peter");

    // --- Single-parameter: all three forms behave the same ---
    book_for_one_night_impl(&mut hotel, "Piers");
    book_for_one_night_impl(&mut airbnb, "Piers");

    book_for_one_night_generic(&mut hotel, "Ava");
    book_for_one_night_generic(&mut airbnb, "Ava");

    book_for_one_night_where(&mut hotel, "Maya");
    book_for_one_night_where(&mut airbnb, "Maya");

    println!("After single-parameter calls:\n  hotel = {:#?}\n  airbnb = {:#?}\n", hotel, airbnb);

    // --- Two-parameter: differences in allowed argument types ---

    // (A) Two `impl` params -> can mix different types freely
    mix_impl_params(&mut hotel, &mut airbnb, "Sam");

    // (B) Same-type generic -> both arguments must be the *same* concrete type
    // Works when both are Hotels:
    let mut hotel2 = Hotel::new("The Grand");
    same_type_generic(&mut hotel, &mut hotel2, "Quinn");

    // ❌ Won’t compile (kept as comment):
    // same_type_generic(&mut hotel, &mut airbnb, "Nope");
    // error: expected &mut T (Hotel), found &mut Airbnb

    // (C) Two generics -> can mix different types *and* still name types if needed
    two_types_generic(&mut hotel, &mut airbnb, "Riley");

    println!("After two-parameter calls:\n  hotel = {:#?}\n  hotel2 = {:#?}\n  airbnb = {:#?}", hotel, hotel2, airbnb);
}

/* ===========================
    What to remember
   ===========================
- `&mut impl Trait`: concise; great for 1–2 parameters; each param can be a different type.
- `T: Trait`: name the type so you can reuse it (multiple params/returns). A single `T` forces the same type across all its uses.
- `T: Trait, U: Trait`: multiple generics let parameters be different types while still naming them.
- `where` clause: identical semantics; improves readability for long/complex bounds.
- Performance: Both `impl Trait` (in params) and `T: Trait` use static dispatch via monomorphization (zero runtime cost). To opt into dynamic dispatch, use trait objects like `&mut dyn Accommodation`.
*/
```

---

### 1. The Core Idea

We’re working with a **trait** (`Accommodation`) and two types (`Hotel` and `Airbnb`) that implement it.  
We want to write functions that can take **any type that implements this trait**, but sometimes we want to restrict _how_ those types are used together.

Rust gives us two main syntaxes for that:

- **`impl Trait` in function parameters** → short, simple, good when we don’t need to name the type.
    
- **Generics with trait bounds (`T: Trait`)** → a bit longer, but gives us more control (like requiring multiple parameters to be the same type).
    

---

### 2. Single-Parameter Functions

All three versions (`impl`, `T: Trait`, and `where T: Trait`) do exactly the same thing for one parameter:

- `book_for_one_night_impl`:  
    Just says “take any type that implements `Accommodation`.” It doesn’t care what the actual type is.
    
- `book_for_one_night_generic<T: Accommodation>`:  
    Same thing, but now we name the type `T`. That’s useful if we need to refer to `T` in multiple places (like return type or another parameter).
    
- `book_for_one_night_where<T> where T: Accommodation`:  
    Same as the above, but written in a `where` clause to make signatures easier to read when you have many bounds.
    

👉 Bottom line: for **one parameter**, `impl Trait` is shorter, but generics are more flexible if you need to reuse the type name.

---

### 3. Two-Parameter Functions

Here’s where the difference really matters.

- **Two `impl Trait` parameters**:
    
    ```rust
    fn mix_impl_params(first: &mut impl Accommodation, second: &mut impl Accommodation, guest: &str)
    ```
    
    Each parameter can be a different type.  
    Example: `Hotel` for `first`, `Airbnb` for `second`. Works fine.
    
- **One generic `T: Accommodation` for both**:
    
    ```rust
    fn same_type_generic<T: Accommodation>(first: &mut T, second: &mut T, guest: &str)
    ```
    
    Now both parameters must be the same type, because they share the same `T`.  
    Example: `Hotel` + `Hotel` works, but `Hotel` + `Airbnb` won’t compile.
    
- **Two different generics `T` and `U`**:
    
    ```rust
    fn two_types_generic<T: Accommodation, U: Accommodation>(first: &mut T, second: &mut U, guest: &str)
    ```
    
    Lets each parameter be its own type again (like `impl Trait`), but now you can also _name_ them if you need to use those type names later (returning one of them, storing them, etc.).
    

👉 Bottom line:

- Use **two `impl Trait`** when you just want flexibility without naming types.
    
- Use **one generic `T`** when both arguments must be the same type.
    
- Use **two generics `T, U`** when arguments can differ, but you need to refer to their concrete types somewhere else.
    

---

### 4. Dispatch and Performance

- All these versions (`impl Trait` and `T: Trait`) use **static dispatch**. That means the compiler generates specialized code for each concrete type (monomorphization).
    
- This has **no runtime cost**—it’s zero-cost abstraction.
    
- If you wanted **dynamic dispatch** (deciding at runtime which implementation to use), you’d write `&mut dyn Accommodation` instead. That trades performance for flexibility.
    

---

### 5. Mental Model

Think of it like this:

- **`impl Trait` in params** = “I don’t care what type you give me, as long as it implements this trait.”
    
- **Generic `T: Trait`** = “I need to name this type, because I want to enforce consistency (or reuse it).”
    
- **Multiple generics (`T, U`)** = “I’ll accept multiple independent types, but I still want to track their identities.”
    

---

📌 **Key takeaway for your code:**  
For single parameters, all three forms are interchangeable. For multiple parameters, the choice depends on whether you want them to be the _same type_ or _potentially different types_.
