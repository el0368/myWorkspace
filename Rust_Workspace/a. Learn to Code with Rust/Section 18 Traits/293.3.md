### **How `self.get_description()` calls the trait method**

1. **Trait implementation guarantees the method exists**
    

```rust
trait Describe {
    fn get_description(&self) -> String {
        String::from("Default description")
    }
}

struct Hotel {
    name: String,
}

impl Describe for Hotel {} // Hotel now "implements" Describe
```

- The trait `Describe` provides `get_description`.
    
- `impl Describe for Hotel {}` tells Rust: _Hotel implements this trait_.
    
- Even though we didn’t define `get_description` in the `Hotel` block, Rust **automatically uses the trait’s default method**.
    

---

2. **Calling it inside `impl Hotel`**
    

```rust
impl Hotel {
    fn summarize(&self) -> String {
        format!("{}: {}", self.name, self.get_description())
    }
}
```

- When you write `self.get_description()`:
    
    1. Rust first looks for a **method named `get_description` in `impl Hotel`**.
        
    2. If it doesn’t exist, Rust checks the **traits implemented by Hotel**.
        
    3. It finds `Describe::get_description` and calls it automatically.
        
- So `self.get_description()` **resolves to the trait method** because Hotel implements the trait and didn’t override it.
    

---

3. **Important points**
    

- If you **defined `get_description` in `impl Hotel`**, that would take priority. The trait’s default would be ignored.
    
- This allows methods like `summarize` to **reuse trait functionality** without knowing whether the type has a custom implementation or the default.
    

---

4. **Analogy**
    

Think of it like this:

- `Describe` is a “manual” every hotel follows.
    
- `Hotel` doesn’t write its own `get_description`, so it just **reads the manual**.
    
- When `summarize()` wants a description, it **asks Hotel**, which consults the manual if it doesn’t have its own instructions.
