### Traits with Default Implementations

Up to now, our `Accommodation` trait only acted as a **contract**: it required every type that implemented it to define both methods, `get_description` and `book`.

But traits in Rust can do more. Instead of always requiring implementers to write _all_ the methods themselves, we can provide **default implementations**. These act like fallbacks:

- If a type implements the method explicitly, Rust uses that version.
    
- If a type _doesn’t_ implement the method, Rust falls back to the default provided in the trait definition.
    

This gives us flexibility: some methods can be mandatory, others optional with a sensible default.

---

### Updating the `Accommodation` Trait

Suppose we decide that every accommodation must define its own `book` method, because booking is very specific to the type. But for `get_description`, we can provide a generic fallback.

Here’s how the trait looks now:

```rust
trait Accommodation {
    fn get_description(&self) -> String {
        String::from("A wonderful place to stay")
    }

    fn book(&mut self, name: &str, nights: u32);
}
```

Notice the difference:

- `book` still ends with a semicolon (`;`), meaning it has no body and must be implemented.
    
- `get_description` now has a body, returning a generic string.
    

---

### What Happens with Default Methods

1. **If a type defines its own `get_description`**:  
    That custom version overrides the default. For example, both `Hotel` and `Airbnb` previously had their own unique descriptions, and those are the ones that will run.
    
2. **If a type does _not_ define `get_description`**:  
    Rust automatically uses the default implementation from the trait. The code still compiles, and calls to `get_description` return `"A wonderful place to stay"`.

### Example: Removing a Method

Let’s say we remove `get_description` from `Hotel`’s implementation:

```rust
impl Accommodation for Hotel {
    fn book(&mut self, name: &str, nights: u32) {
        self.reservations.insert(name.to_string(), nights);
    }
}
```

Now `Hotel` only implements `book`. If we call `hotel.get_description()`, Rust will fall back to the default method from the trait and print:

```
A wonderful place to stay
```

Meanwhile, `Airbnb` still defines its own `get_description`, so calling it will return something like:

```
Please enjoy Peter's apartment!
```

### Mixing Defaults and Mandatory Methods

This shows how traits can combine:

- Some methods (like `book`) are **required**, forcing each implementer to write its own.
    
- Others (like `get_description`) can be **optional**, since we’ve given a generic default.
    

This pattern is useful when you want consistency across types but also want to avoid writing boilerplate code if a generic behavior is “good enough.”

---

✅ **Key Takeaway**:  
Traits don’t just define contracts. They can also provide reusable behavior through default method implementations. This makes traits more flexible: each type can either stick with the defaults or override them with something more specific.
