# Rust Error Handling - Comprehensive Study Guide

## Core Error Categories

### Recoverable Errors

Recoverable errors are situations where your program encounters a problem but can gracefully handle it and continue execution. These errors don't crash your program - instead, they provide you with information about what went wrong so you can decide how to respond.

**Key characteristics:**

- Program continues running
- Can be handled programmatically
- Represented by the `Result<T, E>` enum
- Allow for graceful degradation of functionality

**Common scenarios:**

- File not found when trying to open it
- Network connection timeout
- Invalid user input
- Permission denied errors

### Unrecoverable Errors (Panics)

Unrecoverable errors are critical failures that prevent your program from continuing safely. When these occur at runtime, Rust triggers a "panic" - essentially a controlled crash of your program.

**Key characteristics:**

- Program terminates immediately
- Indicates a logical error in your code
- Provides a backtrace showing the call stack
- Should be avoided in production code when possible

**When panics occur:**

- Array index out of bounds
- Integer overflow (in debug mode)
- Assertion failures
- Calling `unwrap()` on a `None` or `Err` value

## Program Termination Strategies

### Graceful Exit with `process::exit()`

Instead of allowing a panic to crash your program ungracefully, you can use `std::process::exit()` to terminate your program in a controlled manner.

**Function signature:** `exit(code: i32)`

**Exit code conventions:**

- `0`: Program completed successfully without errors
- Any positive integer (typically `1`): Program encountered an error
- These codes can be read by shells, scripts, or other programs that launched your application

**Example usage:**

```rust
use std::process;

if critical_error_occurred {
    eprintln!("Fatal error: Cannot continue execution");
    process::exit(1);
}
```

## Output Streams and Error Reporting

### Standard Output vs Standard Error

Your program has access to two separate output channels, similar to different TV channels where you can broadcast different types of messages.

**Standard Output (`stdout`):**

- Used with `println!` macro
- Intended for normal program output
- Can be redirected to files easily
- Contains the "results" of your program

**Standard Error (`stderr`):**

- Used with `eprintln!` macro
- Intended for error messages and diagnostics
- Usually displayed on terminal even when stdout is redirected
- Helps separate success data from error information

**Practical benefits:**

- You can save successful results to a file while still seeing errors on screen
- Log analysis tools can process different streams separately
- Shell scripts can handle success and error cases differently

## The Result Enum - Modeling Recoverable Errors

### Structure and Purpose

The `Result<T, E>` enum is Rust's primary mechanism for handling operations that might fail. It forces you to explicitly handle both success and failure cases.

**Enum definition:**

```rust
enum Result<T, E> {
    Ok(T),    // Success variant containing the successful result
    Err(E),   // Error variant containing error information
}
```

**Generic type parameters:**

- `T`: Type of the success value
- `E`: Type of the error value

### Common Functions Returning Result

**File operations:**

- `File::open()`: Returns `Result<File, io::Error>`
- Opening files can fail due to permissions, file not existing, etc.

**Input operations:**

- `stdin().read_line()`: Returns `Result<usize, io::Error>`
- Reading input can fail due to I/O errors

## Pattern Matching with Results

### Using `match` Statements

The `match` statement provides comprehensive handling of all possible `Result` variants:

```rust
match file_operation_result {
    Ok(file) => {
        // Handle successful case
        // Use the file here
    }
    Err(error) => {
        // Handle error case
        // Deal with the error appropriately
    }
}
```

**Benefits:**

- Compiler ensures you handle all cases
- Explicit about what happens in each scenario
- Can extract values from both variants

### Using `if let` for Selective Handling

When you only care about one specific variant, `if let` provides a more concise approach:

```rust
if let Ok(file) = File::open("config.txt") {
    // Only execute if file opened successfully
    // Use file here
}
// Silently ignore the error case
```

**When to use `if let`:**

- You only care about the success case
- Error handling is done elsewhere or not needed
- You want cleaner, less verbose code

## Error Propagation

### The Concept

Error propagation means passing errors up the call chain instead of handling them immediately. This allows calling code to decide how to handle errors based on their specific context.

**Benefits of propagation:**

- **Separation of concerns**: Functions focus on their primary responsibility
- **Flexibility**: Different callers can handle the same error differently
- **Composability**: Errors can be handled at the most appropriate level
- **Cleaner code**: Less nested error handling in helper functions

### Manual Error Propagation

```rust
fn read_config() -> Result<String, io::Error> {
    match File::open("config.txt") {
        Ok(mut file) => {
            match file.read_to_string(&mut contents) {
                Ok(_) => Ok(contents),
                Err(e) => Err(e), // Propagate the error up
            }
        }
        Err(e) => Err(e), // Propagate the error up
    }
}
```

### The Question Mark Operator (`?`)

The `?` operator provides elegant syntax for error propagation, dramatically reducing boilerplate code.

**How it works:**

- If the `Result` is `Ok(value)`: extracts `value` and continues execution
- If the `Result` is `Err(error)`: immediately returns `Err(error)` from the function

**Equivalent transformations:**

```rust
// Verbose manual approach
let file = match File::open("config.txt") {
    Ok(f) => f,
    Err(e) => return Err(e),
};

// Concise with ? operator
let file = File::open("config.txt")?;
```

**Method chaining with `?`:**

```rust
fn process_config() -> Result<ProcessedConfig, io::Error> {
    let content = File::open("config.txt")?
        .read_to_string()?
        .parse()?;
    
    Ok(ProcessedConfig::new(content))
}
```

## Option Enum and the `?` Operator

### Similar Patterns with Option

The `Option<T>` enum represents the presence or absence of a value, and the `?` operator works similarly:

**With `Option<T>`:**

- `Some(value)`: extracts `value` and continues
- `None`: immediately returns `None` from the function

**Parallel behavior:**

- Both `Result` and `Option` have a "success" case you want to continue with
- Both have a "failure" case where you want to terminate early
- The `?` operator provides consistent syntax for both

### Early Return Pattern

The `?` operator implements the "early return" pattern, which is common in error handling:

1. Try an operation
2. If it succeeds, continue with the extracted value
3. If it fails, immediately return the failure to the caller

This pattern keeps your code focused on the "happy path" (success case) while cleanly handling failures.

## Best Practices and Design Principles

### Function Responsibility

- Keep functions focused on a single responsibility
- If a function can fail in many different ways, it might be doing too much
- Functions should either succeed completely or fail cleanly

### Error Handling Strategy

- Use `Result` for recoverable errors
- Reserve panics for truly unrecoverable situations
- Propagate errors when the caller is better positioned to handle them
- Handle errors locally when you have sufficient context

### Code Organization

- Separate error handling logic from business logic
- Use the `?` operator to keep happy path code readable
- Choose between `match` and `if let` based on how many variants you need to handle

### Testing and Debugging

- Use backtraces to understand panic locations
- Test both success and failure paths in your functions
- Consider using `Result` even for internal functions to improve testability
