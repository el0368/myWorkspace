## 1. Defining the Trait

We start with a `trait` that represents a contract. Any type that implements it must provide these methods.

```rust
trait Accommodation {
    fn get_description(&self) -> String;
    fn book(&mut self, guest: &str, nights: u32);
}
```

- `&self`: Immutable access (can read, cannot change).
    
- `&mut self`: Mutable access (can read _and_ change).
    
- Any struct that implements `Accommodation` must define both methods.
    

---

## 2. Implementing for Concrete Types

### Example: `Hotel`

```rust
#[derive(Debug)]
struct Hotel {
    name: String,
    reservations: std::collections::HashMap<String, u32>,
}

impl Hotel {
    fn new(name: &str) -> Self {
        Self {
            name: name.to_string(),
            reservations: std::collections::HashMap::new(),
        }
    }
}

impl Accommodation for Hotel {
    fn get_description(&self) -> String {
        format!("{}: a wonderful place to stay.", self.name)
    }

    fn book(&mut self, guest: &str, nights: u32) {
        self.reservations.insert(guest.to_string(), nights);
    }
}
```

---

### Example: `Airbnb`

```rust
#[derive(Debug)]
struct Airbnb {
    location: String,
    guests: Vec<(String, u32)>,
}

impl Airbnb {
    fn new(location: &str) -> Self {
        Self {
            location: location.to_string(),
            guests: Vec::new(),
        }
    }
}

impl Accommodation for Airbnb {
    fn get_description(&self) -> String {
        format!("Airbnb in {}", self.location)
    }

    fn book(&mut self, guest: &str, nights: u32) {
        self.guests.push((guest.to_string(), nights));
    }
}
```

At this point, both `Hotel` and `Airbnb` satisfy the same trait contract but store bookings differently.

## 3. Functions With Trait Bounds

### (a) Immutable Reference

Suppose we just want to read a description:

```rust
fn print_description(entity: &impl Accommodation) {
    println!("{}", entity.get_description());
}
```

- Works with **any type** that implements `Accommodation`.
    
- Takes `&impl Accommodation`, so it borrows immutably.
    
- Cannot mutate the underlying data.
    

Usage:

```rust
let hotel = Hotel::new("The Luxe");
let airbnb = Airbnb::new("Downtown Loft");

print_description(&hotel);
print_description(&airbnb);
```

---

### (b) Mutable Reference

Now we want to perform bookings, which require mutation:

```rust
fn book_for_one_night(entity: &mut impl Accommodation, guest: &str) {
    entity.book(guest, 1);
}
```

Usage:

```rust
let mut hotel = Hotel::new("The Luxe");
let mut airbnb = Airbnb::new("Downtown Loft");

book_for_one_night(&mut hotel, "Piers");
book_for_one_night(&mut airbnb, "Amanda");

println!("{:#?}", hotel);
println!("{:#?}", airbnb);
```

At runtime:

- `Hotel` stores `{"Piers": 1}` in its map.
    
- `Airbnb` stores `[("Amanda", 1)]` in its vector.

## 4. Why `impl Trait` Works

- `impl Trait` means _any type implementing that trait_.
    
- At compile-time, Rust checks that the provided type honors the trait.
    
- Inside the function body, Rust guarantees the methods defined in the trait exist.
    
- This makes the function **generic** without using explicit type parameters.
    

---

## 5. Generic Syntax Alternative

Instead of `impl Trait`, you can use a generic parameter:

```rust
fn book_for_one_night<T: Accommodation>(entity: &mut T, guest: &str) {
    entity.book(guest, 1);
}
```

- `T: Accommodation` means "`T` must implement the `Accommodation` trait."
    
- Both versions (`impl Trait` and generic bound) are equivalent in this simple case.
    
- The generic form is more powerful when you need multiple parameters constrained to the same type `T`.

## 7. Key Takeaways

- `impl Trait` makes functions **type-agnostic** but **trait-aware**.
    
- References control whether mutation is allowed (`&` vs `&mut`).
    
- Trait-bound functions make code **reusable and extensible**: you can add new `Accommodation` types in the future with no changes to the functions.
    
- Use **generic bounds (`T: Trait`)** when you need more control, especially with multiple generic parameters.
