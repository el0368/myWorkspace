### Part 1: The `Result` Enum & The `Ok` Variant

This progressive example introduces the **`Result` enum**, which is Rust's idiomatic way of handling operations that can either succeed or fail. We demonstrate the `Ok` variant, which represents success, and a common compiler issue related to its generic types.

- **The `Result` Enum:** The `Result` enum has two variants: `Ok(T)` for a successful value and `Err(E)` for an error value. `T` and `E` are generic type parameters.
    
- **The Problem with `Ok`:** When you create a `Result::Ok` instance, the compiler can infer the type of `T` from the associated data you provide. However, it has no way to infer the type of `E` (the error type), which leads to a compile-time error.
    
- **The Solution:** To fix this, you must provide a full type annotation, specifying both the `T` and `E` types.
    

Rust

```Rust
fn main() {
    // The compiler can infer `T` is `i32`, but it doesn't know what `E` is.
    // This line would cause a compile-time error: "type annotations needed"
    // let ok = Result::Ok(5);

    // The solution is to explicitly annotate the variable's type.
    // We specify `T` as `i32` and `E` as a string slice (`&str`).
    let ok: Result<i32, &str> = Ok(5); // The `Result::` prefix is optional (prelude).
    
    // We can see the variable's type in the output.
    println!("The `ok` variable is: {:?}", ok);
    // Output: The `ok` variable is: Ok(5)

}
```

### Part 2: The `Err` Variant and Type Ambiguity

This part demonstrates the `Err` variant, which is used for a failed outcome. The same type-inference problem from Part 1 occurs, but in reverse.

- **The `Err` Variant:** The `Err` variant is typically used to hold a descriptive error message or an error struct.
    
- **The Problem with `Err`:** When you create a `Result::Err` instance, the compiler can infer the type of `E` (the error type) from the associated data. However, it has no way to infer the type of `T` (the success type), which again leads to a compile-time error.
    
- **The Solution:** You must provide a full type annotation, specifying a concrete type for both `T` and `E`.
    

Rust

```Rust
fn main() {
    // The compiler can infer `E` is `&str`, but it doesn't know what `T` is.
    // This line would cause a compile-time error: "type annotations needed"
    // let disaster = Result::Err("Something went wrong");
    
    // The solution is to explicitly annotate the variable's type.
    // We specify `T` as an `i32` and `E` as `&str`.
    let disaster: Result<i32, &str> = Err("Something went wrong");
    
    // We can see the variable's type in the output.
    println!("The `disaster` variable is: {:?}", disaster);
    // Output: The `disaster` variable is: Err("Something went wrong")

}
```

### Part 3: Final Code & Shorthand Syntax

This final part brings all the concepts together into a complete, working program. It demonstrates a mix of `Ok` and `Err` variants, both requiring a full type annotation. It also uses the concise shorthand for `Ok` and `Err` because they are part of the Rust prelude.

- **The Prelude:** The `Result` enum and its variants (`Ok` and `Err`) are available in the prelude. The `Result::` prefix is optional when referring to variants.
    
- **The Code:** This example shows a complete program with a successful `Ok` result and a failed `Err` result, demonstrating the full power of the `Result` enum.
    

Rust

```Rust
fn main() {
    // Both variables are of the same type: `Result<i32, &str>`.
    // The compiler needs to know both T and E to understand the full type.
    
    // An `Ok` variant requires a value of type `i32`.
    let ok: Result<i32, &str> = Ok(5);
    
    // An `Err` variant requires a value of type `&str`.
    let disaster: Result<i32, &str> = Err("Something went wrong");

    println!("The `ok` variable is: {:?}", ok);
    // Output: The `ok` variable is: Ok(5)
    
    println!("The `disaster` variable is: {:?}", disaster);
    // Output: The `disaster` variable is: Err("Something went wrong")
}
```
