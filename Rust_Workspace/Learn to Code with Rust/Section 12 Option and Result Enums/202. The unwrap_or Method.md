### Part 1: The `Option` Setup & The "Success" Scenario

This progressive example introduces the **`unwrap_or()`** method on the `Option` enum. Unlike `unwrap()`, this method takes a fallback value, providing a safe alternative for extracting data. In this part, we see how the method behaves when the `Option` contains a value.

- **`.unwrap_or()` Method:** This method attempts to extract the associated data from a `Some` variant. It requires one argument, which is a **default or fallback value**.
    
- **Success Path:** If the `Option` variant is `Some`, the method will successfully extract the associated data and ignore the fallback value.
    
- **The Code:** This part sets up two `Option` variables and shows a call to `unwrap_or()` on the successful `Some` variant.
    

Rust

```Rust
fn main() {
    // A variable with a `Some` variant, containing an `i32`
    let present_value: Option<i32> = Some(13);
    
    // A variable with a `None` variant.
    let missing_value: Option<i32> = None;

    // Call `unwrap_or()` on a successful `Some` variant.
    // The method extracts the `13` and ignores the fallback value of `0`.
    let extracted_from_some = present_value.unwrap_or(0);
    
    println!("Extracted from `Some`: {}", extracted_from_some);
    // Output: Extracted from `Some`: 13

}
```

### Part 2: The "Failure" Scenario with `.unwrap_or()`

This part demonstrates the core purpose of the `unwrap_or()` method: to handle the `None` variant gracefully. Instead of causing a panic, it returns the provided fallback value.

- **Failure Path:** If the `Option` variant is `None`, the method cannot extract any data. It then safely returns the default fallback value that you passed as an argument.
    
- **No Panicking:** This is the key advantage over `.unwrap()` or `.expect()`. The program does not crash, providing a safe way to proceed with a default value.
    
- **The Code:** This example shows a call to `unwrap_or()` on the `None` variant, and the output reflects the fallback value.
    

Rust

```Rust
fn main() {
    let present_value: Option<i32> = Some(13);
    let missing_value: Option<i32> = None;
    
    // Call `unwrap_or()` on a `None` variant.
    // The method returns the fallback value (`100`) because there is no value to unwrap.
    let extracted_from_none = missing_value.unwrap_or(100);
    
    println!("Extracted from `None` (fallback): {}", extracted_from_none);
    // Output: Extracted from `None` (fallback): 100

}
```

### Part 3: Type Consistency and Mismatches

This part highlights a crucial rule: the fallback value's type must be consistent with the `Option` enum's generic type `T`. This is an important part of Rust's type safety.

- **Type Matching:** The type of the value held in the `Some` variant (i.e., the type `T`) must be the exact same type as the fallback value provided to `unwrap_or()`.
    
- **Compiler Error:** The compiler will produce an error if there is a type mismatch, preventing a bug where the function might return a `bool` when an `i32` is expected.
    
- **The Code:** This example shows a commented-out line that would cause a compile-time error due to a type mismatch.
