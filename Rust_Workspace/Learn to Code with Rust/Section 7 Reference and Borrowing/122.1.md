### Part 1: The Second Borrowing Rule: One Mutable Reference

Rust's second core borrowing rule is: you can have only **one mutable reference (`&mut T`)** to a particular piece of data in a particular scope.

While you have that single mutable reference, you cannot create any other references to that same value, regardless of whether they are mutable or immutable. This rule is enforced at compile time to prevent potential data races. For a mutable reference to exist, the original owner of the data must also be declared as mutable.

Example of an Error:

This code fails because ref2 (an immutable reference) is created while ref1 (a mutable reference) still exists.

```Rust
fn main() {
    let mut car = String::from("Blue");
    let ref1 = &mut car;
    let ref2 = &car; // ERROR: cannot borrow `car` as immutable
```

### Part 2: The Reason: Preventing Data Races

This rule exists to prevent data races. The problem arises from conflicting expectations:

- An **immutable reference** (`&T`) acts as a "reader." It expects the data it's pointing to not to change.
    
- A **mutable reference** (`&mut T`) acts as a "writer." It has permission to change the data.
    

Using the analogy from the transcript, if one friend borrows your "blue" car with a promise not to change it (immutable borrow), and another friend borrows it with permission to paint it "red" (mutable borrow), a conflict is inevitable. The first friend's expectation of a blue car will be violated.

By allowing only one mutable reference at a time (and no immutable ones alongside it), Rust guarantees that no "reader" can have the data change out from under it.

### Part 3: Advanced Topic: Non-Lexical Lifetimes (NLL)

The Rust compiler is smarter than just looking at where variables are declared. It analyzes when references are **last used**. A reference's **lifetime** effectively ends after its last use, even if its declared scope continues.

This means that if the lifetimes of two references do not overlap, the code is valid. This is why code that _looks_ like it should fail might actually compile.

Example of Valid Code:

This code works because ref1 is last used when .push_str() is called. After that line, its lifetime is over, so creating ref2 on the next line is safe because they don't coexist.

Rust

```Rust
fn main() {
    let mut car = String::from("Blue");
    let ref1 = &mut car;

    ref1.push_str(" and Silver"); // `ref1` is last used here. Its lifetime ends.

    // This is OK because `ref1` is no longer in use.
    let ref2 = &car;
    println!("The car is now: {}", ref2);
}
```

### Part 4: Summary of Rust's Two Borrowing Rules

The entire borrowing system can be summarized by two rules that create a "one or the other" scenario for any given scope:

You can have either:

1. **Any number of immutable references (`&T`)** to a value. (Multiple readers are okay).
    
    **OR**
    
2. **Exactly one mutable reference (`&mut T`)**. (One writer is okay).
    

You can **never** have a mutable reference at the same time as any other references (mutable or immutable). The compiler enforces this at compile time to guarantee memory safety.
