# References & Borrowing — detailed study guide

---

# What a reference is (and what borrowing means)

- A **reference** stores the **memory address** of an existing value (an address/pointer you can follow to get the value).
    
- **Borrowing** = creating a reference (use `&` to borrow).
    
- Purpose: let code **reuse data** without taking ownership and without duplicating heap data (cheap and fast).
    

---

# Two categories of references

## Immutable references (`&T`)

- Created with `&value`.
    
- **Read-only**: you can inspect/use the value but **cannot modify** it through the reference.
    
- **Any number** of immutable references to the same value are allowed at the same time.
    
- Immutable references are **Copy** (they are cheap addresses); you can freely copy them.
    

Example:

```rust
let s = String::from("hello");
let r1 = &s;
let r2 = &s;
println!("{}, {}", r1, r2); // allowed — both read
```

## Mutable references (`&mut T`)

- Created with `&mut value` and require the original binding to be `mut`.
    
- Allow **reading and modifying** the original value through the reference.
    
- **Only one mutable reference** to a value can exist at any given time — no other mutable or immutable references may coexist while that mutable reference is alive.
    
- Mutable references **do not implement Copy**. They follow ownership-like move rules (you can move the mutable reference, but you cannot silently copy it).
    

Example (error if you try to make two at once):

```rust
let mut s = String::from("hello");
let r1 = &mut s;
// let r2 = &mut s; // ERROR: cannot borrow `s` as mutable more than once at a time
r1.push_str(" world");
```

To create multiple mutable references sequentially, make sure the first one’s lifetime ends before creating the next:

```rust
let mut s = String::from("hello");
{
    let r1 = &mut s;
    r1.push_str(" world");
} // r1's lifetime ends here
let r2 = &mut s; // ok now
r2.push_str(" again");
```

---

# Why these rules exist (safety & race prevention)

- If you had a mutable reference while an immutable reference existed, the immutable borrower could observe inconsistent data while the mutable one mutates it — this can lead to subtle bugs and data races.
    
- The rules ensure **no data races** at compile time: either many readers (immutable refs) or one writer (mutable ref).
    

---

# Lifetimes (brief, in-scope)

- Every reference has a **lifetime**: the region of code where the reference is valid.
    
- The _referent_ (the original value) **must outlive** any references to it — i.e., references cannot outlive the data they point to.
    
- This prevents **dangling references** (pointers to deallocated memory). Rust enforces this at compile-time.
    

Dangling reference example (won’t compile):

```rust
fn dangle() -> &String {
    let s = String::from("hello");
    &s // ERROR: returns reference to local value that will be dropped
}
```

Correct approach: return the owned `String` instead of a reference.

---

# Borrowing rules in function parameters

- Passing a `String` by value moves ownership to the function (if `String` does not implement `Copy`).
    
- Passing `&String` or `&T` borrows: the function reads (or mutates with `&mut`) without taking ownership.
    
- Using references avoids the need to return values just to preserve them after a call.
    

Example:

```rust
fn read_len(s: &String) -> usize { s.len() } // borrows for read-only
fn append_world(s: &mut String) { s.push_str(" world"); } // borrows for mutation
```

---

# Composite types (arrays, tuples, Vec) and indexing

- Composite types **own** their elements.
    
- When you **index** into a collection:
    
    - If the element type **implements `Copy`** (like `i32`), the value is copied out and you can use it directly:
        
        ```rust
        let v = vec![1, 2, 3]; // i32 is Copy
        let x = v[0]; // copies 1
        ```
        
    - If the element type **does not implement `Copy`** (e.g., `String`), you **cannot move the element out** by simple indexing — doing so would break the collection’s integrity. Instead:
        
        - Borrow a reference: `let s_ref = &v[0];` (gives `&String`), or
            
        - Remove/move explicitly with a method that is designed to move out (e.g., `v.remove(index)`), or
            
        - Clone the value `v[0].clone()` to get a fresh owned copy.
            

Example showing the compile-time rule:

```rust
let v = vec![String::from("a"), String::from("b")];
// let s = v[0]; // ERROR: cannot move out of index of `Vec<String>`
let s_ref: &String = &v[0]; // OK: borrow
let s_owned = v.remove(0);  // OK: remove returns owned String (but shifts elements)
```

---

# Dangling references — Rust prevents them

- You cannot return a reference to a local value that goes out of scope — compiler error.
    
- The rule "referent must outlive the reference" is enforced by borrow checker and lifetimes.
    

Bad:

```rust
fn bad() -> &str {
    let s = String::from("hello");
    &s // ERROR: `s` will be dropped at end of function
}
```

Good:

```rust
fn good() -> String {
    String::from("hello") // return owned value instead
}
```

---

# Immutable references implement `Copy` — practical consequence

- Since `&T` is `Copy`, you can assign or pass immutable references around cheaply:
    

```rust
let s = String::from("hi");
let r1 = &s;
let r2 = r1; // r1 still usable; references are copied
println!("{}, {}", r1, r2);
```

- Mutable references are **not** `Copy`. Assigning a `&mut T` moves the reference (so you cannot silently duplicate a mutable borrow).

# Common borrow-checker errors and how to fix them

1. **Cannot borrow as mutable because it’s also borrowed as immutable**
    
    ```rust
    let mut s = String::from("hello");
    let r1 = &s;
    let r2 = &mut s; // ERROR
    ```
    
    **Fix:** Ensure immutable borrows are out of scope before the mutable borrow; or avoid immutable borrow if you need mutation.
    
2. **Cannot borrow as mutable more than once**
    
    ```rust
    let mut s = String::from("hello");
    let r1 = &mut s;
    let r2 = &mut s; // ERROR
    ```
    
    **Fix:** Use sequential mutable borrows in separate non-overlapping scopes.
    
3. **Returning reference to local variable**
    
    ```rust
    fn bad() -> &String {
        let s = String::from("x");
        &s // ERROR
    }
    ```
    
    **Fix:** Return `String` (owned) instead.
    
4. **Attempting to move out of a borrow**
    
    ```rust
    let v = vec![String::from("a")];
    let s = v[0]; // ERROR for non-Copy type
    ```
    
    **Fix:** `let s_ref = &v[0];` or `let s = v.remove(0);` or `let s = v[0].clone();`
    

---

# Quick rules checklist

- `&T` = immutable borrow; any number allowed; `Copy`.
    
- `&mut T` = mutable borrow; exactly one at a time while alive; **not** `Copy`.
    
- References cannot outlive their referent — borrow checker enforces lifetimes.
    
- Use references to avoid copying heap data (e.g., `String`) and to avoid unnecessary `clone()`.
    
- To modify through a borrow, you need `&mut` and exclusive access.

# Compact examples (copy-paste to test)

1. Multiple immutable borrows — allowed:
    

```rust
let s = String::from("Hello");
let r1 = &s;
let r2 = &s;
println!("{} and {}", r1, r2);
```

2. Mutable borrow after immutable borrow ends:
    

```rust
let mut s = String::from("Hello");
{
    let r = &s;
    println!("{}", r);
} // r's scope ends here
let rmut = &mut s; // OK now
rmut.push_str(" world");
println!("{}", rmut);
```

3. Preventing dangling reference (compile error shown conceptually):
    

```rust
fn bad() -> &String {
    let s = String::from("hi");
    &s // compile-time error: returns reference to local value
}
```

4. Indexing behavior:
    

```rust
let nums = vec![1, 2, 3];
let n = nums[0]; // OK: i32 is Copy

let words = vec![String::from("a"), String::from("b")];
// let w = words[0]; // ERROR: cannot move out of index of `Vec<String>`
let w_ref = &words[0]; // borrow instead
```

---

# Final practical guidance

- Prefer borrowing (`&T` / `&mut T`) over cloning for performance.
    
- Keep borrow scopes as small as possible so you can easily create mutable borrows when needed.
    
- Think in terms of **who owns** the data and **who needs access** (read vs write).
    
- Let the borrow checker guide you: its errors are the precise rules to ensure safety.
