### In-Depth Study Guide: Array Slices as Function Parameters

This guide explains the difference between using `&[T; N]` (a reference to a sized array) and `&[T]` (an array slice) as function parameters and clarifies why `&[T]` is almost always the better, more idiomatic choice.

---

### 1. The Choice: `&[T; N]` vs. `&[T]`

When writing a function that needs to operate on the elements of an array without taking ownership, you have two primary choices for the parameter's type:

- **`&[T; N]`**: A reference to an array of type `T` with a **specific, fixed size `N`**.
    
- **`&[T]`**: An array slice of type `T`. The **length is not part of the type**.
    

While they seem similar, one is significantly more flexible than the other.

---

### 2. The Problem with `&[T; N]` Parameters (References to Sized Arrays)

Defining a function parameter as `&[T; N]` is **too restrictive**. It forces the caller to provide a reference to an array of that _exact_ length. It cannot accept an array of a different length, nor can it accept a slice of an array.

#### Example: A Restrictive Function

Rust

```Rust
// This function is NOT idiomatic because it's too restrictive.
// It will ONLY accept a reference to an array of EXACTLY 6 i32s.
fn print_length(reference: &[i32; 6]) {
    println!("The length is: {}", reference.len());
}

fn main() {
    let values = [4, 8, 15, 16, 23, 42];
    let regular_reference = &values; // Type is &[i32; 6]
    let slice_of_three = &values[0..3]; // Type is &[i32]

    // This works because the types match exactly.
    print_length(regular_reference);

    // This line causes a COMPILE ERROR.
    // The function expects a reference to a 6-element array,
    // but we are giving it a 3-element slice.
    // print_length(slice_of_three); // ERROR: mismatched types
}
```

---

### 3. The Solution: Using `&[T]` for Flexibility (Array Slices)

The idiomatic and most flexible approach is to use **`&[T]`** for function parameters that need to borrow array data. A function that accepts an array slice can be called with a reference to a sized array (of any size) or a slice of an array.

#### Example: A Flexible Function

Rust

```Rust
// This function IS idiomatic. It accepts a slice of i32s of any length.
fn print_length(slice: &[i32]) {
    println!("The length of the slice is: {}", slice.len());
}

fn main() {
    let values = [4, 8, 15, 16, 23, 42];
    let regular_reference = &values; // Type is &[i32; 6]
    let slice_of_three = &values[0..3]; // Type is &[i32]

    // This works! Rust automatically converts `&[i32; 6]` to `&[i32]`.
    print_length(regular_reference);

    // This also works because we are passing a slice.
    print_length(slice_of_three);
}
```

---

### 4. The "Magic" Behind It: Deref Coercion

**Why can a function expecting `&[T]` accept a `&[T; N]`?**

This works because of a convenient, behind-the-scenes feature called **Deref Coercion**.

- **Definition:** Deref coercion is an automatic conversion that Rust performs on references.
    
- **How it applies here:** When you pass a reference to a sized array (`&[T; N]`) to a function that expects an array slice (`&[T]`), the compiler automatically coerces (converts) the array reference into a slice that covers the whole array.
    

Why doesn't it work in reverse?

Rust cannot automatically convert an array slice &[T] into a reference to a sized array &[T; N]. An array slice has a dynamic length that is only known at runtime. The compiler cannot guarantee at compile time that the slice you provide will have the exact length N that the function requires. Since Rust must make these guarantees at compile time, the conversion is disallowed.

---

### 5. The Golden Rule and Summary

> **Prefer `&[T]` over `&[T; N]` as function parameters.**

This makes your functions more general, reusable, and ergonomic, allowing them to be called with arrays of any length or slices of those arrays.

|Parameter Type|Accepts `&[T; N]`?|Accepts `&[T]`?|Recommended?|
|---|---|---|---|
|`&[T; N]`|Yes (only if `N` matches)|No|**No** (too restrictive)|
|`&[T]`|**Yes** (via deref coercion)|**Yes**|**Yes** (most flexible and idiomatic)|
