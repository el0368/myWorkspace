### Rust Enums Study Guide: Advanced Associated Data and Variant Heterogeneity

This study guide builds on the fundamentals of Rust enums, focusing on the advanced concept from the provided transcript: how different enum variants can store varying amounts and types of associated data. This allows for flexible, type-safe modeling of diverse scenarios, like different payment methods requiring unique credentials.

We'll progress through examples, starting from a basic enum with uniform data and evolving to heterogeneous variants. Each section includes explanations, key concepts, pitfalls, and complete, runnable code snippets. Examples continue the `PaymentMethodType` theme. All code is Rust 1.78+ compatible.

#### 1. Review: Uniform Associated Data
Recall that enums can associate data uniformly across variants for consistency.

**Key Concepts:**
- All variants can share the same data structure if needed.
- Use tuple variants for unnamed fields.
- Data types must match when instantiating.

**Progressive Example 1: Uniform Single Field**
Start with all variants having one `String`.

```rust
// src/main.rs

#[derive(Debug)]
enum PaymentMethodType {
    CreditCard(String),  // Account number
    DebitCard(String),
    PayPal(String),      // Account ID
}

fn main() {
    let credit = PaymentMethodType::CreditCard(String::from("5678"));
    let debit = PaymentMethodType::DebitCard(String::from("2532"));
    let paypal = PaymentMethodType::PayPal(String::from("paypal123"));
    
    println!("{:?}", credit);
    println!("{:?}", debit);
    println!("{:?}", paypal);
}
```

**Output:**
```
CreditCard("5678")
DebitCard("2532")
PayPal("paypal123")
```

**Explanation:**
- Each variant requires exactly one `String`.
- Progressive base: Simple instantiation and printing.
- Pitfall: Providing wrong type (e.g., `i32`) causes compile-time error.

#### 2. Introducing Heterogeneous Associated Data
One key advantage: Variants can have *different* numbers of fields and types, tailored to each case.

**Key Concepts:**
- Heterogeneity: Mix and match data per variant (e.g., one variant with 1 field, another with 2).
- Syntax remains tuple-like: `Variant(Type1, Type2, ...)`.
- Compiler enforces correct count and types per variant.
- Useful for real-world diversity (e.g., PayPal needs email + password, others just account).

**Progressive Example 2: Mixed Fields Across Variants**
Update to make PayPal require two `String`s (email, password), while others keep one.

```rust
// src/main.rs

#[derive(Debug)]
enum PaymentMethodType {
    CreditCard(String),   // Account number
    DebitCard(String),    // Account number
    PayPal(String, String),  // Email, password
}

fn main() {
    let credit = PaymentMethodType::CreditCard(String::from("5678"));
    let paypal = PaymentMethodType::PayPal(String::from("bob@gmail.com"), String::from("password"));
    
    println!("{:?}", credit);
    println!("{:?}", paypal);
}
```

**Output:**
```
CreditCard("5678")
PayPal("bob@gmail.com", "password")
```

**Explanation:**
- PayPal now has two fields; others one.
- Instantiation matches per variant: one arg for CreditCard, two for PayPal.
- `Debug` shows variant-specific data.
- Progressive: Builds by differentiating PayPal.
- Pitfall: Wrong arg count (e.g., one for PayPal) errors: "takes 2 arguments but 1 was supplied."

#### 3. Mutable Reassignment Across Variants
Enums support reassigning to different variants, but you must provide the new variant's required data.

**Key Concepts:**
- Use `mut` for reassignment.
- Each reassignment is like constructing a new instance.
- Type safety: Compiler checks data for the *new* variant.

**Progressive Example 3: Reassigning a Mutable Enum**
Make a mutable variable, start as CreditCard, reassign to PayPal.

```rust
// src/main.rs

#[derive(Debug)]
enum PaymentMethodType {
    CreditCard(String),
    DebitCard(String),
    PayPal(String, String),
}

fn main() {
    let mut my_payment = PaymentMethodType::CreditCard(String::from("5678"));
    println!("Initial: {:?}", my_payment);
    
    // Reassign to PayPal, providing its required data
    my_payment = PaymentMethodType::PayPal(String::from("bob@gmail.com"), String::from("password"));
    println!("Reassigned: {:?}", my_payment);
}
```

**Output:**
```
Initial: CreditCard("5678")
Reassigned: PayPal("bob@gmail.com", "password")
```

**Explanation:**
- Start with one-field variant, reassign to two-field.
- Must provide exact data for the target variant.
- Progressive: Adds mutability and reassignment.
- Pitfall: Forgetting args for reassignment fails compilation with type/arg mismatch details.

#### 4. Handling Heterogeneous Enums with Match
Use `match` to destructure and access variant-specific data safely.

**Key Concepts:**
- Pattern matching binds variables to fields (e.g., `PayPal(email, pass)`).
- Handle all variants exhaustively.
- Access data only if present for that variant.

**Progressive Example 4: Matching on Heterogeneous Variants**
Add a function to process based on variant data.

```rust
// src/main.rs

#[derive(Debug)]
enum PaymentMethodType {
    CreditCard(String),
    DebitCard(String),
    PayPal(String, String),
}

fn process_payment(method: &PaymentMethodType) {
    match method {
        PaymentMethodType::CreditCard(acct) => println!("Credit account: {}", acct),
        PaymentMethodType::DebitCard(acct) => println!("Debit account: {}", acct),
        PaymentMethodType::PayPal(email, pass) => println!("PayPal email: {}, pass: [hidden]", email),
    }
}

fn main() {
    let mut my_payment = PaymentMethodType::CreditCard(String::from("5678"));
    process_payment(&my_payment);
    
    my_payment = PaymentMethodType::PayPal(String::from("bob@gmail.com"), String::from("password"));
    process_payment(&my_payment);
}
```

**Output:**
```
Credit account: 5678
PayPal email: bob@gmail.com, pass: [hidden]
```

**Explanation:**
- `match` destructures fields per variant.
- Borrow (`&`) to avoid moving ownership.
- Progressive: Integrates with functions for logic.
- Pitfall: Incomplete `match` (missing arm) errors; wrong binding (e.g., one var for PayPal) fails.

#### 5. Advanced: Adding More Variety
Extend with more types (e.g., add a bool for verification) to show flexibility.

**Key Concepts:**
- Mix types freely (String, i32, bool, etc.).
- Data must implement required traits (e.g., Debug for printing).

**Progressive Example 5: Adding Mixed Types**
Add a bool to PayPal (e.g., verified), keep others as is.

```rust
// src/main.rs

#[derive(Debug)]
enum PaymentMethodType {
    CreditCard(String),
    DebitCard(String),
    PayPal(String, String, bool),  // Email, password, verified
}

fn process_payment(method: &PaymentMethodType) {
    match method {
        PaymentMethodType::CreditCard(acct) => println!("Credit: {}", acct),
        PaymentMethodType::DebitCard(acct) => println!("Debit: {}", acct),
        PaymentMethodType::PayPal(email, pass, verified) => {
            println!("PayPal: {} (verified: {})", email, verified);
        }
    }
}

fn main() {
    let paypal = PaymentMethodType::PayPal(
        String::from("bob@gmail.com"),
        String::from("password"),
        true,
    );
    process_payment(&paypal);
}
```

**Output:**
```
PayPal: bob@gmail.com (verified: true)
```

**Explanation:**
- PayPal now has String, String, bool.
- Instantiation and matching update accordingly.
- Progressive: Evolves to more complex types.
- Pitfall: Non-Debug types need manual impl or derive.
