# Rust HashMap Study Guide

## Core Concept: What is a HashMap?

A HashMap is a fundamental collection type in Rust that stores data as unordered key-value pairs. Unlike arrays or vectors that maintain sequential order, HashMaps prioritize establishing connections and associations between two pieces of related data.

### Key Characteristics

**Structure**: Each entry consists of exactly one key paired with exactly one value

- Keys must be unique and distinct within the HashMap
- Values can contain duplicates (multiple keys can map to the same value)
- Storage is unordered - there's no concept of "first" or "last" element

**Purpose**: HashMaps excel at creating mappings between related data

- Restaurant menu item → price
- Company name → stock price
- User ID → user profile
- Any A-to-B relationship where quick lookup is needed

**Length**: The count represents key-value pairs, not individual elements. You cannot have orphaned keys or values.

## HashMap Creation and Setup

### Basic Creation

```rust
use std::collections::HashMap;

let mut my_map = HashMap::new();
```

### Type Inference Challenge

When creating an empty HashMap without immediate data insertion, Rust cannot infer the types. This requires explicit type annotation:

```rust
let mut scores: HashMap<String, i32> = HashMap::new();
```

The generic parameters `<K, V>` represent:

- `K`: Key type (must be consistent across all keys)
- `V`: Value type (must be consistent across all values)

## Mutation Methods

### The `insert` Method

Adds or updates key-value pairs with replacement behavior:

```rust
map.insert(key, value);
```

**Critical Behavior**: If the key already exists, `insert` will **replace** the entire key-value pair with the new value. This is destructive - the old value is lost.

**Requirement**: The HashMap variable must be declared as `mut` for any modification operations.

### The `remove` Method

Deletes key-value pairs using the key as the identifier:

```rust
let removed_value = map.remove(&key);
```

**Return Type**: Returns `Option<V>` because removal might fail:

- `Some(value)`: Key existed and was successfully removed
- `None`: Key didn't exist in the HashMap

### The `entry` and `or_insert` Pattern

Provides conditional insertion that respects existing data:

```rust
map.entry(key).or_insert(default_value);
```

**Behavior**: Only inserts if the key is **not** already present. This prevents accidental overwrites and is safer than `insert` when you want to preserve existing data.

## Data Access Strategies

### Square Bracket Notation

Direct access syntax similar to array indexing:

```rust
let value = map[&key];
```

**Risk**: This approach will cause a **runtime panic** if the key doesn't exist. The program will crash rather than handle the missing key gracefully.

### The `get` Method (Recommended)

Safe access that returns an `Option` type:

```rust
let maybe_value = map.get(&key);
```

**Return Behavior**:

- `Some(&value)`: Key exists, returns a **reference** to the value
- `None`: Key doesn't exist, no associated data

**Why References**: The `Some` variant contains a reference (`&value`) rather than owned data. This prevents transferring ownership away from the HashMap, allowing multiple access operations without moving data.

## Working with Options

Since `get` and `remove` return `Option` types, you'll typically handle them with pattern matching:

```rust
match map.get(&key) {
    Some(value) => println!("Found: {}", value),
    None => println!("Key not found"),
}
```

This forced explicit handling prevents runtime errors and makes your code more robust.

## Key Design Principles

### Keys as Entry Points

Keys serve as unique identifiers and search criteria. All HashMap operations revolve around keys:

- Insertion uses keys to determine placement
- Removal requires keys to identify targets
- Access uses keys to locate values

### Mutability Requirements

Any operation that changes the HashMap's contents requires the variable to be declared with `mut`. This includes:

- Adding new pairs
- Updating existing pairs
- Removing pairs

### Safety-First Philosophy

Rust's HashMap design emphasizes preventing runtime crashes:

- `get` returns `Option` instead of panicking
- `remove` returns `Option` to indicate success/failure
- `entry().or_insert()` prevents accidental overwrites

## Common Use Cases

HashMaps are ideal when you need:

- Fast lookups by unique identifier
- Association between related pieces of data
- Counting occurrences (key = item, value = count)
- Caching computed results
- Configuration mappings
- Any scenario where order doesn't matter but relationships do

## Memory and Performance Considerations

- HashMap operations are generally O(1) average case
- Keys must implement Hash and Eq traits
- No guaranteed iteration order
- Efficient for large datasets where lookup speed matters more than order
