## Rust Ownership: Functions, Parameters, and Argument Passing

This study guide focuses on how Rust's ownership rules (specifically `Copy` vs. `Move` semantics) apply when values are passed as **arguments** to function **parameters**. This is a critical aspect of understanding how Rust manages memory safety and data flow.

### I. Parameters and Arguments: Review

- **Parameter:** A named placeholder for an expected input within a function's definition (`fn my_func(parameter_name: Type)`). It acts like a variable local to the function.
    
- **Argument:** The actual concrete value passed to a function's parameter when the function is invoked (`my_func(argument_value)`).
    

### II. Ownership Rules When Passing Arguments to Functions

The same ownership rules that apply to variable assignments (`let new_var = old_var;`) also apply when a value is passed as an argument to a function parameter. The behavior depends on whether the argument's type implements the `Copy` trait.

#### 1. Passing `Copy` Types to Functions

- **Behavior:** When an argument whose type implements the `Copy` trait is passed to a function parameter, Rust creates a **full copy** of the value for the parameter.
    
- **Ownership:** The original variable (in the calling function) **retains ownership** of its value. The function parameter receives a separate, independent copy.
    
- **Lifetime:**
    
    - The parameter's copy exists only within the function's scope. When the function returns, this copy is dropped (its stack memory reclaimed).
        
    - The original variable in the caller remains valid and usable after the function call.
        
- **Types:** This applies to `i32`, `f64`, `bool`, `char`, and any fixed-size composite types (arrays, tuples) where all their elements are also `Copy`.
    
- **Analogy:** You photocopy a document and give the copy to someone. You still have your original.
    

**Example: Passing an Integer (`i32`) to a Function**

Rust

```Rust
// Function that takes an integer
fn print_my_value(value: i32) { // `value` is the parameter, type i32
    println!("Inside function: Your value is {}", value);
} // `value` (the parameter) goes out of scope here. Its copy of `6` is dropped.

fn main() {
    let apples = 6; // `apples` owns `6` (on the stack)

    // Call `print_my_value` with `apples` as the argument.
    // Since `i32` is `Copy`, a copy of `6` is made and given to `value` parameter.
    print_my_value(apples);

    // `apples` is still valid and usable because its ownership was not moved.
    println!("Outside function: `apples` is still valid: {}", apples);
    // Output:
    // Inside function: Your value is 6
    // Outside function: `apples` is still valid: 6
}
```

#### 2. Passing Non-`Copy` Types to Functions (Ownership Moves)

- **Behavior:** When an argument whose type _does not_ implement the `Copy` trait (typically heap-allocated types) is passed to a function parameter, Rust performs a **move of ownership** to the function parameter.
    
- **Ownership:** The original variable (in the calling function) **transfers ownership** of its value to the function parameter.
    
- **Lifetime:**
    
    - The function parameter becomes the new owner of the value. It uses the value within the function's scope.
        
    - When the function returns, the parameter (as the owner) goes out of scope, and the value it owns (including any associated heap memory) is dropped.
        
    - **The original variable in the caller becomes invalid** after the function call. It can no longer be used.
        
- **Types:** This applies to `String`, `Vec<T>`, `Box<T>`, and any custom `struct` or `enum` that contains a non-`Copy` field.
    
- **Analogy:** You give your original document to someone. You no longer have it.
    

**Example: Passing a `String` to a Function**

Rust

```Rust
// Function that takes a String (ownership moves here)
fn print_my_string(value: String) { // `value` is the parameter, type String. It now owns the String.
    println!("Inside function: Your string is '{}'", value);
} // `value` (the parameter) goes out of scope here.
  // As the owner, `value` drops the String's heap memory. The String is deallocated.

fn main() {
    let oranges = String::from("oranges"); // `oranges` owns the String "oranges" (on heap)

    // Call `print_my_string` with `oranges` as the argument.
    // Since `String` is NOT `Copy`, ownership of "oranges" moves from `oranges` to `value`.
    print_my_string(oranges); // `oranges` is now invalid (moved).

    // Attempting to use `oranges` after the function call will cause a compile-time error:
    // println!("Outside function: `oranges` is still valid: {}", oranges);
    // ERROR: borrow of moved value: `oranges`

    println!("`oranges` variable is no longer valid after the function call.");
    // Output:
    // Inside function: Your string is 'oranges'
    // `oranges` variable is no longer valid after the function call.
}
```

Compiler Error Details:

When oranges is passed to print_my_string, the compiler error "borrow of moved value" clearly indicates that oranges lost its ownership. The compiler points to:

- Where the value was originally declared (`let oranges = ...`).
    
- Where the move occurred (`print_my_string(oranges);`).
    
- Where the invalid use happened (`println!("{}", oranges);`).
    

### III. Solutions for Reusing Data After Function Calls

If you _do_ need to use the original variable after passing a non-`Copy` type to a function, you have two primary options:

1. **Cloning (`.clone()`):**
    
    - Explicitly create a full, independent duplicate of the value before passing it.
        
    - The function receives the clone, and the original variable retains its ownership and validity.
        
    - This can be expensive for large heap data.
        
    - **Example:** `print_my_string(oranges.clone());`
        
2. **Borrowing (`&` References):**
    
    - Pass a reference to the value instead of moving ownership.
        
    - The function parameter accepts a reference (`&String` instead of `String`).
        
    - The original variable retains ownership and validity.
        
    - This is the most common and efficient way to "lend" data to a function without transferring ownership.
        
    - **Example:** `fn print_my_string_ref(value: &String) { ... }` and then `print_my_string_ref(&oranges);` (This will be covered more in the next lessons).
        

### IV. Key Takeaways

- **Ownership Applies to Functions:** The rules for `Copy` vs. `Move` apply identically when values are passed as arguments to function parameters.
    
- **`Copy` Types (e.g., `i32`):** Arguments are _copied_. Original variable remains valid.
    
- **Non-`Copy` Types (e.g., `String`):** Ownership is _moved_ to the parameter. Original variable becomes invalid after the function call.
    
- **Compiler's Role:** Rust's compiler rigorously enforces these rules at compile time, preventing memory errors like double-frees by ensuring only one owner is responsible for deallocating a given piece of heap memory.
    
- **Safety First:** While potentially annoying for new developers, this mechanism is fundamental to Rust's promise of memory safety without garbage collection.
