## Rust Ownership: References and the `Copy` Trait

This study guide clarifies how references themselves behave within Rust's ownership system, specifically highlighting that **references implement the `Copy` trait**. This means that when a reference is assigned to a new variable, the reference itself is copied, rather than its ownership being moved.

### I. Review: The `Copy` Trait and Stack Data

- **`Copy` Trait:** This trait indicates that a type can be duplicated via a simple, bitwise copy (a "copy" operation).
    
- **Stack Data and `Copy`:** Primitive types (like `i32`, `bool`, `char`, `f64`) and fixed-size aggregates of `Copy` types (like arrays of `i32` or tuples of `bool`s) are stored on the Stack and implement `Copy`.
    
- **Behavior on Assignment:** When a `Copy` type is assigned (`let new_var = old_var;`), a full, independent duplicate of the value is made. The original variable remains valid. This is cheap because stack data is fixed-size and readily duplicated.
    

### II. References Implement the `Copy` Trait

Do references implement the Copy trait?

Yes, all types of references in Rust (&T and &mut T) implement the Copy trait.

- **Why?** A reference, at its core, is just a **memory address** (a pointer). A memory address is a fixed-size, small piece of data (e.g., 8 bytes on a 64-bit system). Copying a memory address is very cheap and efficient, just like copying an integer.
    
- **Implication:** Because references implement `Copy`, when you assign one reference variable to another, a **copy of the reference itself** is made. Ownership of the reference is _not_ moved.
    

### III. `Copy` in Action with References

When you assign a reference variable to another variable (`let new_ref = old_ref;`), the following occurs:

1. A **new, independent copy of the reference (the memory address)** is created.
    
2. The new variable then holds this duplicate reference.
    
3. Both the original reference variable and the new reference variable now point to the **same underlying piece of data** in memory.
    
4. Crucially, the **original reference variable remains valid** and can continue to be used.
    
5. There are now **multiple "borrowers"** of the same underlying data, but that data still has its single owner.
    

**Example: Copying an `&str` Reference**

Recall that a string literal (`"Cookies and Cream"`) is embedded directly into the program's binary. The `&str` variable holds a reference to this read-only data.

Rust

```Rust
fn main() {
    // `ice_cream` is an `&str`. It's a reference to "Cookies and Cream" in the program binary.
    // The `ice_cream` variable itself (the reference value) is on the stack.
    let ice_cream: &str = "Cookies and Cream";

    // `ice_cream` (an &str) implements the Copy trait.
    // So, `dessert` gets a *copy* of the reference stored in `ice_cream`.
    let dessert = ice_cream;

    // After this line, `ice_cream` is still valid.
    // Memory (Conceptual):
    // Stack:
    //   ice_cream -> { ptr_to_binary_data, len }
    //   dessert   -> { ptr_to_binary_data, len } (a *duplicate* of the reference)
    // Program Binary (Read-Only Data Section): "Cookies and Cream" (at ptr_to_binary_data)

    println!("Ice Cream: {}", ice_cream); // `ice_cream` is valid, implicitly dereferenced by Display. Output: Cookies and Cream
    println!("Dessert: {}", dessert);     // `dessert` is valid, implicitly dereferenced by Display. Output: Cookies and Cream

    // Both variables point to the *same single underlying data*.
    // They are two separate pieces of paper with the same address written on them.
}
```

**Example: Copying an `&String` Reference**

The same logic applies to references to heap-allocated `String`s.

Rust

```Rust
fn main() {
    let owned_string = String::from("Rustacean"); // `owned_string` owns String "Rustacean" (on Heap)

    // `first_ref` is an `&String`. It's a reference to `owned_string`'s heap data.
    let first_ref: &String = &owned_string;

    // `first_ref` (an &String) implements the Copy trait.
    // So, `second_ref` gets a *copy* of the reference stored in `first_ref`.
    let second_ref = first_ref;

    // After this, `first_ref` is still valid. `second_ref` now also points to the same data.
    // Memory (Conceptual):
    // Stack:
    //   owned_string -> { Ptr_A, Len, Cap }
    //   first_ref    -> { Ptr_A } (reference to the above heap data)
    //   second_ref   -> { Ptr_A } (a *duplicate* of the reference value from first_ref)
    // Heap: "Rustacean" (at Ptr_A)

    println!("Original String: {}", owned_string);
    println!("First Ref: {}", first_ref);
    println!("Second Ref: {}", second_ref);

} // All references (`first_ref`, `second_ref`) go out of scope, their stack entries are popped.
  // Then, `owned_string` goes out of scope, and as the owner, it deallocates "Rustacean" from the heap.
```

### IV. Ownership Implications with Reference Copies

- **No Ownership Transfer of the Referent:** When a reference is copied, ownership of the _underlying data_ (the "referent" like "Cookies and Cream" or "Rustacean") is **never transferred**. The original owner of that data (e.g., the `&str` literal, or the `String` variable) retains ownership.
    
- **Multiple Borrowers:** Copying a reference simply means there are now multiple distinct references (multiple "borrowers") pointing to the same data. This is perfectly safe in Rust because references (by default) are immutable and the compiler ensures no conflicting access rules are violated.
    
- **The Reference Itself is Owned:** Each reference variable (e.g., `ice_cream`, `dessert`) _does_ own its own copy of the _reference value_ (the memory address). When the reference variable goes out of scope, its small, stack-allocated memory address is popped off the stack.
    

### V. Key Takeaways

- **References are `Copy`:** All types of references (`&T`, `&mut T`) implement the `Copy` trait.
    
- **Copying a Reference:** When you assign one reference variable to another, the reference itself (the memory address) is copied.
    
- **No Ownership Change of Data:** This does _not_ move ownership of the data being referenced. The original owner of the data remains the same.
    
- **Multiple Borrowers:** You can have multiple immutable references pointing to the same underlying data at the same time.
    
- **Efficiency:** Copying references is cheap because they are fixed-size memory addresses.
    
- **Clarity:** It's like having multiple pieces of paper, each with the exact same address written on them, all pointing to one specific house.
