## Rust Strings: Mutating `String` and Heap Dynamics

This study guide explains how to modify (mutate) a `String` in Rust, detailing the behind-the-scenes memory management on the heap, particularly when using the `push_str` method.

### I. Review: `&str` vs. `String` Mutability

- **String Literal (`&str`):**
    
    - Hard-coded, fixed, **immutable** text.
        
    - Stored directly in the program's binary executable (read-only data).
        
    - Cannot be changed or mutated at runtime.
        
    - Example: `"hello"`.
        
- **`String` (Owned, Growable):**
    
    - Dynamically sized, **mutable** text.
        
    - Stored on the **Heap**.
        
    - Can be changed (concatenated, shortened, characters replaced) at runtime.
        
    - Example: `String::from("hello")`.
        
    - The entire reason for `String`'s existence is to provide this mutability and dynamism.
        

### II. `String` Structure in Memory: Stack and Heap Components

When you create a `String` (e.g., `let name = String::from("Boris");`), data is stored in two places:

1. On the Stack (for the String variable itself):
    
    The name variable on the stack holds three fixed-size pieces of information, regardless of how long the string is:
    
    - **Pointer (Reference):** An address in memory that points to the actual text content stored on the heap. This is typically 8 bytes on a 64-bit system.
        
    - **Length:** The current number of **bytes** the string's text content actually occupies in the heap.
        
        - Important: Length in bytes is not always equal to the character count due to UTF-8 encoding (e.g., emojis or non-English characters can take more than 1 byte). For English letters, 1 character usually equals 1 byte.
            
        - Example: For "Boris", length would be 5 bytes.
            
    - **Capacity:** The total amount of **bytes** that have been _allocated_ for this string in its current heap location. This is often _greater than or equal to_ the length.
        
        - Example: For "Boris" (length 5), the capacity might be 10 or 16 bytes.
            
2. **On the Heap (for the actual text data):**
    
    - This is where the raw UTF-8 encoded character data ("Boris" in our example) is stored.
        
    - The memory allocator attempts to find a contiguous block of memory on the heap that is large enough to hold the string's current content, and possibly some extra for future growth (the capacity).
        

### III. Mutating `String` with `push_str()` (Concatenation)

The `push_str()` method is used to add content to the end of an existing `String`. This operation is also known as **concatenation** or **appending**.

- **Requirement:** The `String` variable must be declared as **mutable (`mut`)** to allow changes.
    
- **Method Signature:** `string_variable.push_str(string_literal_or_slice: &str)`
    
    - It takes a string slice (`&str`) as an argument.
        

**Example: `push_str()` in Action**

Rust

```Rust
fn main() {
    let mut name = String::from("Boris"); // `name` is a mutable String on the heap
                                         // Initial state:
                                         // Stack: name -> { ptr to heap, len: 5, cap: ~5-16 (e.g., 5 or 8 or 16) }
                                         // Heap:  "Boris" (at ptr location)

    println!("Original Name: '{}'", name); // Output: Original Name: 'Boris'

    // First Concatenation
    name.push_str(" Pask"); // Add a space and "Pask" (5 bytes)
    // Total new length: 5 + 5 = 10 bytes

    println!("After first push_str: '{}'", name); // Output: After first push_str: 'Boris Pask'

    // Second Concatenation
    name.push_str("evich"); // Add "evich" (5 bytes)
    // Total new length: 10 + 5 = 15 bytes

    println!("After second push_str: '{}'", name); // Output: After second push_str: 'Boris Paskevich'
}
```

### IV. Heap Dynamics During `push_str()`

When you call `push_str()`, one of two scenarios occurs on the heap, depending on the `String`'s current capacity:

1. **Scenario 1: Existing Capacity is Sufficient**
    
    - **Condition:** The `String`'s current `capacity` (allocated heap space) is large enough to accommodate the new characters being added.
        
    - **Action:** The new characters are simply written directly into the existing allocated space on the heap, immediately following the current content.
        
    - **Stack Update:** The `reference` (pointer) to the heap **remains the same** on the stack. The `capacity` on the stack **remains the same**. Only the `length` value on the stack is **updated** to reflect the increased number of occupied bytes.
        
    - **Efficiency:** This is very efficient as it avoids new memory allocations and data copying.
        
    
    _Diagram (Conceptual):_
    
    ```Rust
    Initial:
    Stack: name -> { Ptr_A, Len: 5, Cap: 16 }
    Heap:  [B][o][r][i][s][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ] (at Ptr_A)
    
    push_str(" Pask"): (New total len = 10. Old cap = 16. Sufficient!)
    Stack: name -> { Ptr_A, Len: 10, Cap: 16 }  // Capacity stays, Length updates
    Heap:  [B][o][r][i][s][ ][P][a][s][k][ ][ ][ ][ ][ ][ ] (at Ptr_A) // Data written in place
    ```
    
2. **Scenario 2: Existing Capacity is Insufficient (Reallocation)**
    
    - **Condition:** The `String`'s current `capacity` is _not_ large enough to fit the new characters.
        
    - **Action:**
        
        1. The memory allocator finds a **new, larger contiguous block of memory on the heap** (usually double the old capacity, or enough to fit the new size plus some extra).
            
        2. The `String`'s **entire current content is copied** from the old heap location to this new, larger heap location.
            
        3. The new characters are then written to the end of the copied content in the new location.
            
        4. The **old heap space is deallocated** (returned to the system).
            
    - **Stack Update:** The `reference` (pointer) on the stack is **updated** to point to the new heap location. The `length` is **updated** to the new total. The `capacity` is **updated** to the new, larger capacity of the newly allocated block.
        
    - **Efficiency:** This is a more expensive operation due to the new allocation and data copying, but it's necessary to maintain dynamism. Rust handles this automatically and efficiently.
        
    
    _Diagram (Conceptual):_
    
    ```Rust
    Initial:
    Stack: name -> { Ptr_A, Len: 10, Cap: 10 }
    Heap:  [B][o][r][i][s][ ][P][a][s][k] (at Ptr_A)
    
    push_str("evich"): (New total len = 15. Old cap = 10. INSUFFICIENT!)
    1. Find new larger space (e.g., capacity 20)
    2. Copy "Boris Pask" to new space
    3. Write "evich" to new space
    4. Deallocate old space (Ptr_A)
    
    Stack: name -> { Ptr_B, Len: 15, Cap: 20 }  // Pointer and Capacity update
    Heap:  [B][o][r][i][s][ ][P][a][s][k][e][v][i][c][h][ ][ ][ ][ ][ ] (at Ptr_B) // Old Ptr_A is now free
    ```
    

### V. Benefits of `String`'s Dynamic Nature

- **Mutability:** Allows modifying text data in place.
    
- **Flexibility:** Can grow or shrink to fit varying data sizes (e.g., user input, file reads).
    
- **Efficiency (Amortized):** While reallocation is expensive, it happens less frequently because capacity often grows exponentially. This makes appending operations efficient on average (amortized constant time).
    
- **Ownership Management:** Rust's ownership system ensures that all this complex heap allocation and deallocation is handled automatically and safely when the `String` variable goes out of scope, preventing memory leaks and other common bugs.
