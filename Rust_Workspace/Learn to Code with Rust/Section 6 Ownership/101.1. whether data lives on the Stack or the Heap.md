In Rust, understanding whether data lives on the Stack or the Heap is fundamental to grasping its ownership and borrowing system, which ensures memory safety.

Here's a breakdown:

### Data that Lives on the **Stack** in Rust:

The Stack is fast, ordered (LIFO), and automatically managed.1 Data placed here must have a **fixed, known size at compile time**.

1. **Scalar Primitive Types:**
    
    - **Integers:** `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64`, `i128`, `u128`.
        
    - **Floats:** `f32`, `f64`.2
        
    - **Booleans:** `bool`.
        
    - **Characters:** `char`.
        
    - **Sized Pointers/References:** `usize`, `isize`.3
        
    - **Raw Pointers:** `*const T`, `*mut T` (the pointer itself, not the data it points to).4
        
2. **Fixed-size Compound Types (if all their components are also on the Stack):**
    
    - **Arrays:** `[T; N]` (e.g., `[i32; 5]`, `[bool; 20]`).5 The entire array's content is stored contiguously on the stack because its size (`N * sizeof(T)`) is known at compile time.
        
    - **Tuples:** `(T1, T2, ... Tn)` (e.g., `(i32, bool, char)`). The entire tuple's content is stored contiguously on the stack because its size is the sum of its fixed-size elements.
        
    - **Structs and Enums:** If _all_ the fields/variants within a `struct` or `enum` are types that live on the stack (e.g., all primitives, arrays, other stack-allocated structs/enums), then the instance of that `struct` or `enum` will live on the stack.
        
3. **References/Pointers to other data:**
    
    - **References:** `&T`, `&mut T`. 6A reference is essentially a memory address. The address itself has a fixed, known size (e.g., 8 bytes on a 64-bit system), so the reference variable is stored on the stack. (The data it _points to_ can be on the stack, heap, or in the program's binary).
        
    - **Smart Pointers (the pointer part):** For smart pointers like `Box<T>`, `Rc<T>`, `Arc<T>`, `Vec<T>`, `String`, the pointer itself (which points to the data on the heap) along with metadata like length and capacity (for `Vec`/`String`), are stored on the stack. The actual data they manage lives on the heap.
        
4. **Function Call Stack Frames:**
    
    - When a function is called, a new "stack frame" (or "activation record") is pushed onto the stack.7 This frame holds:
        
        - The function's local variables (of stack-allocated types).
            
        - Function parameters.
            
        - The return address (where to go back to after the function finishes).

### Data that Lives on the **Heap** in Rust:

The Heap is a flexible, large pool of memory, but slower to manage. Data placed here typically has a **size that is dynamic or unknown at compile time**.

1. **Growable / Dynamically Sized Collections:**
    
    - **`String`:** Rust's owned, growable string type.8 The actual text data is stored on the heap because its length can change at runtime (e.g., from user input, file reads, or concatenation).
        
    - **`Vec<T>`:** Rust's growable vector (dynamic array).9 The elements of the vector are stored on the heap because the vector can grow or shrink in size at runtime.10
        
2. **Data Explicitly Boxed to the Heap:**
    
    - **`Box<T>`:** This is a smart pointer that _explicitly_ allocates its owned data `T` on the heap.11 You use `Box` when you have recursive data structures (like tree nodes) where Rust needs a fixed-size pointer on the stack to refer to heap-allocated data, or when you have large amounts of data you don't want to copy on the stack.
        
3. **Data Managed by other Smart Pointers for Shared Ownership/Mutation (Heap components):**
    
    - **`Rc<T>` (Reference Counted):** Used for shared ownership within a single thread. The `T` data is on the heap, and `Rc` manages a reference count alongside it.
        
    - **`Arc<T>` (Atomic Reference Counted):** Similar to `Rc`, but thread-safe for shared ownership across multiple threads.12 The `T` data is on the heap.
        
    - **`RefCell<T>`:** Provides "interior mutability" for data that would otherwise be immutable.13 While `RefCell` itself might be on the stack, it typically wraps data that you want to mutably access through shared (immutable) references, often used in conjunction with `Rc` where the actual data `T` would be on the heap.
        

---

**Key takeaway:** Rust defaults to placing data on the **Stack** whenever possible, due to its speed and automatic management.14 The **Heap** is used when dynamism (unknown or changing size) or explicit shared ownership (beyond single-threaded `Rc`) is required. Rust's Ownership system then provides the rules to safely manage this heap memory.15
