## Rust Ownership: Mutability of Function Parameters

This study guide explains that function parameters, like variables, are immutable by default in Rust. It delves into how declaring a parameter as mutable (`mut`) is crucial for modifying the value it receives, especially when ownership is moved for non-`Copy` types.

### I. Function Parameters are Immutable by Default

Are function parameters mutable by default?

Yes, just like variables declared with let, function parameters are immutable by default. This means that within the body of a function, you cannot modify the value that a parameter holds unless that parameter is explicitly marked as mutable.

Why is this important with ownership?

When a non-Copy type (like String) is passed as an argument to a function, ownership of that value is moved to the function parameter. This means the parameter becomes the new owner. If you intend to modify the value within that function, the new owner (the parameter) must have explicit permission to mutate it.

**Example: Immutable Parameter (Leads to Error)**

Rust

```Rust
// This function attempts to modify its parameter, which is immutable by default.
fn add_fries_immutable(meal: String) { // `meal` is an immutable parameter (default)
    // ERROR: `meal` is not mutable
    // meal.push_str(" and fries");
    // This line would cause a compile-time error:
    // `meal` is a `String`, which is immutable by default, but `push_str` requires a mutable `self`.
    println!("Prepared: {}", meal);
}

fn main() {
    let burger = String::from("Burger"); // `burger` is immutable, then its ownership moves.

    // This call is valid (ownership moves)
    add_fries_immutable(burger);

    // After this, `burger` is moved/invalidated (as String is not Copy).
    // println!("{}", burger); // ERROR: borrow of moved value
}
```

### II. Making a Parameter Mutable (`mut`)

How do you make a function parameter mutable?

To allow modification of a parameter's value within the function body, you must explicitly add the mut keyword directly before the parameter name in the function signature.

- **Syntax:** `fn my_function(mut parameter_name: Type)`
    

**Example: Mutable Parameter (Enabling Modification)**

Rust

```Rust
// This function takes a mutable String parameter, allowing modification.
fn add_fries_mutable(mut meal: String) { // `meal` is now a mutable parameter
    meal.push_str(" and fries"); // This modification is now ALLOWED!
    println!("Prepared: {}", meal);
}

fn main() {
    let burger = String::from("Burger"); // `burger` can be immutable here (see explanation below)

    // Ownership of "Burger" moves from `burger` to `meal`.
    // `meal` receives "Burger" and has permission to modify it.
    add_fries_mutable(burger);

    // `burger` is moved/invalidated.
    // println!("{}", burger); // ERROR: borrow of moved value
}
```

**Output:**

```
Prepared: Burger and fries
```

### III. Interplay of Mutability and Ownership Transfer

This is a key concept that often confuses new Rust developers:

- **Source Variable's Mutability is Irrelevant to Parameter's Mutability (after move):**
    
    - When a non-`Copy` value (like `String`) is passed to a function, ownership is _moved_.
        
    - The parameter (`meal` in our example) then becomes the _new owner_.
        
    - The `meal` parameter's mutability (i.e., whether it's `mut meal: String` or `meal: String`) is **independent** of whether the _original_ variable (`burger`) was `mut` or not.
        
    - The `meal` parameter needs to be `mut` **because it is the new owner** and is performing a mutation, not because the original `burger` was `mut`.
        
    
    Rust
    
    ```
    fn add_to_string(mut s: String) { // `s` needs to be `mut` because `push_str` changes `s` itself.
        s.push_str(" World");
        println!("{}", s);
    }
    
    fn main() {
        let hello_str = String::from("Hello"); // `hello_str` is immutable.
                                                // Ownership moves to `s` in `add_to_string`.
        add_to_string(hello_str);
        // `hello_str` is now invalid.
    }
    ```
    
- Rust Compiler's Helpfulness:
    
    The compiler will issue a warning if you declare a variable as mut but never actually perform a mutation on it within its active scope.
    
    Rust
    
    ```
    fn main() {
        // Warning: `burger` does not need to be mutable
        let mut burger = String::from("Burger"); // `burger` is declared mutable
        // No mutation (like `burger.push_str(...)`) is called on `burger` itself.
        add_fries_mutable(burger); // Ownership is just moved.
    }
    ```
    
    In this case, the `mut` on `burger` is unnecessary because `burger`'s only action is to transfer ownership. Rust's compiler correctly identifies this and suggests removing `mut` for cleaner code. This helps enforce minimal mutability, which is a good practice for safety and clarity.
    

### IV. Key Takeaways

- **Parameters are `immutable` by default:** Just like `let` bindings.
    
- **Declare `mut` for mutation:** To modify a parameter's value within a function, mark it `mut` in the function signature (e.g., `fn func(mut param: Type)`).
    
- **Ownership Transfer Matters:** When a non-`Copy` type is passed, ownership moves to the parameter. The parameter's mutability determines if the _new owner_ can modify the value.
    
- **Source `mut` is Separate:** The mutability of the original variable is independent of the parameter's mutability after a move. The compiler helps you by warning about unnecessary `mut` declarations.
    
- **Safety via Compiler:** Rust ensures that you either have the correct `mut` permission on the current owner or it prevents the operation at compile time, preventing undefined behavior.
