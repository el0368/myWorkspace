A `struct` definition acts as a **blueprint** or a template for a custom data type. **Struct instantiation** is the process of creating a concrete, realized value from that blueprint. The resulting value is called a **struct instance**.

To create a named-field struct instance, you use a syntax that mirrors the struct's definition, but you provide actual values for each field instead of types.

### 1. The General Syntax

The general syntax for creating a struct instance involves binding it to a variable using `let`, naming the struct, and providing the fields and their values within curly braces.

Rust

```Rust
let instance_name = StructName {
    field1: value1,
    field2: value2,
    // ... all defined fields ...
};
```

The Rust compiler is a strict guardian during this process, enforcing several key rules.

### 2. Key Rules for Instantiation

Let's use a `User` struct as our blueprint to demonstrate the rules.

Rust

```Rust
// The struct blueprint defines the fields and their types.
struct User {
    name: String,
    email: String,
    is_active: bool,
    sign_in_count: u64,
}
```

#### Rule 1: All Fields Must Be Provided

You must provide a value for **every single field** defined in the `struct`. Omitting even one field will cause a compilation error.

Rust

```Rust
fn main() {
    // Correct Instantiation: All four fields are provided.
    let user1 = User {
        name: String::from("Alice"),
        email: String::from("alice@example.com"),
        is_active: true,
        sign_in_count: 1,
    };

    // Incorrect Instantiation (missing a field):
    /*
    let user2 = User {
        name: String::from("Bob"),
        is_active: true,
        sign_in_count: 5,
        // ERROR: missing structure fields: `email`
    };
    */
}
```

#### Rule 2: Field Types Must Match

The value you provide for each field must have a data type that **exactly matches** the type specified in the `struct` definition.

Rust

```Rust
fn main() {
    // Correct Instantiation: All values match their required types.
    let user1 = User {
        name: String::from("Alice"), // `String`
        email: String::from("alice@example.com"), // `String`
        is_active: true, // `bool`
        sign_in_count: 1, // `u64`
    };

    // Incorrect Instantiation (mismatched type):
    /*
    let user3 = User {
        name: String::from("Charlie"),
        email: String::from("charlie@example.com"),
        is_active: "yes", // ERROR: mismatched types; expected `bool`, found `&str`
        sign_in_count: 10,
    };
    */
}
```

#### Rule 3: Field Order Is Irrelevant

For named-field structs, the order in which you list the fields during instantiation does **not matter**. Rust uses the field names to match the values to the correct place in the struct.

Rust

```Rust
fn main() {
    // This is a correctly ordered instantiation.
    let user1 = User {
        name: String::from("Alice"),
        email: String::from("alice@example.com"),
        is_active: true,
        sign_in_count: 1,
    };

    // This is an equally valid instantiation, even though the fields are in a different order.
    let user4 = User {
        is_active: false,
        sign_in_count: 5,
        name: String::from("Bob"),
        email: String::from("bob@example.com"),
    };
}
```

### 3. Instantiation and Ownership

When you create a struct instance and bind it to a variable with `let`, that variable becomes the **owner** of the entire struct value. This means it is responsible for the struct's memory management, including the automatic deallocation of any heap-allocated data (like the `String` fields in our `User` struct) when the variable goes out of scope.
