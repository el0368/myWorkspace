### 9. Ownership Rules for Structs

**Explanation in the Scope of the Transcript:**

The transcript emphasizes that **structs in Rust adhere to ownership rules**, a fundamental aspect of Rust’s memory safety model. Specifically, structs do not implement the `Copy` trait by default, meaning that when a struct is assigned to another variable or passed to a function, ownership of the struct and its fields is transferred (moved) to the new variable or function parameter. This move invalidates the original variable, preventing further use unless ownership is explicitly returned or a clone is made. For structs containing fields with types that implement `Copy` (e.g., `u32`), those fields are copied during operations, but for non-`Copy` types (e.g., `String`), ownership moves, potentially causing the original struct to become unusable if not handled carefully. This ensures Rust’s strict memory management, preventing issues like dangling references or double freeing.

**Rust Code Example:**

Below is a minimal code example demonstrating ownership rules for structs, aligned with the transcript’s description.
```rust
struct Book {
    title: String, // Non-Copy type
    pages: u32,    // Copy type
}

fn main() {
    let book1 = Book {
        title: String::from("Rust Guide"),
        pages: 300,
    };

    // Ownership moves to book2
    let book2 = book1;
    println!("Book2: {} with {} pages", book2.title, book2.pages);

    // Uncommenting the next line causes a compile error
    // println!("Book1: {}", book1.title); // Error: value moved
}
```

**Code Explanation:**

1. **Struct Declaration**:
   - The `Book` struct has two fields: `title: String` (non-`Copy`, heap-allocated) and `pages: u32` (`Copy`, stack-allocated), setting up a scenario to demonstrate ownership rules.

2. **Ownership Movement**:
   - Assigning `book1` to `book2` moves ownership of the entire struct, including its fields, to `book2`, as structs do not implement `Copy` by default, per the transcript.
   - The `title` field (`String`, non-`Copy`) moves its ownership, making `book1` invalid. The `pages` field (`u32`, `Copy`) is copied, but the struct’s overall ownership still moves.

3. **Consequence of Move**:
   - Attempting to access `book1.title` after the move results in a compile error, illustrating the transcript’s point that ownership moves to the new variable, invalidating the original.

4. **Minimal Usage**:
   - The `println!` macro shows `book2`’s fields to confirm the move, keeping the example minimal while highlighting ownership rules.

**Key Takeaways**:
- Structs do not implement `Copy` by default, so assigning or passing them moves ownership, invalidating the original variable.
- Fields with `Copy` types (e.g., `u32`) are copied, but non-`Copy` fields (e.g., `String`) move ownership, affecting the entire struct.
