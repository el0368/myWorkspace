### Part 2: Defining Non-Chainable Methods (The Problem)

This study guide explains the issue that the Builder Pattern is designed to solve: the inconvenience of calling multiple, non-chainable methods on a single variable.

#### 1. The Problem with Non-Chainable Methods

In Rust, a method can only be chained with another method if it returns a value that the next method can be called upon.

- **Default Behavior:** Methods that do not specify a return type implicitly return the **unit type `()`** (an empty tuple).
    
- **Consequence:** If a method returns `()`, there is no value for the next dot operator (`.`) to act on. This breaks the chain, forcing you to start a new line and re-reference the original variable for each subsequent method call. This leads to repetitive and verbose code.
    

#### 2. Our Non-Chainable Methods

We will define three methods (`upgrade_cpu`, `upgrade_memory`, and `upgrade_hard_drive_capacity`) whose purpose is to mutate a field. In this "before" state, they return nothing.

- **Parameter Type:** They all take a **mutable reference (`&mut self`)** to the `Computer` instance. This is the correct way to modify a struct in-place without moving ownership.
    
- **Return Type:** They implicitly return `()` because they do not have a `-> ReturnType` annotation.
    
- **The "Problem":** Because their return type is `()`, they are not chainable.
    

#### Code Example (The Problem)

The following code illustrates the repetitive calls required when methods are not designed for chaining. This is the code that the Builder Pattern will refactor and improve.

Rust

```Rust
#[derive(Debug)]
struct Computer {
    cpu: String,
    memory: u32,
    hard_drive_capacity: u32,
}

impl Computer {
    fn new(cpu: String, memory: u32, hard_drive_capacity: u32) -> Self {
        Self { cpu, memory, hard_drive_capacity }
    }
    
    // These methods return nothing (implicitly `()`), so they are not chainable.
    fn upgrade_cpu(&mut self, new_cpu: String) {
        self.cpu = new_cpu;
        // returns `()` implicitly
    }
    
    fn upgrade_memory(&mut self, new_memory: u32) {
        self.memory = new_memory;
        // returns `()` implicitly
    }
    
    fn upgrade_hard_drive_capacity(&mut self, new_capacity: u32) {
        self.hard_drive_capacity = new_capacity;
        // returns `()` implicitly
    }
}

fn main() {
    let mut computer = Computer::new(String::from("M3 Max"), 64, 2);

    // This is the repetitive, non-chainable code we want to improve.
    computer.upgrade_cpu(String::from("M4 Max"));
    computer.upgrade_memory(128);
    computer.upgrade_hard_drive_capacity(4);

    println!("Current computer stats: {:#?}", computer);
    // Output:
    // Computer {
    //     cpu: "M4 Max",
    //     memory: 128,
    //     hard_drive_capacity: 4,
    // }
}
```

This code works, but the syntax is less elegant than what the Builder Pattern allows. The next part will demonstrate how to refactor these methods to enable a clean, chained syntax.
