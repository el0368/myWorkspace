## Rust Structs: Accessing Fields and Ownership Implications

This study guide explains how to read values from `struct` fields and delves into the critical ownership rules that apply when accessing fields, especially those holding non-`Copy` types.

### 1. Review: Struct Instances

- A `struct` definition is a **blueprint** for a custom data type.
    
- A **struct instance** is a concrete value created from that blueprint, holding actual data for its fields. (e.g., `let mocha = Coffee { ... };`)
    

### 2. Accessing Struct Field Values

To read or access the value of a specific field within a struct instance, you use **dot notation**.

- **Syntax:** `struct_variable.field_name`
    
- **Purpose:** This syntax directly retrieves the value associated with that named field.
    

**Example: Accessing `Coffee` Struct Fields**

Assuming the `Coffee` struct defined in the previous lesson:

Rust

```Rust
#[derive(Debug)] // Required for easy printing of the whole struct
struct Coffee {
    name: String,
    price: f64,
    is_hot: bool,
}

fn main() {
    let mocha = Coffee {
        name: String::from("Mocha"),
        price: 4.99,
        is_hot: true,
    };

    // Accessing individual fields and printing them
    println!("Coffee Name: {}", mocha.name);      // Output: Coffee Name: Mocha
    println!("Coffee Price: {}", mocha.price);    // Output: Coffee Price: 4.99
    println!("Coffee is hot: {}", mocha.is_hot);  // Output: Coffee is hot: true

    // Accessing all fields to form a sentence
    println!("\nMy {} this morning cost {}. It is {} that it was hot.",
             mocha.name,      // Accesses the 'name' field
             mocha.price,     // Accesses the 'price' field
             mocha.is_hot     // Accesses the 'is_hot' field
    );
    // Output: My Mocha this morning cost 4.99. It is true that it was hot.
}
```

### 3. Ownership Hierarchy in Structs

Understanding ownership within structs is crucial:

- **Struct Owns Its Fields:** A `struct` instance (the variable holding the entire struct) is the **owner of its fields**.
    
- **Fields Own Their Values:** Each individual field within the struct (e.g., `name`, `price`, `is_hot`) is, in turn, the **owner of its corresponding value**.
    
    - Think of a field name as another "name" in your program that corresponds to a value, similar to a variable or a function parameter.
        
- **Responsibility:** As owners, fields are responsible for cleaning up the memory associated with their values when they go out of scope (which happens when the encompassing struct instance itself goes out of scope).
    
- **Cleanup Cascade (Waterfall of Cleanups):** When a struct instance goes out of scope (e.g., `mocha` at the end of `main`), its `drop` function is called. This triggers a cascade:
    
    1. The struct (`mocha`) cleans up itself (its stack part).
        
    2. The struct then proceeds to clean up (drop) its individual fields.
        
    3. Each field, as it's dropped, is responsible for dropping its associated value (e.g., freeing a `String`'s heap memory or popping an `i32` from the stack).
        

### 4. Ownership Semantics (Copy vs. Move) When Accessing Fields

This is a critical area where Rust's ownership rules become very strict and powerful, preventing common memory bugs. The behavior depends on whether the field's type implements the `Copy` trait.

#### a. Accessing `Copy` Fields (e.g., `f64`, `bool`, `i32`)

- **Behavior:** When you access a field whose type implements the `Copy` trait (like `price: f64` or `is_hot: bool`), Rust performs an **automatic full copy** of that field's value.
    
- **Result:** The new variable (or parameter) gets a duplicate of the value. The field within the struct **retains its value**, and the struct instance **remains valid**.
    
- **Reason:** Copying fixed-size, stack-allocated data is cheap and efficient.
    

**Example: Copying a `f64` Field**

Rust

```Rust
#[derive(Debug)]
struct Coffee {
    name: String,
    price: f64,
    is_hot: bool,
}

fn main() {
    let mocha = Coffee {
        name: String::from("Mocha"),
        price: 4.99,
        is_hot: true,
    };

    let favorite_price = mocha.price; // `f64` implements Copy. `favorite_price` gets a *copy* of 4.99.
                                     // `mocha.price` remains valid.

    println!("Favorite Price: {}", favorite_price); // Output: Favorite Price: 4.99
    println!("Original Mocha price still here: {}", mocha.price); // Output: Original Mocha price still here: 4.99
    println!("Original Mocha struct still here: {:?}", mocha); // Whole struct still valid
}
```

#### b. Accessing Non-`Copy` Fields (e.g., `String`, `Vec<T>`, `Box<T>`)

- **Behavior:** When you access a field whose type **does NOT implement the `Copy` trait** (like `name: String`), Rust performs a **move of ownership** for that specific field's value.
    
- **Result:** The value (e.g., the `String` "Mocha") is transferred out of the struct's field to the new variable (or parameter). The field within the struct **becomes invalid** (it no longer "owns" that value). The struct instance, while still existing, is now in a partially "moved-out" state.
    
- **Reason:** Rust enforces a "one owner at a time" rule. If it copied the `String`, you'd have two owners of the same Heap data, leading to a double-free error. By moving, it ensures only one owner is responsible for deallocation.
    

**Example: Moving a `String` Field**

Rust

```Rust
#[derive(Debug)] // This derive will actually fail later due to moved field, proving the point.
struct Coffee {
    name: String,
    price: f64,
    is_hot: bool,
}

fn main() {
    let mocha = Coffee {
        name: String::from("Mocha"), // `name` field owns "Mocha" String (on Heap)
        price: 4.99,
        is_hot: true,
    };

    // This is a move operation!
    let favorite_coffee_name = mocha.name; // `String` does NOT implement Copy.
                                            // Ownership of the "Mocha" String moves from `mocha.name`
                                            // to `favorite_coffee_name`.
                                            // `mocha.name` is now INVALIDATED.

    println!("My Favorite Coffee Name: {}", favorite_coffee_name); // Output: My Favorite Coffee Name: Mocha

    // !!! CRITICAL: Attempting to use `mocha.name` or the whole `mocha` struct will now cause a compile-time error.
    // println!("Original Mocha name: {}", mocha.name);
    // ERROR: borrow of moved value: `mocha.name` (because it was moved to `favorite_coffee_name`)

    // This also fails, because a part of `mocha` (its `name` field) has been moved out.
    // Rust says you can't use `mocha` in its entirety if parts of it are missing/moved.
    // println!("Original Mocha struct: {:?}", mocha);
    // ERROR: use of moved value: `mocha.name`
    // (This error message can be complex, often referring to the whole struct being partially moved).
}
```

**Consequences of Moving a Field:**

- You cannot access the specific field that was moved out.
    
- You cannot use the entire struct instance in contexts that would require access to the moved-out field (e.g., printing the whole struct with `Debug` or `Display`, or moving the entire struct).
    
- The original struct becomes "partially moved" or "partially invalid."
    

### 5. Solutions to Avoid Moves When Accessing Fields

If you need to use a non-`Copy` field _and_ keep the struct intact, you must prevent the move:

1. **Borrowing (References):** The most common and idiomatic solution. Instead of taking ownership, you create a reference to the field.
    
    - **Immutable Borrow:** `let name_ref = &mocha.name;`
        
        - `name_ref` is `&String`. You can read the `name` field via `name_ref`, and `mocha.name` remains valid.
            
        - Rust
            
            ```Rust
              let mocha = Coffee { /* ... */ name: String::from("Mocha") };
              let name_ref = &mocha.name; // `name_ref` borrows `mocha.name`.
              println!("Name by ref: {}", name_ref);
              println!("Original struct still whole: {:?}", mocha); // Works!
            ```
            
    - **Mutable Borrow:** `let name_mut_ref = &mut mocha.name;`
        
        - `name_mut_ref` is `&mut String`. You can modify the `name` field via `name_mut_ref`, and `mocha` remains the owner. (Requires `mocha` to be `mut`).
            
        - Rust
            
            ```Rust
              let mut mocha = Coffee { /* ... */ name: String::from("Mocha") };
              let name_mut_ref = &mut mocha.name;
              name_mut_ref.push_str(" latte");
              println!("Modified name by mut ref: {}", name_mut_ref);
              println!("Original struct now changed: {:?}", mocha); // Works!
            ```
            
2. **Cloning (`.clone()`):** Explicitly create a full, independent duplicate of the field's value.
    
    - **Cost:** Involves duplicating the actual heap data.
        
    - **Use Case:** When you need a completely separate, owned copy of the field's data that can be modified independently without affecting the original struct.
        
    - Rust
        
        ```Rust
          let mocha = Coffee { /* ... */ name: String::from("Mocha") };
          let cloned_name = mocha.name.clone(); // Explicitly clones the String.
          println!("Cloned Name: {}", cloned_name);
          println!("Original struct still whole: {:?}", mocha); // Works!
        ```
        

### 6. Key Takeaways

- **Struct Owns Fields, Fields Own Values:** A hierarchical ownership.
    
- **Ownership Semantics Apply to Fields:** When you access a field and assign it to a new variable or pass it to a function:
    
    - **`Copy` fields** (e.g., `i32`, `f64`, `bool`): The value is **copied**. The field remains valid.
        
    - **Non-`Copy` fields** (e.g., `String`, `Vec<T>`): Ownership of that specific field's value is **moved**. The field within the struct becomes invalid, and the entire struct instance is considered partially moved/invalidated.
        
- **Compiler Catches Errors:** Rust's compiler rigorously enforces these rules, preventing bugs like using a partially moved struct.
    
- **Solutions:** Use **references (`&`, `&mut`)** to borrow a field without moving ownership, or **`clone()`** to explicitly create an independent duplicate when a move is not desired.
