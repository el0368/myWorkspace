Here’s a detailed explanation of **purpose, reason, and rationale** for invoking trait-mandated methods from other methods in Rust, based on your progressive examples:

---

## 1) **Purpose**

The main purpose of calling trait-mandated methods from other methods is **code reuse and abstraction**:

1. **Reuse common behavior**:  
    If a trait provides a default implementation for a method (like `get_description`), you can call it from multiple methods without rewriting the logic in each place.
    
2. **Write generic, type-agnostic methods**:  
    By calling methods from a trait, your code doesn’t need to know the exact type of the instance—it only needs to know that it implements the trait. For example, a `summarize` method can call `get_description` on any type that implements `Accommodation`.
    
3. **Keep inherent methods simple**:  
    A method like `summarize` can focus on combining and formatting data, while the trait method handles the actual logic (e.g., returning a description). This separation improves readability and maintainability.
    

---

## 2) **Reason / Why this is needed**

1. **Trait guarantees behavior**  
    Traits define a contract: “any type that implements me will have these methods.”  
    By calling trait methods, you rely on that contract without caring about the type’s internal structure.
    
    Example:
    
    ```rust
    fn summarize(&self) -> String {
        format!("{}: {}", self.name, self.get_description())
    }
    ```
    
    Here, `self.get_description()` is guaranteed to exist because `Hotel` implements `Accommodation`.
    
2. **Avoid code duplication**  
    Suppose multiple methods need a textual description. Instead of copying the logic of `get_description` everywhere, you invoke it from `summarize` or other helper methods.
    
3. **Maintain consistency across types**  
    If you have multiple types implementing `Accommodation` (like `Hotel` and `Airbnb`), calling the trait method ensures all types follow the same expected behavior, either the default or a custom implementation.
    
4. **Separation of concerns**
    
    - **Trait impl block** → ensures required functionality exists (like `book`)
        
    - **Inherent methods (impl Type block)** → add extra utilities or formatting (like `summarize`)  
        This keeps responsibilities clear.
        

---

## 3) **Why we cannot mix default and custom trait method within the same call**

- Rust enforces either:
    
    1. Use the **default implementation** from the trait, **or**
        
    2. Provide a **full override** in the trait impl for the type.
        
- Rust does **not allow**: “call the default and add extra behavior” from the trait impl itself.
    

**Reason:** Rust wants **explicit and predictable method resolution**. The compiler avoids ambiguity about which version of the method is being called.

---

## 4) **Real-world analogy**

- Imagine a hotel chain manual (`Accommodation` trait) with a default description: “A wonderful place to stay.”
    
- Each hotel can optionally write a custom description.
    
- Then a receptionist (`summarize` method) can produce a summary by calling the manual’s description without knowing whether it’s the default or custom version.
    
- The receptionist doesn’t need to rewrite the description logic—they just **invoke the contract provided by the trait**.
    

---

## ✅ Key Takeaways

1. **Purpose**: Reuse logic, write generic methods, and keep code clean.
    
2. **Reason**: Traits guarantee the existence of methods; calling them from other methods allows abstraction from specific types.
    
3. **Benefit**: Consistency, maintainability, and flexibility across multiple types.
    
4. **Limitation**: You cannot partially use the default and partially override in Rust; it’s either default or full override.
