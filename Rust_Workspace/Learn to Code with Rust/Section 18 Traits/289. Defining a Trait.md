# Defining a Trait in Rust: Example with `Accommodation`

---

## 1. Why Traits?

In Rust, **traits** define shared behaviors.  
Think of them as **contracts**: if a type implements a trait, it promises to provide specific methods and follow specific rules.

For our example, imagine we’re building a **travel booking system** (like Expedia, Kayak, or Skyscanner). Users will book places to stay: hotels, Airbnbs, etc.

Each of these is different, but they share the same **distinguishing characteristic**:  
➡️ They are all **accommodations** you can book.

So, instead of writing totally separate logic for hotels and Airbnbs, we’ll define a trait called `Accommodation` that captures this shared quality.

---

## 2. Defining the Trait

In Rust, traits are introduced with the `trait` keyword, followed by a name in **PascalCase**.  
Then, inside curly braces, we define the **methods that every implementing type must provide**.

```rust
trait Accommodation {
    fn get_description(&self) -> String;
    fn book(&mut self, name: &str, nights: u32);
}
```

Here’s what’s happening:

### Method 1: `get_description`

- Signature: `fn get_description(&self) -> String`
    
- Takes an **immutable reference** to `self` (the instance of the type).
    
- Must return a `String`.
    
- Purpose: give a summary/description of the accommodation (e.g., “Hotel in Paris with breakfast included”).
    

This method doesn’t change the object—it just reads from it.

---

### Method 2: `book`

- Signature: `fn book(&mut self, name: &str, nights: u32)`
    
- Takes a **mutable reference** to `self`.
    
- Accepts:
    
    - `name` → a string slice (`&str`) representing the person booking.
        
    - `nights` → a `u32` for how many nights.
        
- Returns nothing (`()`), because its purpose is to **mutate the internal state** of the type (e.g., record the booking, decrement availability).
    

---

## 3. Traits = Contracts, Not Implementations

Notice something important:

- We wrote **method signatures**, but no method bodies.
    
- This is because a trait only says: _“Any type implementing me must have these methods, with these parameters and return types.”_
    
- The **actual logic** of the methods is left to the individual type.
    

So:

- A `Hotel` type might implement `book` by decrementing available rooms.
    
- An `Airbnb` type might implement `book` by flipping a “reserved” flag.
    

Both follow the contract, but the details are unique.

---

## 4. Why This Is Powerful

- **Consistency**: No matter what kind of accommodation (hotel, Airbnb, resort, etc.), you’ll always know it has `.get_description()` and `.book()`.
    
- **Flexibility**: We don’t have to know all possible accommodation types in advance. Future types can implement `Accommodation` later, and they’ll work seamlessly with the rest of the code.
    
- **Safety**: If a type claims to be an `Accommodation` but forgets to define one of the methods, the **compiler rejects the program**.
    

---

## 5. Summary

- A **trait** in Rust defines **shared behavior** as a set of method signatures.
    
- Our `Accommodation` trait requires two methods:
    
    - `get_description(&self) -> String`
        
    - `book(&mut self, name: &str, nights: u32)`
        
- Any type implementing this trait must define **both methods exactly as declared**.
    
- Traits don’t care _how_ the methods are implemented—only that they exist.
    

This gives us both **standardization** (every accommodation type behaves the same way from the outside) and **freedom** (each type customizes the details internally).
