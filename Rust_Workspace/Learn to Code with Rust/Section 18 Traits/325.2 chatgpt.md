# Traits — in-depth study guide (detailed, example-first, in-scope)

---

## What a trait is (plain language)

A **trait** is a _contract_ that says: “Any type that implements this trait will provide these behaviors (methods, associated items).”  
Traits let different types express the **same capability** so you can write code that works with any type that fulfills the contract.

---

## Basic trait syntax and implementation

### Define a trait

```rust
trait Summary {
    fn summarize(&self) -> String;         // required method (no body)
    fn summarize_brief(&self) -> String {  // default implementation
        String::from("(Read more...)")
    }
}
```

- Methods without bodies are **required**; implementors must provide them.
    
- Methods with bodies are **default** implementations; implementors may override them.
    

### Implement the trait for a type

```rust
struct Article {
    headline: String,
    author: String,
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("{} — by {}", self.headline, self.author)
    }
    // summarize_brief() uses default unless we override it here
}
```

- Use `impl Trait for Type { ... }`.
    
- Methods unrelated to the trait belong in a **separate `impl Type { ... }` block** (associated functions / inherent methods).

## Associated constants & methods in traits

You can include **constants** and **associated types** in trait definitions.

```rust
trait HasId {
    const PREFIX: &'static str;
    fn id_string(&self) -> String {
        format!("{}-{}", Self::PREFIX, self.local_id())
    }
    fn local_id(&self) -> u32; // required method
}
```

- `Self::PREFIX` refers to the constant for the concrete implementor.
    
- Constants are handy for shared configuration across implementors.

## Trait bounds (constraining generics)

### Three ways to constrain function parameters with traits

1. `impl Trait` shorthand (parameter position):
    

```rust
fn print_display(x: impl std::fmt::Display) {
    println!("{}", x);
}
```

2. Generic parameter with trait bound:
    

```rust
fn print_display<T: std::fmt::Display>(x: T) {
    println!("{}", x);
}
```

3. `where` clause (good when bounds get complex):
    

```rust
fn compare<T, U>(a: T, b: U) -> bool
where
    T: std::cmp::PartialEq + std::fmt::Debug,
    U: std::fmt::Debug,
{
    println!("{:?} {:?}", a, b);
    // ...
    true
}
```

**Notes**

- Use `impl Trait` for concise APIs. Use generics + `where` when multiple bounds or many generics make signatures noisy.
    
- Multiple trait bounds: `T: Trait1 + Trait2`.

## Trait objects & dynamic dispatch (`dyn`)

Trait objects let you work with **heterogeneous collections** or accept different types at runtime:

```rust
trait Draw {
    fn draw(&self);
}

struct Button;
impl Draw for Button {
    fn draw(&self) { println!("Button"); }
}

struct Label;
impl Draw for Label {
    fn draw(&self) { println!("Label"); }
}

// collect different types that implement Draw
let widgets: Vec<Box<dyn Draw>> = vec![Box::new(Button), Box::new(Label)];

for w in widgets {
    w.draw(); // dynamic dispatch: runtime call to concrete draw()
}
```

- Use `Box<dyn Trait>` (or `&dyn Trait`) to store trait objects because types implementing the trait usually have different sizes.
    
- **Dynamic dispatch** (runtime vtable lookup) is used; contrast with **static dispatch** for generics (monomorphization).
    

### Object safety (short note)

Not every trait can become a trait object. A trait is **object-safe** if it:

- doesn’t require `Self: Sized`, and
    
- has no methods that use generic type parameters.
    

E.g., `fn new() -> Self` prevents making a trait object because it returns `Self` by value (not object-safe).

## Getters / Setters pattern with traits

Traits can’t mandate particular fields, but they can require methods that read/write data — a standard getter/setter pattern:

```rust
trait Named {
    fn name(&self) -> &str;           // getter
    fn set_name(&mut self, name: String); // setter
}
```

Any type can implement these methods using its own internal storage.

## Supertraits (trait inheritance)

A trait can require that implementors also implement another trait:

```rust
use std::fmt::Display;

trait AsText: Display {
    fn as_text(&self) -> String;
}

impl AsText for i32 {
    fn as_text(&self) -> String { format!("{}", self) }
}
```

- `AsText: Display` means “to implement `AsText`, you must also implement `Display`.”
    
- Supertraits allow using methods/behaviors from the parent inside the child trait implementations.

## Built-in traits — important ones and how to implement / derive

### `Debug` & `Display`

- `Debug` — programmer-facing, printable via `{:?}` (auto-derive is common).
    
- `Display` — user-facing, printable via `{}` (usually custom impl).
    

Example `Display` impl:

```rust
use std::fmt;

struct Point { x: i32, y: i32 }

impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "Point({}, {})", self.x, self.y)
    }
}
```

### `Drop`

- Implement `Drop` to run cleanup logic when a value is deallocated.
    
- Rust automatically runs `drop` when the owner goes out of scope; you **do not call `drop` directly** (you can call `std::mem::drop`, but not `Drop::drop`).
    

```rust
impl Drop for MyType {
    fn drop(&mut self) {
        // cleanup
    }
}
```

### `Clone` and `Copy`

- `Clone` → explicit deep copy via `.clone()`.
    
- `Copy` → implicit, cheap copy in assignments; **Copy is a subtrait of Clone**.
    
- `Copy` is for small, trivially copyable types (integers, bools). `String` is not `Copy`.
    

Use derive when appropriate:

```rust
#[derive(Clone, Copy, Debug)]
struct Point { x: i32, y: i32 }
```

### `PartialEq`, `Eq`, `PartialOrd`, `Ord`

- `PartialEq` enables `==` and `!=`. `Eq` is a stricter subtrait (reflexive, symmetric, transitive).
    
- Floating-point types implement `PartialEq` but **not** `Eq` because of `NaN`.
    
- `PartialOrd`/`Ord` for ordering; `Ord` requires total ordering.
    

Derive or implement as needed:

```rust
#[derive(PartialEq, Eq, PartialOrd, Ord, Debug)]
struct UserId(u64);
```

### Associated types (example: `Iterator`, `Add`)

Traits can define associated types that the implementor specifies:

```rust
use std::ops::Add;

impl Add for Point {
    type Output = Point;
    fn add(self, other: Point) -> Point {
        Point { x: self.x + other.x, y: self.y + other.y }
    }
}
```

- Associated types avoid long generic signatures like `trait MyTrait<T>` by giving a named placeholder inside the trait.

## `derive` attribute — quick, safe defaults

Rust can auto-generate implementations for common traits using `#[derive(...)]`:

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
struct Person { name: String, age: u32 }
```

- `derive(Clone)` uses field `clone()`; `derive(Copy)` is only allowed when all fields are `Copy`.
    
- Use custom `impl` only if you need non-default behavior.

## Practical patterns & examples

### 1) Default methods + override

```rust
trait Logger {
    fn log(&self, msg: &str) { println!("[LOG] {}", msg); }
    fn name(&self) -> &str;
}

struct App;
impl Logger for App {
    fn name(&self) -> &str { "App" }
    // uses default log()
}
```

### 2) Trait bounds to accept many types

```rust
fn summarize_all(items: &[impl Summary]) {
    for item in items { println!("{}", item.summarize()); }
}
```

### 3) Heterogeneous collection with trait objects

```rust
let mut v: Vec<Box<dyn Draw>> = Vec::new();
v.push(Box::new(Button::new()));
v.push(Box::new(Label::new()));
for widget in &v { widget.draw(); }
```

### 4) Associated type example (Iterator-like)

```rust
trait MyIterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
}
```

## Performance & design tradeoffs

- **Generics (static dispatch)**: compile-time monomorphization; zero-cost abstraction but can increase binary size. Use when performance matters and types are known at compile-time.
    
- **Trait objects (`dyn`) (dynamic dispatch)**: runtime vtable lookup; flexible and small binary but slight runtime cost. Use when you need heterogeneity or plugin-like behavior.
    

---

## Common pitfalls & tips

- Trying to make a trait object for a trait that is not object-safe → compile error. Keep object-safe design if you want `dyn Trait`.
    
- Don’t rely on `derive` blindly if you need special behavior (equality semantics, cloning resources, etc.). Implement manually when semantics differ.
    
- Prefer `&dyn Trait` or `Box<dyn Trait>` rather than plain `dyn Trait` (unsized).
    
- Choose between `impl Trait` and generic bounds depending on API clarity and whether callers need to name concrete types.
    
- Use `where` to keep signatures readable for many bounds.

## Quick reference: cheat sheet

- Define trait:
    
    ```rust
    trait Name { fn required(&self); fn optional(&self) { /* default */ } }
    ```
    
- Implement:
    
    ```rust
    impl Name for MyType { fn required(&self) { ... } }
    ```
    
- Trait bounds:
    
    ```rust
    fn f<T: TraitA + TraitB>(x: T) { }
    fn g(x: impl TraitA + TraitB) { }
    fn h<T>(x: T) where T: TraitA + TraitB { }
    ```
    
- Trait object:
    
    ```rust
    let v: Vec<Box<dyn Trait>> = vec![Box::new(A), Box::new(B)];
    ```
    
- Common derives: `#[derive(Debug, Clone, PartialEq, Eq, PartialOrd, Ord, Hash)]`
    

---

## Wrap-up recommendations

- Use traits to express **capabilities**, not data layout.
    
- Favor small, focused traits (single responsibility) — they compose better.
    
- Use default methods for shared behavior; override when implementors need special logic.
    
- Pick static dispatch (generics) for tight loops and performance; pick trait objects when you need runtime flexibility.
    
- When designing APIs, prefer taking `&impl Trait` or `T: Trait` for flexibility; document whether you need ownership or just a borrow.
