Here is the professional rephrasing of your requirement, graded by context.

The technical term you are looking for is **"Multi-Instance Support"** or **"Non-Singleton Windows."**

### Option 1: The "Software Engineer" Definition (Precise)

> "The application must support **multiple concurrent instances** of the same feature. Triggering a feature from the main menu should always **instantiate a new tab** with its own independent state, rather than focusing an existing tab of that type."

### Option 2: The "Product Requirement" (Clear & Actionable)

> "We need to allow the user to open the same tool multiple times simultaneously. If I select 'Stock Scanner' from the menu, it should open a new 'Stock Scanner' tab every time, allowing me to perform **parallel tasks** without overwriting my previous work."

### Option 3: The "User Story" (Simple)

> "As a user, I want to be able to open multiple, separate tabs of the same feature (like two different charts) so that I can work on different tasks side-by-side."

---

### The Technical Implication (Mental Model)

You are describing a **Factory Pattern** vs. a **Singleton Pattern**.

- **Singleton (What you DON'T want):**
    
    1. User clicks "Chart".
        
    2. App checks: "Is Chart open?"
        
    3. Yes $\rightarrow$ Focus existing Chart.
        
- **Factory (What you DO want):**
    
    1. User clicks "Chart".
        
    2. App says: "Create `new Chart { id: random_uuid() }`."
        
    3. App pushes this new object into the `egui_tiles` tree.
        

### How this affects your Project Structure

To make this work in Rust with `egui_tiles`, your **Data Structure** must be designed to hold a `Vec` or `HashMap` of these features, where every tab has a unique ID.

You cannot just have:

Rust

```
struct AppState {
    scanner: Scanner, // BAD: Only allows one scanner
}
```

You must have:

Rust

```
struct AppState {
    // GOOD: Allows infinite scanners, identified by unique IDs
    open_scanners: HashMap<TileId, ScannerState>, 
}
```
