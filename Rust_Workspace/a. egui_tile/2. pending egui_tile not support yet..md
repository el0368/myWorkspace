Here is the professional rephrasing of your requirement.

The industry term for "detaching a tab into a real window" is **"Tear-out Tabs"** or **"Floating Viewports."**

### Option 1: The "UX Designer" Definition (Behavioral)

> "The application must support **Tear-out Tabs**. Users should be able to drag a tab outside the main window boundaries to create a new **Floating Window**. This new window must act as a fully functional **Docking Container**, allowing other tabs to be dropped into it."

### Option 2: The "Systems Architect" Definition (Technical)

> "We require **Multi-Viewport Support** with deep integration into the layout engine. The state management system must allow transferring a `Pane` from the primary `Tree` to a secondary `Native Window` (Viewport) at runtime."

---

### Can `egui_tiles` do this?

**Short Answer:** Yes, but it is **not automatic**. You have to build the bridge yourself.

**The Engineering Reality:**

1. **`egui` (The core):** Supports this via **Viewports**. It allows you to spawn real OS windows.
    
2. **`egui_tiles` (The layout):** Supports tiling _inside_ a container.
    

The Challenge (The "Hard" Part):

egui_tiles does not inherently know about other OS windows. It assumes it lives in one rectangle.

To achieve the VS Code effect, you must implement **State Transfer**:

1. **Detect Drag:** When the mouse leaves Window A with a tab.
    
2. **Spawn Window B:** Create a new `egui` Viewport.
    
3. **Transfer State:** Remove the data (the specific Stock Scanner instance) from `Tree A` and inject it into a new `Tree B` inside the new window.
    

### Mentor's Advice:

**Do not build this in Phase 1.**

This is a "High Complexity / Low Value" feature for an initial prototype.

- **Reason:** Syncing data between two separate windows in Rust requires complex thread locking (`Arc<Mutex<State>>`) or message passing. If you get it wrong, the app will crash when you close the second window.
    

My Recommendation:

Stick to a Single Window MDI (Multiple Document Interface) first. Let egui_tiles handle the tiling inside one main window. Once that is robust, we can refactor for Multi-Window support (Phase 2).
