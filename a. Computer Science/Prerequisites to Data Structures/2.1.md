Below are the answers to the study questions based on the study guide for "Data Types vs. Abstract Data Types," adapted for Rust programming.

### 1. What are the two main aspects of a data type? Provide examples using Rust types `i32` and `f64`.
**Answer**:
The two main aspects of a data type are:
- **Domain of Values**: The set of valid values the data type can hold.
- **Allowed Operations**: The operations that can be performed on those values.

**Examples**:
- **`i32`** (32-bit signed integer in Rust):
  - **Domain**: Integer values from `-2,147,483,648` to `2,147,483,647`.
  - **Operations**: Addition (`+`), subtraction (`-`), multiplication (`*`), division (`/`), bitwise operations (`&`, `|`, `^`), modulo (`%`).
  - Example: `let x: i32 = 5; let y = x + 3; // y = 8`
- **`f64`** (64-bit floating-point number in Rust):
  - **Domain**: Floating-point values (e.g., `3.14`, `-0.001`, `1e-10`).
  - **Operations**: Addition, subtraction, multiplication, division, but **not** bitwise operations or modulo.
  - Example: `let a: f64 = 2.5; let b = a * 2.0; // b = 5.0`

### 2. How does a user-defined data type differ from a primitive data type in Rust? Give an example of a user-defined type.
**Answer**:
- **Primitive Data Type**: Predefined by the Rust language, with fixed values and operations (e.g., `i32`, `f64`, `bool`, `char`). These are built into the language and cannot be modified.
- **User-Defined Data Type**: Created by the programmer, allowing custom combinations of values and operations. The programmer defines the structure and behavior using constructs like `struct`, `enum`, or `union`.

**Example of a User-Defined Type**:
```rust
struct Point {
    x: i32,
    y: i32,
}

impl Point {
    fn new(x: i32, y: i32) -> Self {
        Point { x, y }
    }

    fn distance_from_origin(&self) -> f64 {
        ((self.x.pow(2) + self.y.pow(2)) as f64).sqrt()
    }
}
```
- **Explanation**: The `Point` struct combines two `i32` fields to represent a 2D point. The `impl` block defines custom operations (e.g., calculating the distance from the origin), which is not possible with primitive types like `i32` alone.

### 3. What is an abstract data type (ADT), and how does it hide implementation details?
**Answer**:
- **Definition**: An Abstract Data Type (ADT) is a user-defined data type that specifies a set of operations on values using functions, without revealing how those operations are implemented. It acts as a "black box," hiding the internal structure and logic from the user.
- **Hiding Implementation Details**:
  - The ADT provides an interface (e.g., function names like `push`, `pop`) that defines what operations can be performed.
  - The internal data structure and logic (e.g., whether an array or linked list is used) are not exposed to the user.
  - In Rust, this is often achieved using `pub` for interface functions and `private` fields in structs, ensuring clients can only interact through the defined interface.
- **Example**: A stack ADT allows `push` and `pop` operations, but the user doesn’t know whether the stack is implemented with a `Vec` or a linked list.

### 4. Describe the operations of a stack ADT and provide a Rust code snippet showing its interface.
**Answer**:
- **Stack ADT Operations**:
  - `initialize()` or `new()`: Creates an empty stack.
  - `push(item)`: Adds an item to the top of the stack.
  - `pop()`: Removes and returns the top item from the stack.
  - `is_empty()`: Checks if the stack is empty.
  - `is_full()`: Checks if the stack is full (relevant for fixed-size implementations).
- **Rust Code Snippet (Interface)**:
```rust
pub struct Stack<T> {
    items: Vec<T>, // Private field, implementation hidden
}

impl<T> Stack<T> {
    pub fn new() -> Self {
        Stack { items: Vec::new() }
    }

    pub fn push(&mut self, item: T) {
        self.items.push(item);
    }

    pub fn pop(&mut self) -> Option<T> {
        self.items.pop()
    }

    pub fn is_empty(&self) -> bool {
        self.items.is_empty()
    }
}
```
- **Explanation**: This defines a generic `Stack<T>` with public methods (`new`, `push`, `pop`, `is_empty`) that form the interface. The `items` field (a `Vec<T>`) is private, hiding the implementation from the client.

### 5. Why is abstraction important in ADTs? How does it benefit client programs?
**Answer**:
- **Importance of Abstraction**:
  - Abstraction hides the internal implementation details of an ADT, exposing only the interface (e.g., function names and their behavior).
  - This simplifies the user’s interaction with the data structure, as they only need to know what operations are available, not how they work internally.
- **Benefits to Client Programs**:
  - **Ease of Use**: Clients can use the ADT (e.g., `stack.push(5)`) without understanding the underlying data structure (e.g., array or linked list).
  - **Flexibility**: The implementation can change (e.g., from `Vec` to a linked list) without requiring changes to the client code, as long as the interface remains the same.
  - **Maintainability**: Separates the concerns of implementation (backend) and usage (client), making it easier to update or optimize the implementation without affecting users.
  - **Error Reduction**: By limiting access to the interface, abstraction prevents clients from directly manipulating internal data, reducing bugs.

### 6. How can a stack ADT be implemented in Rust? List two possible data structures and explain their differences.
**Answer**:
A stack ADT in Rust can be implemented using:
- **1. Vector (`Vec<T>`)**:
  - **Description**: Uses Rust’s dynamic array (`Vec`) to store elements. Elements are added/removed from the end using `push` and `pop`.
  - **Implementation** (as shown in question 4):
    ```rust
    struct Stack<T> {
        items: Vec<T>,
    }
    ```
  - **Characteristics**:
    - **Memory**: Contiguous memory allocation, efficient for small to medium-sized stacks.
    - **Performance**: Fast for `push` and `pop` (O(1) amortized) but may require reallocation if the vector grows.
    - **Use Case**: Suitable for stacks with predictable sizes or when memory efficiency is key.
- **2. Linked List (`std::collections::LinkedList` or custom)**:
  - **Description**: Uses a linked list where each node contains an element and a reference to the next node. `push` adds to the head, and `pop` removes from the head.
  - **Implementation** (simplified custom linked list):
    ```rust
    struct Node<T> {
        data: T,
        next: Option<Box<Node<T>>>,
    }

    pub struct Stack<T> {
        head: Option<Box<Node<T>>>,
    }

    impl<T> Stack<T> {
        pub fn new() -> Self {
            Stack { head: None }
        }

        pub fn push(&mut self, data: T) {
            let new_node = Box::new(Node {
                data,
                next: self.head.take(),
            });
            self.head = Some(new_node);
        }

        pub fn pop(&mut self) -> Option<T> {
            self.head.take().map(|node| {
                self.head = node.next;
                node.data
            })
        }

        pub fn is_empty(&self) -> bool {
            self.head.is_none()
        }
    }
    ```
  - **Characteristics**:
    - **Memory**: Non-contiguous memory, each node has overhead for storing pointers.
    - **Performance**: O(1) for `push` and `pop`, no reallocation needed, but higher memory overhead.
    - **Use Case**: Better for stacks with unpredictable sizes or frequent insertions/removals.

**Differences**:
- **Memory Layout**: `Vec` uses contiguous memory (cache-friendly), while linked lists use scattered nodes (less cache-friendly).
- **Performance**: `Vec` is faster for most operations due to cache locality but may incur reallocation costs. Linked lists have constant-time operations but higher memory overhead.
- **Flexibility**: Linked lists handle dynamic sizes better, while `Vec` is more efficient for fixed or predictable sizes.

### 7. Explain how Rust’s ownership model enhances the safety of ADTs compared to C.
**Answer**:
- **Rust’s Ownership Model**:
  - Rust enforces strict ownership rules: each value has a single owner, and borrowing rules (`&` for immutable, `&mut` for mutable) prevent data races and invalid memory access.
  - Lifetimes ensure references are valid, preventing dangling pointers.
  - Example in `Stack<T>`:
    ```rust
    pub fn push(&mut self, item: T) {
        self.items.push(item);
    }
    ```
    - The `&mut self` ensures only one mutable reference to the stack exists at a time, preventing concurrent modifications.
- **C’s Limitations**:
  - C relies on manual memory management (`malloc`, `free`), which can lead to memory leaks, dangling pointers, or double-free errors.
  - No ownership model, so multiple pointers can modify the same memory, risking data corruption.
  - Example: A C stack implementation might use a raw pointer array, where accidental overwrites or invalid access can cause undefined behavior.
- **Safety Enhancements in Rust**:
  - **Memory Safety**: Rust’s ownership prevents memory leaks and dangling pointers (e.g., `Vec` handles deallocation automatically).
  - **Type Safety**: Rust’s type system ensures operations are valid (e.g., attempting a bitwise operation on `f64` fails at compile time).
  - **Concurrency Safety**: Borrowing rules prevent data races in multi-threaded programs, unlike C where manual synchronization is needed.
  - **Encapsulation**: Rust’s `pub`/`private` visibility ensures clients only access the ADT interface, reducing accidental misuse compared to C’s less strict encapsulation.

### 8. Why can the implementation of an ADT change without affecting the client program? Provide an example.
**Answer**:
- **Reason**: An ADT provides an interface that defines operations (e.g., `push`, `pop`) without exposing the internal implementation. The client program interacts only with this interface, so changes to the underlying data structure (e.g., from `Vec` to a linked list) don’t affect the client as long as the interface remains consistent.
- **Mechanism**:
  - The ADT hides implementation details (e.g., data storage) behind public functions.
  - Rust’s module system and visibility rules (`pub`/`private`) enforce this separation.
- **Example**:
  - **Initial Implementation (Using `Vec`)**:
    ```rust
    pub struct Stack<T> {
        items: Vec<T>,
    }

    impl<T> Stack<T> {
        pub fn new() -> Self {
            Stack { items: Vec::new() }
        }
        pub fn push(&mut self, item: T) {
            self.items.push(item);
        }
        pub fn pop(&mut self) -> Option<T> {
            self.items.pop()
        }
    }
    ```
  - **Client Code**:
    ```rust
    fn main() {
        let mut stack: Stack<i32> = Stack::new();
        stack.push(1);
        stack.push(2);
        println!("Popped: {:?}", stack.pop()); // Prints: Popped: Some(2)
    }
    ```
  - **Changed Implementation (Using Linked List)**:
    ```rust
    struct Node<T> {
        data: T,
        next: Option<Box<Node<T>>>,
    }

    pub struct Stack<T> {
        head: Option<Box<Node<T>>>,
    }

    impl<T> Stack<T> {
        pub fn new() -> Self {
            Stack { head: None }
        }
        pub fn push(&mut self, data: T) {
            let new_node = Box::new(Node {
                data,
                next: self.head.take(),
            });
            self.head = Some(new_node);
        }
        pub fn pop(&mut self) -> Option<T> {
            self.head.take().map(|node| {
                self.head = node.next;
                node.data
            })
        }
    }
    ```
  - **Explanation**: The client code remains unchanged because it only uses the `new`, `push`, and `pop` methods, which have the same signatures in both implementations. The switch from `Vec` to a linked list is transparent to the client, demonstrating the power of abstraction in ADTs.
