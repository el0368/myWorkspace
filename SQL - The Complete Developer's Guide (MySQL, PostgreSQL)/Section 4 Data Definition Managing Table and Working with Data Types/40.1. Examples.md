# In-Depth Study Guide: Numeric Data Types in Detail & Choosing for `yearly_salary` - With More SQL Examples

This study guide continues our deep dive into numeric data types, expanding on the nuances of each category and providing more concrete SQL examples, particularly in the context of our `yearly_salary` column and other common scenarios.

## 1. Recap: Categories of Numeric Data Types

Before diving into the `yearly_salary` decision, let's briefly reiterate the three main categories of numeric data types, with additional SQL syntax for clarity.

### 1.1. Integers (Whole Numbers)

- **Definition:** Store whole numbers without decimal places.
    
- **Behavior:** If a non-integer is inserted, it's typically rounded or truncated.
    
- **Benefits:** Excellent performance, efficient storage.
    
- **Variations (with SQL Examples):**
    
    - **`TINYINT` (MySQL specific):** Typically -128 to 127 (signed) or 0 to 255 (unsigned).
        
        SQL
        
        ```SQL
        -- Example for a column storing age (max 200, so TinyInt is fine)
        CREATE TABLE people (
            person_id INT,
            age TINYINT
        );
        ```
        
    - **`SMALLINT`:** Typically -32,768 to 32,767.
        
        SQL
        
        ```SQL
        -- Example for a column storing a small count
        CREATE TABLE orders (
            order_id INT,
            item_count SMALLINT
        );
        ```
        
    - **`INT` (or `INTEGER`):** Standard integer, typically -2,147,483,648 to 2,147,483,647.
        
        SQL
        
        ```SQL
        -- Example for user IDs or general counts
        CREATE TABLE products (
            product_id INT,
            stock_quantity INT
        );
        ```
        
    - **`MEDIUMINT` (MySQL specific):** Larger than `SMALLINT` but smaller than `INT`.
        
        SQL
        
        ```SQL
        -- Example for a column that might exceed SMALLINT but not INT
        -- (less commonly used than INT)
        CREATE TABLE cities (
            city_id INT,
            population_estimate MEDIUMINT
        );
        ```
        
    - **`BIGINT`:** For very large integers, typically -9,223,372,036,854,775,808 to 9,223,372,036,854,775,807.
        
        SQL
        
        ```SQL
        -- Example for very large counters or IDs that could grow over time
        CREATE TABLE website_analytics (
            event_id BIGINT,
            total_clicks_today BIGINT
        );
        ```
        

### 1.2. Exact Fractional Numbers (`DECIMAL`, `NUMERIC`)

- **Definition:** Store numbers with decimal places with **guaranteed exact precision**. Essential for financial data.
    
- **Syntax:** `DECIMAL(P, S)` or `NUMERIC(P, S)`
    
    - `P` (Precision): Total number of digits (before and after the decimal point).
        
    - `S` (Scale): Number of digits after the decimal point.
        
- **Behavior:** No data loss in the fractional part.
    
- **Benefits:** Absolute precision.
    
- **Downside:** Slightly higher performance cost.
    
- **SQL Examples:**
    
    SQL
    
    ```SQL
    -- Example for storing product prices (e.g., $999.99, max value of 9999.99)
    CREATE TABLE items (
        item_id INT,
        price DECIMAL(6, 2) -- Total 6 digits, 2 after decimal
    );
    ```
    
    - `DECIMAL(6, 2)`: Allows values up to `9999.99`. If you insert `12.345`, it might be rounded to `12.35`. If you insert `12345.67`, it would result in an error (too many digits before decimal).
        
    
    SQL
    
    ```SQL
    -- Example for a percentage with high precision
    CREATE TABLE statistics (
        stat_id INT,
        accuracy_rate NUMERIC(5, 4) -- Total 5 digits, 4 after decimal (e.g., 0.9876)
    );
    ```
    
    - `NUMERIC(5, 4)`: Allows values like `0.9876`, `9.9999`.
        

### 1.3. Approximate Fractional Numbers (`FLOAT`, `REAL`, `DOUBLE`)

- **Definition:** Store numbers with decimal places using **approximate precision**. Minor rounding errors can occur.
    
- **Benefits:** Generally better performance and storage efficiency than exact fractional types.
    
- **Downside:** Not suitable for exact monetary or critical calculations.
    
- **SQL Examples:**
    
    - **`REAL` (PostgreSQL) / `FLOAT` (MySQL):** Single-precision floating-point.
        
        SQL
        
        ```SQL
        -- Example for storing sensor readings where slight imprecision is okay
        CREATE TABLE sensor_data (
            reading_id INT,
            temperature REAL -- Or FLOAT in MySQL
        );
        ```
        
    - **`DOUBLE PRECISION` (PostgreSQL) / `DOUBLE` (MySQL):** Double-precision floating-point, offering more precision than `REAL`/`FLOAT`.
        
        SQL
        
        ```SQL
        -- Example for storing geographical coordinates (latitude/longitude)
        CREATE TABLE locations (
            location_id INT,
            latitude DOUBLE PRECISION, -- Or DOUBLE in MySQL
            longitude DOUBLE PRECISION
        );
        ```
        

## 2. Decision Process: Choosing Data Type for `yearly_salary` (Revisited with Examples)

For the `yearly_salary` column in our `users` table, we reconsider the numeric data types based on application needs.

### 2.1. Why `DECIMAL` (Exact Fractional) might seem logical but is opted against for this use case:

- **Syntax:** `yearly_salary DECIMAL(10, 2)` (for a salary up to 99,999,999.99)
    
- **Argument For:** Money, so exactness seems important. This type guarantees no rounding errors.
    
- **Argument Against (for _this specific scenario_):**
    
    - **Context:** Is this salary used for _exact_ payroll processing within _this specific app_, or more for informational/statistical/display purposes?
        
    - **Common Representation:** Salaries are often expressed as whole numbers in general conversation ("50 thousand," not "50,000.17").
        
    - **Performance:** `DECIMAL` operations can be slightly slower than integer or float operations.
        
    
    SQL
    
    ```
    -- If we *absolutely* needed exact cents for yearly_salary:
    -- yearly_salary DECIMAL(10, 2)
    -- This would store 50000.12 exactly.
    ```
    

### 2.2. Why `FLOAT`/`REAL` (Approximate Fractional) could be considered but also opted against:

- **Syntax:** `yearly_salary REAL` (or `FLOAT` in MySQL)
    
- **Argument For:** If we wanted to store cents (e.g., 50000.12) but were willing to accept minor approximation errors for better performance.
    
- **Argument Against:** The "minor approximation errors" could still be undesirable, even for statistical purposes, if the expectation is to see the exact number entered.
    
    SQL
    
    ```
    -- If we needed fractional numbers but were okay with approximation:
    -- yearly_salary REAL
    -- This would store something like 50000.12 as 50000.1199999999...
    ```
    

### 2.3. The Chosen Approach: `INT` (Integer / Whole Number)

- **Column Name:** `yearly_salary`
    
- **Data Type:** `INT` (or `INTEGER`)
    
- **Rationale:**
    
    - **Simplicity & Common Usage:** Salaries are frequently conceptualized and reported as whole numbers.
        
    - **Application's Use Case:** For Talently's `users` table, salary is primarily for general information, filtering, or broad statistical analysis. Exact cents are unlikely to be critical for the app's functionality (e.g., no payroll processing).
        
    - **Performance:** `INT` offers the best performance and storage efficiency among numeric types.
        
    - **No Unnecessary Precision:** We avoid storing decimal places that might not be relevant to the primary use of this data in the application.
        
- **SQL Implementation:**
    
    SQL
    
    ```SQL
    CREATE TABLE users (
        full_name VARCHAR(200),
        yearly_salary INT, -- This is our chosen type for salary
        -- ... next column for status
    );
    ```
    
    - If `50000.12` is inserted into `yearly_salary INT`, it will be converted (typically rounded or truncated depending on DBMS default behavior) to `50000`.
        

## 3. Importance of Data Type Understanding (Reinforced)

This in-depth review of numeric types and the decision-making process for `yearly_salary` highlight:

- **Contextual Decisions:** The "best" data type is never a one-size-fits-all answer. It's a contextual decision based on:
    
    - The nature of the data itself.
        
    - The specific requirements of your application.
        
    - The trade-offs you are willing to make between precision, storage, and performance.
        
- **Understanding Implications:** Always know what happens when you store different types of numbers (rounding, precision loss, performance impact).
