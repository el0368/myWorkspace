# In-Depth Study Guide: Planning Table Structures & The Importance of Data Types

## 1. From Database to Tables: Defining Structure

Having created our `talently` database, the next crucial step is to define the tables that will store our actual application data. This isn't just about creating the table, but also meticulously planning its structure:

- **Which columns will it have?**
    
- **What type of data will each column hold?**
    

This forward planning is essential because, when creating a table, you _must_ explicitly define its structure, including the data type for every single column.

## 2. The "Talently" Data Model: Planning Our Tables

We will create three main tables for the "Talently" application, building them step-by-step:

### 2.1. `users` Table (for Talents/Potential Employees)

This table will store information about the individuals (talents) managed by "Talently" and available for connection with employers.

- **Key Information to Store:**
    
    - **Full Name:** Separated into `first_name` and `last_name`.
        
    - **Yearly Salary:** The annual salary a talent receives after being hired.
        
    - **Current Status:** Indicates if the talent is:
        
        - Employed
            
        - Self-Employed
            
        - Unemployed (meaning they could be immediately connected to employers, though employed talents might also seek new opportunities).
            
- **Clarification:** This is a simplified model for learning. In a real-world application, a `users` table would likely require many more fields (e.g., social security number, address, expected salary, contact details, resume, skills list, etc.). The goal here is to keep the example manageable for learning core SQL concepts.
    

### 2.2. `employers` Table (for Hiring Companies)

This table will store details about the companies that use "Talently" to hire talents.

- **Key Information to Store:**
    
    - **Company Name:** The legal name of the hiring company.
        
    - **Address:** Separated into `street` and `city` (location where talents would work).
        
    - **Yearly Revenue:** The company's annual revenue.
        
        - **Note:** The lecturer suggests storing this in "millions" (e.g., 12.5 for 12.5 million), implying a numeric data type that can handle decimals.
            
    - **Hiring Flag:** A simple indicator (e.g., a boolean or a tiny integer) showing whether the company is actively hiring at the moment (`true`/`false` or `1`/`0`).
        

### 2.3. `conversations` Table (for Employer-Talent Communication)

This table will facilitate and store interactions between employers and users.

- **Key Information to Store:**
    
    - **Involved Parties:** Identify which `user` and which `employer` are part of the conversation. (This implies relationships/links to the `users` and `employers` tables, which will be explored later).
        
    - **Actual Text Message:** The content of the message exchanged.
        
    - **Timestamp:** The exact date and time when the message was sent. (This implies a more detailed structure where a "conversation" might hold multiple "messages," or the `conversations` table itself might represent individual messages.)
        

## 3. The Critical Role of Data Types

One of the most fundamental rules in SQL database design is the strict enforcement of data types for columns.

- **Heterogeneous Data is NOT Allowed:** You **cannot** have a single column in a table that stores different types of data across its rows (records).
    
    - **Incorrect Example:** A `yearly_salary` column cannot store a `string` (e.g., "fifty thousand") for one user and a `number` (e.g., `50000`) for another.
        
- **Homogeneous Data Per Column:** Every record (row) in a table _must_ have the same data type for a given column.
    
    - **Correct Example:** If `yearly_salary` is defined as a numeric type, _all_ values in that column, for all records, must be numbers.
        
- **Implication:** This strict requirement makes **planning ahead** for data types absolutely essential before you even write your `CREATE TABLE` statement. You need to know what kind of values each column will eventually hold.
