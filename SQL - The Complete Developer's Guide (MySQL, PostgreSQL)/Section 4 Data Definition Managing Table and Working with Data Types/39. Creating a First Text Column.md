# In-Depth Study Guide: Defining Table Columns - The `VARCHAR` Data Type

## 1. Introduction: Specifying Column Names and Data Types

After outlining the overall `CREATE TABLE` structure, the next step is to define individual columns. Each column definition requires a **column name** followed by its chosen **data type**. This lecture focuses on defining a name column using the `VARCHAR` data type.

## 2. Defining the `full_name` Column

For our `users` table in the "Talently" database, we'll start by defining a column to store the user's full name.

- **Chosen Column Name:** `full_name`
    
    - **Naming Conventions:** Adheres to the recommended `snake_case` (lowercase with underscores for spaces) and avoids SQL keywords.
        
    - **Escaping (If Needed):** While `full_name` is not a reserved keyword, remember that if you _were_ to use one, you'd wrap it in double quotes (`"full_name"`) for PostgreSQL or backticks (`` `full_name` ``) for MySQL.
        
- **Placement:** The column definition goes inside the parentheses of the `CREATE TABLE` statement.
    
    SQL
    
    ```SQL
    CREATE TABLE users (
        full_name DATATYPE, -- This is where we're working
        -- ... other columns will go here
    );
    ```
    

## 3. Choosing the Appropriate Text Data Type for Names

When storing textual data like a person's name, we need to select from the available text data types: `CHAR`, `VARCHAR`, `TEXT`, or `ENUM`.

- **Eliminating `TEXT` (and `LONGTEXT`, `MEDIUMTEXT`):**
    
    - A person's name is typically not extremely long, like a blog post or product description.
        
    - Using `TEXT` for a name would allocate more storage than necessary and is generally overkill for this use case.
        
- **Eliminating `ENUM`:**
    
    - `ENUM` is for a predefined, fixed set of values (e.g., 'employed', 'unemployed').
        
    - A person's name can be almost any combination of characters, so `ENUM` is unsuitable.
        
- **Choosing Between `CHAR` and `VARCHAR`:**
    
    - Both `CHAR(X)` and `VARCHAR(X)` define a maximum length (`X`).
        
    - **`CHAR(X)`:** Pads shorter strings with spaces up to `X` characters. This wastes space if names vary significantly in length.
        
    - **`VARCHAR(X)`:** Stores only the characters provided, without padding. This is more efficient for variable-length data.
        
    - **Conclusion:** `VARCHAR` is the preferred choice for names because names vary in length, and we don't want unnecessary padding.
        

## 4. Defining `VARCHAR(X)` for `full_name`

- **Keyword:** `VARCHAR` (conventionally written in uppercase in this course, though lowercase also works).
    
- **Maximum Length `X`:** You must specify a maximum length in parentheses after `VARCHAR`.
    
    - **Units:** This length typically refers to the maximum number of _bytes_. For many common character encodings (like ASCII or UTF-8 for basic Latin characters), one byte equals one character. However, for multi-byte characters (e.g., many international characters in UTF-8), a single character might take up more than one byte.
        
    - **Practical Consideration:** For names, a length like `200` characters is generally considered sufficient to accommodate long names without being excessively large.
        
- **Complete Column Definition:**
    
    SQL
    
    ```SQL
    full_name VARCHAR(200)
    ```
    

## 5. Separating Column Definitions with Commas

- After defining a column (its name and data type), you **must** add a **comma (`,`)** if you plan to define more columns within the same `CREATE TABLE` statement.
    
- **Last Column:** The last column definition in the list should _not_ have a trailing comma.
    

## 6. Formatting for Readability

- **Line Breaks:** While SQL statements can be written on a single line, using line breaks to put each column definition on a new line significantly improves readability, especially for tables with many columns. This is a common and highly recommended practice.
