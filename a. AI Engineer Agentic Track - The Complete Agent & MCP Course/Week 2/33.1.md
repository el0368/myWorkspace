# Deep Dive: Parallel Personas and Simplified Tools

In this stage of the SDR project, we move from simple serial calls to high-efficiency parallel workflows and automated tool integration using the OpenAI Agents SDK.

## 1. The Power of Parallelism (AsyncIO)

When we want to generate multiple outreach options (Professional, Witty, and Concise), running them one after another is slow. Instead, we use `asyncio.gather`.

### How it Works

It's not "multithreading" (which uses multiple CPU cores), but rather an **Event Loop**. While one agent is waiting for a response from the OpenAI API, the script "yields" and starts the next agent. They all wait on the network simultaneously.

```python
# We run all three agents at once
async def generate_options(query):
    runner = Runner()
    results = await asyncio.gather(
        runner.run(prof_agent, query),
        runner.run(humor_agent, query),
        runner.run(concise_agent, query)
    )
    return results
```

## 2. The "Picker" Pattern

Once we have our three options, we don't just dump them on the user. we use a specialized **Sales Picker** agent to evaluate the work of the other agents.

### Implementation Logic

1. **Generate**: Call the three SDR agents in parallel.
    
2. **Evaluate**: Pass the results to the `sales_picker`.
    
3. **Trace**: The entire process—from the initial query to the final selected email—is captured in a single **OpenAI Trace**, allowing us to debug exactly why a specific email was chosen.
    

```python
picker_instr = "Pick the best cold sales email. Reply with ONLY the email content."
sales_picker = Agent(name="Sales Picker", instructions=picker_instr)

# The orchestrator script
options = await generate_options("Write a cold email for Comply.AI")
best_email = await runner.run(sales_picker, str(options))
```

## 3. Tool Use: From "Gunk" to Elegance

In Week 1, we wrote complex JSON schemas to describe functions to the AI. The OpenAI Agents SDK eliminates this boilerplate with the `@function_tool` decorator.

### Automatic Schema Generation

The SDK performs "reflection" on your Python function. It looks at three things to build the AI's internal map:

1. **Function Name**: Used as the tool name.
    
2. **Docstring**: Used as the tool's description (crucial for the LLM to know _when_ to use it).
    
3. **Type Hints**: (e.g., `email_body: str`) Used to build the JSON parameter schema automatically.
    

```python
@function_tool
def send_email(email_body: str):
    """
    Send out an email with the given body to all sales prospects.
    """
    # SendGrid boilerplate logic lives here
    return {"status": "success"}

# Checking the tool's hidden metadata
print(send_email.description) # "Send out an email with..."
print(send_email.params_json_schema) # Automatic JSON!
```

## 4. Key Takeaways

- **Traces**: Don't just look at the output; use the OpenAI dashboard to see the parallel calls happening inside the event loop.
    
- **Efficiency**: Parallelizing LLM calls can reduce a 60-second workflow to 20 seconds.
    
- **Maintenance**: Using `@function_tool` means if you change your Python function's arguments, the AI's "understanding" of that tool updates automatically without you touching any JSON.
