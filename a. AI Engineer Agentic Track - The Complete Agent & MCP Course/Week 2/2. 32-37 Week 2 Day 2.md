## 1. Initial Setup: External APIs & Environment

Before building the agents, Day 2 requires setting up the communication infrastructure. We use **SendGrid** to allow our agents to send real transactional emails.

### Detailed SendGrid Overview:

SendGrid is a cloud-based SMTP provider that allows applications to send emails reliably without being flagged as spam. For our SDR agent, it serves as the "hands" that allow the AI to reach out to potential customers.

1. **API Key Generation:** After creating a free account, navigate to **Settings > API Keys**. Generate a "Full Access" key. This key acts as your password for the SendGrid service.
    
2. **Sender Authentication (Single Sender Verification):** SendGrid prevents spoofing by requiring you to prove you own the email address you intend to send from. Go to **Settings > Sender Authentication**, click **Verify a Single Sender**, and follow the instructions to verify your personal email.
    
    - _Note: You can only send emails "from" this verified address._
        
3. **Environment Variables:** Securely store your key in the `.env` file. Never hardcode this key into your scripts.
    
    ```
    SENDGRID_API_KEY=SG.your_key_here
    ```

## 2. Learning Objectives: From Manual JSON to Agentic SDK

The primary goal for Day 2 is to move past the "manual labor" of AI development. In Week 1, we spent a significant amount of time writing boilerplate code just to make a tool functional. Today, we let the SDK handle the "gunk."

### Abstracting Complexity: The Great Simplification

In Week 1, we had to manually define the parameters and descriptions for every tool using complex nested dictionaries. This was error-prone and tedious.

**Week 1: The Manual JSON Way**

```
# You had to write this massive dictionary manually
record_user_details_json = {

    "parameters": {
        "type": "object",
        "properties": {
```

Week 2: The SDK Way (After)

The SDK uses Python's native features to infer the schema. By simply adding a decorator, the framework "reads" your Python function and explains it to the LLM automatically.

```
from openai_agents import function_tool

@function_tool
def get_company_details(company_name: str):
    """
    Fetches public SOC2 compliance status and security history for a given company.
    Use this to personalize the cold email outreach.
    """
    # The SDK automatically generates the JSON schema from the docstring above
    # and the type hint 'company_name: str'
    return {
        "company": company_name,
        "status": "Non-compliant",
        "last_audit": "N/A",
        "pain_points": ["Manual evidence collection", "Lack of automated monitoring"]
    }
```

This shift is more than just "saving lines of code." It reduces the surface area for bugs (like typos in JSON keys) and allows the developer to treat AI capabilities as native Python functions.

### Architectural Thinking: The "Team" Mindset

We move from a single list of instructions to a coordinated team. You learn to coordinate multiple specialized agents through three distinct layers of complexity.

- **Layer 1: Parallel Orchestration:** Using `asyncio.gather` to run multiple agents at once to generate variety.
    
- **Layer 2: Agents as Tools:** Wrapping agents as tools so a "Manager" can call them autonomously based on the situation.
    
- **Layer 3: Delegation via Handoffs:** Passing total control from a manager to a specialist agent for the remainder of the task.
    

### Professional Tooling: Observability

Real-world applications require observability. We implement **tracing**, which provides a visual timeline of the agent's logic. In the SDK, this allows you to see the exact sequence of events: which personality wrote the draft, which judge picked it, and exactly how much that specific operation cost in terms of tokens.

## 3. Layer 1: Parallel Workflow (Manual Orchestration)

In the first layer, we use Python’s `asyncio` library to orchestrate a competitive workflow. The goal is to generate three different styles of outreach emails simultaneously, then use a final judge to select the winner. This pattern is ideal for tasks where "quality through variety" is the goal.

```
import asyncio
from openai_agents import Agent, runner

# Define specialized agents with unique 'personalities'
agent_prof = Agent(
    name="Professional Agent", 
    instructions="You are a serious sales agent. Write professional cold emails.", 
    model="gpt-4o-mini"
)
agent_humor = Agent(
    name="Humorous Agent", 
    instructions="You are a witty sales agent. Write engaging, funny cold emails.", 
    model="gpt-4o-mini"
)
agent_busy = Agent(
    name="Concise Agent", 
    instructions="You are a busy sales agent. Write short, to-the-point emails.", 
    model="gpt-4o-mini"
)

# The 'Judge' Agent that evaluates the outputs
sales_picker = Agent(
    name="Sales Picker",
    instructions="""You are a customer. Pick the best email from the options provided. 
    Pick the one you are most likely to respond to. Reply with the selected email ONLY.""",
    model="gpt-4o-mini"
)

async def layer_1_workflow():
    # Step 1: Execute 3 agents in parallel to save time and generate variety
    print("Generating three email variations...")
    results = await asyncio.gather(
        runner.run(agent_prof, "Write a cold email for Comply AI (SOC2 compliance)"),
        runner.run(agent_humor, "Write a cold email for Comply AI (SOC2 compliance)"),
        runner.run(agent_busy, "Write a cold email for Comply AI (SOC2 compliance)")
    )
    
    # Step 2: Combine the outputs for the judge
    options = f"""
    Option 1 (Professional): {results[0].final_output}
    ---
    Option 2 (Humorous): {results[1].final_output}
    ---
    Option 3 (Concise): {results[2].final_output}
    """
    
    # Step 3: The Judge picks the winner
    print("Selecting the best version...")
    best_email = await runner.run(sales_picker, f"Analyze these options and pick the best:\n{options}")
    print(f"\n--- FINAL SELECTION ---\n{best_email.final_output}")

# To run: await layer_1_workflow()
```

## 4. Layer 2: Agents as Tools (Autonomous Planning)

The major shift here is giving the LLM **autonomy**. Instead of the Python script deciding to call three agents, we wrap those agents as **Tools**. We then give those tools to a "Sales Manager" agent who decides which writer is best suited for the specific task at hand. This is a "request-response" pattern.

```
from openai_agents import function_tool

# Define a functional tool for the real-world action
@function_tool
def send_email(email_body: str):
    """
    Send out a cold sales email to a prospect.
    The email_body should be the final, polished text.
    """
    # This would contain SendGrid logic in a real app
    print(f"DEBUG: Email physically sent via SendGrid API!")
    return {"status": "success", "message": "Email dispatched"}

# Package our previous agents into 'Tools'
# This allows the Manager to 'call' them just like a function
writer_tools = [
    agent_prof.as_tool(description="Use this to get a professional, formal draft"),
    agent_humor.as_tool(description="Use this to get a witty, high-engagement draft"),
    agent_busy.as_tool(description="Use this for short, punchy messages"),
    send_email # The physical action tool
]

# The Sales Manager: The 'Brain' of the operation
sales_manager = Agent(
    name="Sales Manager",
    instructions="""You lead the sales team. Your goal is to send a great cold email.
    1. Call at least two writers to see different styles.
    2. Pick the best one based on the company's needs.
    3. Use the send_email tool to send the final version.
    Never draft the email yourself; always use your specialist writers.""",
    tools=writer_tools,
    model="gpt-4o-mini"
)

# Example call:
# await runner.run(sales_manager, "Prepare and send a pitch to the CTO of a Series A startup.")
```

## 5. Layer 3: The Handoff Pattern (Delegation)

Handoffs represent the "next level" of agentic architecture. In the tool pattern (Layer 2), the Manager stays in control. In the **Handoff Pattern**, the Manager **hands off** the entire conversation to a specialist. Once a handoff occurs, the specialist takes over the interaction completely. This is perfect for multi-stage processes like formatting or security reviews.

```
# Specialist agent specifically for HTML formatting and delivery
email_manager = Agent(
    name="Email Manager",
    handoff_description="Handles HTML conversion, subject line generation, and final sending.",
    instructions="""You are an expert in email deliverability.
    1. Create an eye-catching subject line for the provided email body.
    2. Convert the text into a clean HTML format.
    3. Use the send_email tool to finish the job.""",
    tools=[send_email]
)

# The SDR Agent who knows about the email_manager
autonomous_sdr = Agent(
    name="Autonomous SDR",
    instructions="""Draft a great pitch for Comply AI using your writer tools. 
    Once you have a winner, HAND OFF the task to the Email Manager to handle formatting and delivery. 
    Do not try to send the email yourself.""",
    tools=[agent_prof.as_tool(), agent_humor.as_tool()],
    handoffs=[email_manager] # This enables the 'Transfer' button in the agent's brain
)

# Example call:
# await runner.run(autonomous_sdr, "Reach out to 'Dear CEO' at Nebula Tech about SOC2.")
```

## 6. Summary: The "Moment of Autonomy"

The "Moment of Autonomy" occurs when you move from **Layer 1** to **Layer 2/3**.

- **In Layer 1**, your Python code acts as the manager (`await asyncio.gather`). Control is rigid and defined by the script.
    
- **In Layer 2 and 3**, you define the _capabilities_ (tools and handoffs) and the _goal_, then step back.
    

The LLM now performs **Planning**: it decides which tools to call, in what order, and when the task is complete. This shift reduces the complexity of your code while increasing the intelligence of your system, allowing for much more flexible business automations.
