# Week 2 Day 3: Mastering the Agentic Toolkit (Elixir Edition)

This document provides an in-depth breakdown of the advanced features within the OpenAI Agents SDK, translated for the Elixir ecosystem. We focus on the "Tooling Workflow" by examining the **Concept**, the **Input** requirements, the underlying **Process**, and the resulting **Output** produced through idiomatic functional patterns.

## 1. Multi-Model Integration (The Universal Connector)

**The Concept:** The ability to use a single orchestration layer (your Elixir application) to drive diverse "engines" like Gemini, DeepSeek, or Llama 3 on Groq. The SDK treats the LLM as a modular component; you don't rewrite your logic when you swap the brain—you simply change the connection string.

### How to use the Tool:

- **Input (Defining the Engine):** You provide an endpoint configuration via `OpenaiEx.new/2`. This requires the `api_key` and, crucially, a `base_url` that points the client to a provider's OpenAI-compatible gateway.
    
- **The Process (Wrapping):** In Elixir, we treat these configurations as data. By passing a specific client map to your agent functions, you isolate the model's platform from the agent's instructions.
    
- **Output (The Brain):** A live connection that handles requests and responses identically, regardless of whether the model is hosted by Google, Groq, or your own local instance.
    

Example Implementation:

This setup allows you to specialize agents by cost, speed, or reasoning capabilities.

```python
# lib/my_app/llm_clients.ex

# 1. Setup the DeepSeek Client: Ideal for low-cost, high-reasoning tasks
deepseek = OpenaiEx.new("DEEPSEEK_KEY") 
           |> OpenaiEx.with_base_url("[https://api.deepseek.com/v1](https://api.deepseek.com/v1)")

# 2. Setup the Gemini Client: Best for massive context windows and creative writing
gemini = OpenaiEx.new("GEMINI_KEY")
         |> OpenaiEx.with_base_url("[https://generativelanguage.googleapis.com/v1beta/openai/](https://generativelanguage.googleapis.com/v1beta/openai/)")

# 3. Setup Groq: The speed leader, perfect for real-time customer interactions
groq = OpenaiEx.new("GROQ_KEY")
       |> OpenaiEx.with_base_url("[https://api.groq.com/openai/v1](https://api.groq.com/openai/v1)")

# Deployment Pattern:
# Pass the 'groq' client to a 'FastResponder' agent, and 'deepseek' to an 'EmailManager'.
```

## 2. Structured Outputs (The Data Sculptor)

**The Concept:** Converting unstructured AI "chatter" into reliable Software 1.0 data. By forcing the LLM to return data that satisfies an `Ecto.Schema`, we bridge the gap between probabilistic AI responses and deterministic application logic.

### How to use the Tool:

- **Input (The Blueprint):** You define an `embedded_schema` using `Ecto`. We use the `@llm_doc` attribute to give the model specific context about what each field represents (e.g., "The confidence score must be between 0 and 1").
    
- **The Process (Enforcement):** The `Instructor` library generates a JSON-schema based on your Ecto definition. It then uses "Function Calling" or "JSON Mode" to force the model to populate that specific structure.
    
- **Output (The Object):** You receive a validated Elixir struct. If the AI returns invalid data, `Instructor` can automatically retry (using `max_retries`) with the specific validation error, allowing the AI to "fix" its own mistake.
    

Example Implementation:

Turning a cold-email check into a robust data object.

```python
defmodule MyApp.Schemas.EmailAnalysis do
  use Ecto.Schema
  use Instructor

  @llm_doc """
  Analyzes an email for sales potential.
  - sentiment: How interested the lead sounds (positive, neutral, negative).
  - pain_points: A list of specific problems the lead mentioned.
  - score: A priority score from 1-10.
  """
  @primary_key false
  embedded_schema do
    field :sentiment, :string
    field :pain_points, {:array, :string}
    field :score, :integer
  end
end

# Usage:
# result = Instructor.chat_completion(
#   model: "gpt-4o-mini",
#   response_model: MyApp.Schemas.EmailAnalysis,
#   max_retries: 2, # Automatically asks LLM to fix validation errors
#   messages: [%{role: "user", content: "I'm struggling with high server costs..."}]
# )
```

## 3. Guardrails (The Execution Gatekeeper)

**The Concept:** Safety "circuit breakers" that evaluate inputs or outputs. In a professional setting, guardrails prevent agents from "hallucinating" illegal advice, leaking PII (Personal Identifiable Information), or responding to malicious prompt injections.

### How to use the Tool:

- **Input (The Message):** Either the raw user prompt (`validate_input`) or the model's final response (`validate_output`).
    
- **The Process (The Gate):** You can use `run_in_parallel: false` (Blocking Mode). This means the main agent doesn't even start—saving you money and tokens—until the guardrail gives the "all clear."
    
- **Output (The Tripwire):** If the guardrail returns `{:error, reason}`, the `Runner` raises a specific Exception, halting the process immediately before any tools (like `send_email`) are triggered.
    

Example Implementation:

Implementing a blocking guard to stop competitor mentions.

```python
defmodule MyApp.Guards.CompetitorGuard do
  use OpenAI.Agents.Guardrail

  @impl true
  def validate_input(_context, message) do
    forbidden = ["CompetitorX", "CompetitorY"]
    
    # Logic can be simple regex or a call to a smaller 'Guard Agent'
    if String.contains?(String.downcase(message), forbidden) do
      {:error, "Security violation: Competitor mention found."}
    else
      {:ok, message}
    end
  end
end
```

## 4. The Runner (The Orchestrator)

**The Concept:** If the Agent is the "brain," the **Runner** is the "body." It manages the **Agentic Loop**: sending prompts, parsing tool calls, executing the code, and feeding the results back until a final answer is reached.

### How to use the Tool:

- **Process-Based Isolation:** In Elixir, every `Runner.run/2` call is isolated in its own BEAM process. If an agent crashes while executing a complex tool, it won't take down your web server or other running agents.
    
- **Output:** You receive an `OpenAI.Agents.RunResult` struct, which contains the `final_output` (the answer), the `messages` (the full audit trail), and the `trace_id`.
    

**Example Workflow:**

```python
# The Runner manages the loop: Prompt -> LLM -> Tool -> LLM -> Result
{:ok, result} = OpenAI.Agents.run(MyApp.Agents.SalesManager, "Contact this lead.")

# Access the audit trail to see exactly what tools were called
Enum.each(result.messages, fn msg -> IO.inspect(msg.role) end)
```

## 5. Tracing and Observability (The Flight Recorder)

**The Concept:** Autonomous agents can be unpredictable. **Tracing** provides a visual map of every step. In Elixir, we leverage `Telemetry` to emit events for every start/stop of a model, tool, or guardrail.

### The "Span" Hierarchy:

A **Trace** is the complete journey. Inside, you have **Spans** (steps):

- **`generation_span`**: Records exactly what was sent to the LLM and how many tokens were used.
    
- **`tool_span`**: Records the arguments passed to a function and the raw data it returned.
    
- **`guardrail_span`**: Shows the reasoning process of your safety checks.
    

## 6. Review: Tools vs. Handoffs

|   |   |   |
|---|---|---|
|**Feature**|**Tool (Call & Return)**|**Handoff (Transfer)**|
|**Logic**|Sub-routine / Helper function.|Delegation / "Pass the baton."|
|**Control**|Manager stays in control.|Manager exits; New Agent takes over.|
|**Best For**|"Get me the weather."|"I'm done with triage, you handle billing."|
