# Anthropic Design Patterns for LLM Workflows

## Executive Summary

This document outlines five distinct design patterns for building Large Language Model (LLM) workflows, as identified by Anthropic. These patterns provide structured approaches for decomposing complex tasks into manageable subtasks, ranging from simple sequential chains to dynamic, multi-agent collaborations. The core components of these patterns are LLM calls (represented as yellow boxes) and optional, user-written code (represented as blue boxes) that facilitates the workflow.

A recurring theme throughout the analysis is the "blurred line" between these structured workflows and more autonomous agentic systems. While Anthropic categorizes them as workflows, several patterns grant LLMs significant discretion in decision-making, task decomposition, and routing, challenging a rigid distinction. The patterns detailed are: **Prompt Chaining**, **Routing**, **Parallelization**, **Orchestrator-Worker**, and **Evaluator-Optimizer**. Each pattern offers unique advantages for managing tasks, enhancing accuracy, and creating robust, production-ready AI systems. The Evaluator-Optimizer pattern, in particular, is highlighted as a powerful and frequently used method for ensuring the quality and reliability of LLM outputs through a systematic feedback loop.

## The Five Design Patterns

Anthropic identifies five key design patterns for constructing workflows in generative AI systems. These patterns provide frameworks for orchestrating LLM calls and code to solve complex problems methodically.

### 1. Prompt Chaining

Prompt Chaining is a foundational pattern that involves a sequential series of LLM calls, where the output of one model serves as the input for the next.

- **Structure:** An input is processed by a first LLM, its output may be processed by custom code, and then passed to a second LLM, and so on, until a final output is generated. The chain can consist of any number of LLMs.
- **Purpose:** The primary goal is to decompose a larger task into a "fixed set of subtasks." This allows developers to:
    - Frame each individual LLM call very precisely to elicit the most effective response for each subtask.
    - Keep the entire workflow "on guardrails" by guiding it through a sequence of well-defined steps.
- **Example:** A commercial analysis task could be chained:
    1. **LLM 1:** Pick an industry sector.
    2. **LLM 2:** Given that sector, identify a common pain point.
    3. **LLM 3:** Given that pain point, propose a solution.
- **Autonomy Insight:** While defined as a workflow, this pattern can exhibit an "element of autonomy." For instance, the topic chosen by the first LLM dictates the context for all subsequent LLMs in the chain, giving the model discretion over the workflow's direction. This highlights the "blurred line" between workflows and agents.

### 2. Routing

The Routing pattern uses an initial LLM to classify an incoming task and direct it to the most appropriate specialist model from a pool of options.

- **Structure:** An input is received by a "router" LLM. This router analyzes the task and selects one of multiple specialist LLMs (e.g., LLM 1, LLM 2, or LLM 3) to handle it.
- **Purpose:** This pattern is powerful and "very common" for achieving a "separation of concerns." It allows a system to leverage different LLMs that have varying levels of expertise or are fine-tuned for specific functions. The router's job is to "understand which of the specialists will be best equipped to tackle this task."
- **Autonomy Insight:** Similar to Prompt Chaining, it is considered "a bit artificial to say that there's no autonomy here." The router LLM clearly makes a decision, albeit within the defined constraints of the workflow, about how the task should be processed.

### 3. Parallelization

This pattern involves using code to break a task into multiple subtasks that can be executed concurrently by several LLMs, with the results later aggregated by code.

- **Structure:** Custom code (e.g., Python) deconstructs an initial task and dispatches the pieces to multiple LLMs to run in parallel. After the LLMs complete their concurrent activities, more code "stitches them together" to form a final output.
- **Key Distinction:** The coordination—both splitting the task and aggregating the results—is handled by deterministic code, not an LLM. This is the primary difference from the Routing and Orchestrator-Worker patterns.
- **Use Cases:**
    - **Concurrent Subtasks:** The most common use is when a task naturally breaks down into multiple independent parts that can be worked on simultaneously.
    - **Redundant Execution:** The same task can be sent to multiple LLMs (e.g., three times), and an aggregator can process the results, perhaps by taking an average, to improve reliability.

### 4. Orchestrator-Worker

The Orchestrator-Worker pattern is a more dynamic version of Parallelization where LLMs, rather than code, are responsible for task decomposition and synthesis.

- **Structure:** A difficult, challenging task is given to an "orchestrator" LLM. This LLM breaks the complex task into smaller steps and assigns them to "worker" LLMs. Finally, an LLM (which could be the orchestrator or another model) combines the results from the workers to produce the final output.
- **Key Distinction:** The critical difference from Parallelization is that LLMs manage the orchestration. This makes the system "much more dynamic," as the orchestrator can decide how to "divvy up the task" and even how many worker LLMs to use.
- **Autonomy Insight:** This pattern strongly challenges the distinction between a workflow and an agent. The source notes, "it's quite artificial to categorize this as a workflow rather than an agent pattern," and "saying that this is just a fixed workflow is perhaps a stretch." The orchestrator LLM possesses significant discretion over the process.

### 5. Evaluator-Optimizer

This pattern, also referred to as "evaluators" or "validation agents," establishes a feedback loop where one LLM generates work and a second LLM critically assesses it. This is identified as the most commonly used pattern by the speaker.

- **Structure:**
    1. An "LM generator" produces a solution or output.
    2. An "evaluator" LLM, armed with extra context and information, checks the work of the generator. Its role is not to generate content but to validate it.
    3. The evaluator either **accepts** the work, which then becomes the final output, or **rejects** it.
    4. If rejected, the evaluator provides a reason, which is sent back to the LM generator.
    5. The generator uses this feedback to create a new solution, and the loop continues.
- **Purpose:** This is a "really effective pattern" for addressing key concerns in production LLM systems, such as accuracy, predictability, and robustness. It is described as a "really powerful way to increase the accuracy and build a higher level of guarantee around the quality of the final output." While not providing "full guarantees," it significantly improves the reliability of responses.
