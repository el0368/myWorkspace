# Architectural Overview: Distinguishing Agentic Workflows and Autonomous Agents

## 1.0 Introduction: Navigating the Ambiguity of "Agentic AI"

For system architects and designers, the current landscape of "Agentic AI" is characterized by significant hype and terminological ambiguity. The term is often applied broadly to a wide range of systems, creating confusion and making it difficult to establish clear design principles. The primary objective of this document is to provide a clear architectural framework for system designers by dissecting the core concepts of agentic systems. We will establish a practical model for differentiation, based on the clarifying work of Anthropic, to move from ambiguous labels to precise architectural paradigms.

To establish a baseline, we can start with a simple, crisp definition provided by Hugging Face's small agents project: AI agents are programs where LLM outputs control the workflow. This definition provides a useful starting point, as it suggests the core idea is that a single output from an LLM is able to decide what tasks are carried out and in what sequence. While this definition is a helpful anchor, the term "agent" is often applied more broadly to systems that may not strictly fit this model.

This document will therefore move beyond this single definition to explore the common characteristics that define agentic systems, before introducing a more structured framework for their classification and design.

## 2.0 The Five Hallmarks of an Agentic System

Beyond a single, narrow definition, an "agentic system" is often identified by a set of common characteristics or hallmarks. For a system designer, it is crucial to understand that this is the primary source of ambiguity in the field, as people will often use the term "agentic AI" if _any one_ of these five hallmarks are met. A system does not need to possess all of these traits; the presence of even one is often enough for the label to be applied.

1. **Multiple LLM Calls** Any solution that involves more than a single call to a Large Language Model can be considered agentic. From an architectural standpoint, this implies a process that is not a simple, single-shot transaction but rather a sequence of cognitive steps, which necessitates architectural patterns for state management and context propagation between calls.
2. **Tool Use Capability** This is the ability for an LLM to use external tools. This capability is frequently seen as the litmus test for agentic behavior. Architecturally, this requires an interface between the LLM and other systems (APIs, databases, hardware), allowing the model to not only generate text but also to take action and interact with the outside world, fundamentally expanding its operational domain.
3. **LLM Coordination Environments** This hallmark refers to a setup that allows different LLMs to exchange information with one another. Designing such a system involves creating a coordination or orchestration layer where multiple specialized models can collaborate. This pattern is foundational for building more complex, multi-actor systems that can handle multifaceted problems by distributing cognitive labor.
4. **LLM-driven Planners** This involves a dedicated process—often an LLM itself—that is responsible for coordinating activities. The planner's role is to decompose a high-level goal into a sequence of executable steps. Architecturally, this introduces a strategic layer atop the execution layer, separating the "what to do" from the "how to do it" and enabling the system to orchestrate complex tasks.
5. **Autonomy** This hallmark captures what many consider the core essence of agentic AI: granting an LLM the ability to control the sequence of actions or to "choose its own adventure." This concept of delegated agency, while sometimes perceived as "spooky," is about giving the model the opportunity to decide how future actions will be carried out. For example, a system tasked to have an LLM come up with a business sector and then analyze it exhibits autonomy at the moment the model chooses which sector to use. This provides a concrete, non-spooky illustration of constrained autonomy, representing a shift from a deterministic process to one where the system exhibits a degree of self-direction based on the model's reasoning.

These hallmarks provide a useful vocabulary for identifying agentic characteristics. To bring greater precision to system design, however, we can adopt a more structured framework that categorizes these systems into distinct architectural patterns.

## 3.0 The Anthropic Framework: A Dichotomy for Design

### 3.1 Introduce the Framework's Value

To bring much-needed clarity to the field, Anthropic has proposed a powerful framework that offers a more precise vocabulary for designers. They use the umbrella term "agentic systems" to encompass two distinct architectural paradigms. This distinction is immensely valuable, as it allows architects to move beyond the hype and make deliberate design choices. Crucially, Anthropic's model hints that many systems people call "agents" are, from an architectural standpoint, more accurately described as "workflows," providing a clarifying tool that helps re-categorize misunderstood systems.

### 3.2 Architectural Deep Dive: Workflows

Anthropic offers a precise definition for the first paradigm:

**Workflows** are systems where models and tools are orchestrated through predefined paths.

From a system design perspective, the term "predefined paths" is the critical architectural constraint. This implies that the developer or system architect retains ultimate control over the execution logic. The sequence of operations, the tools that can be called, and the decision points are all explicitly mapped out in advance. The system's behavior is therefore highly predictable and deterministic. The model operates _within_ a deterministic structure defined by the developer; it does not define the structure itself.

### 3.3 Architectural Deep Dive: Agents

The second paradigm is defined in direct contrast to the first:

**Agents** are systems where models dynamically direct their own processes and tools, maintaining the control over how tasks get accomplished.

Here, the architectural principle is fundamentally different. The concept of models "dynamically directing their own processes" means control over the execution path is delegated to the model itself. Instead of following a rigid, predefined script, the agent assesses a situation, reasons about the next best action, and autonomously selects and executes tools to move toward its goal. This results in architectural trade-offs that include a massive increase in flexibility and the potential for emergent, novel solutions to complex problems. However, this comes at the cost of predictability and introduces the significant challenge of managing, observing, and constraining a truly autonomous process.

With these two paradigms clearly defined, we can now conduct a direct comparison of their practical design considerations.

## 4.0 Core Design Considerations: Workflows vs. Agents

### 4.1 Explain the Importance of Deliberate Choice

The choice between a Workflow and an Agent architecture is a critical design decision with significant downstream consequences for predictability, control, and flexibility. Understanding the fundamental trade-offs between orchestrating a model along a predefined path versus delegating control to the model is paramount for any system architect. The following table synthesizes the previous concepts into a direct comparison to guide this choice.

### 4.2 Create a Comparative Analysis Table

|   |   |   |
|---|---|---|
|Architectural Dimension|Workflows (Predefined Paths)|Agents (Dynamic Direction)|
|**Control Locus**|Control is maintained by the developer and embedded in the system's predefined logic and orchestration.|Control is delegated to the LLM, which dynamically directs the process and sequence of actions.|
|**Execution Path**|The path is deterministic and predictable, following the explicit steps laid out by the system designer.|The path is dynamic, emergent, and non-deterministic, as the model chooses its own course of action.|
|**Degree of Autonomy**|Autonomy is constrained and limited to specific, pre-approved decision points within the fixed process.|Autonomy is high, with the model guiding the overall task accomplishment and choosing its own adventure.|
|**Primary Use Case**|Ideal for structured, repeatable processes where auditability, reliability, and low operational risk are paramount (e.g., automated report generation, structured data extraction).|Ideal for complex, open-ended problem-solving where the path to a solution is unknown and novelty is valued over predictability (e.g., open-ended research, dynamic response systems).|

### 4.3 Provide a Concluding Transition

Ultimately, this architectural choice represents a fundamental trade-off between procedural rigidity and generative flexibility. The architect's primary task is to map the problem domain to the appropriate point on this spectrum.

## 5.0 Conclusion: From Ambiguity to Architectural Clarity

This overview has journeyed from the broad, often ambiguous definition of "agentic AI" to a structured, actionable framework for system design. The initial ambiguity, where any system with tool-use or multiple LLM calls could be labeled an "agent," is resolved by Anthropic's architectural lens. This framework forces a designer to ask the most critical question: where does control reside—in the code or in the model?

The primary takeaway for system designers and architects is this: the critical value lies not in applying the fashionable label of "agent," but in understanding the fundamental architectural distinction between predictable, developer-orchestrated **workflows** and dynamic, model-directed **agents**. This clarity is the foundation of effective system design, enabling architects to make deliberate, informed decisions that align the system's architecture with its intended purpose.
