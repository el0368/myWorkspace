### The Stack and Function Calls 🥞

The instructor explains how the stack manages memory for a sequence of function calls using a "Last-In, First-Out" (LIFO) mechanism.

* **Activation Records are Created for Each Function Call:** When a function starts, a block of memory for its local variables and parameters, called an **"activation record"** (or stack frame), is created on the stack.

* **The Stack Grows with Nested Calls:** Using his example of `main` calling `fun1`, and `fun1` calling `fun2`:
    1.  First, the activation record for `main` is placed on the stack.
    2.  When `main` calls `fun1`, the activation record for `fun1` is placed on *top* of `main`'s.
    3.  When `fun1` calls `fun2`, the activation record for `fun2` is placed on *top* of `fun1`'s.
    The instructor notes, "Now, presently `fun2()` is running and the topmost activation record inside this area is `fun2()`."

* **The Stack Shrinks as Functions Return:** The process happens in reverse.
    1.  When `fun2()` finishes, its activation record is **"deleted"** from the top of the stack.
    2.  When `fun1()` finishes, its activation record is then **"removed from the main memory, that is from the stack."**
    3.  Finally, when `main()` ends, its activation record is also deleted.

* **This Mechanism is Why It's Called a "Stack":** The instructor concludes, "So the way, activation records are created like this, and then deleted like this. **So this mechanism is stack, right? Top and top and top, then, delete, delete, delete**...That's why this section of memory behaves like a stack."

* **Stack Memory is Managed Automatically:** A key takeaway is that "this memory is **automatically created, and automatically destroyed**, the programmer doesn't have to do anything for its allocation and destruction, just programmer has to declare the variable."

### Heap Memory and Dynamic Allocation (Go Perspective) HEAP

The instructor describes the heap as a region for memory that is managed differently from the stack.

* **The Heap is for "Unorganized Memory":** The instructor contrasts the organized LIFO nature of the stack with the heap, which he describes as **"unorganized memory."** In Go, while it's not strictly ordered like the stack, the heap is a highly managed area controlled by the Go runtime.

* **Heap Memory is Treated Like a Resource:** A core principle is that **"Heap memory should be used like a resource, when required, you take the memory, when you don't require, you release the memory."**
    * In Go, this process is automated. You don't manually request heap memory. The Go compiler performs **escape analysis** to determine if a variable must outlive the function that created it. If so, it is automatically "escaped" to the heap.
    * Likewise, you don't manually release memory. Go's **garbage collector** automatically detects when heap memory is no longer referenced and reclaims it.

* **Heap Memory is Accessed via Pointers:** A program does not access the heap directly. As the instructor states, "**programs cannot access heap memory directly...how do they access memory? Using pointer.**"
    * A pointer variable itself (which holds the memory address) is created on the stack within a function's activation record.
    * This pointer then "points" to the actual data, which is located on the heap.

* **Allocation and Memory Leaks in Go:** The instructor warns that if you don't release memory, it causes a "loss of memory...called as **memory leak**."
    * In Go, the garbage collector prevents traditional leaks where you forget to free memory. However, a memory leak can still occur if your program unintentionally holds onto a pointer to an object that is no longer needed. Because a reference still exists, the garbage collector thinks the object is still in use and will never release it.
    * The instructor concludes that heap memory should be explicitly managed. In Go, this translates to being mindful of your program's references to ensure the garbage collector can do its job effectively.
