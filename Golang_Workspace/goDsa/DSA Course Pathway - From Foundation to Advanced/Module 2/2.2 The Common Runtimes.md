## Study Guide: 2.2 The Common Runtimes

This guide covers the most common Big O runtimes. Understanding this hierarchy is key to comparing algorithms.

### 1. O(1) — Constant Time 🚀

This is the fastest and most efficient runtime.

- **Explanation:** The time it takes to run the algorithm is the **same regardless of the input size** (`n`). Whether you have 10 items or 10 million, it takes the same amount of time.
    
- **Example:** Accessing a specific element in an array by its index (`my_array[5]`). The computer knows exactly where to go.
    
- **Analogy:** Grabbing a specific page from a book when you already know the page number.
    

---

### 2. O(logn) — Logarithmic Time 📖

This is exceptionally fast and scalable.

- **Explanation:** The runtime increases very slowly as the input size grows. It works by **repeatedly cutting the problem size in half**.
    
- **Example:** **Binary Search**. Finding a word in a sorted dictionary. You open to the middle, decide which half the word is in, and repeat.
    
- **Analogy:** Finding a person's name in a phone book.
    

---

### 3. O(n) — Linear Time 🚶

This is a common and fair runtime. It's considered efficient and acceptable for most problems.

- **Explanation:** The runtime grows **in direct proportion to the input size** (`n`). If you double the input size, you double the time it takes.
    
- **Example:** Searching for an item in an unsorted list by checking every single element one by one.
    
- **Analogy:** Reading every single page of a book from start to finish.
    

---

### 4. O(nlogn) — Log-Linear Time 🗂️

This is the gold standard for efficient sorting algorithms that handle complex data.

- **Explanation:** This runtime is a combination of linear and logarithmic behavior. It involves breaking a problem down into smaller pieces and then working on them.
    
- **Example:** Efficient sorting algorithms like **Merge Sort** or **Quicksort**.
    
- **Analogy:** Sorting a massive pile of shuffled library books by repeatedly dividing the pile in half, sorting the smaller piles, and then merging them back together in order.
    

---

### 5. O(n2) — Quadratic Time 🐢

This is where performance starts to become a problem with larger datasets.

- **Explanation:** The runtime grows by the square of the input size (`n`). If you double the input, the time quadruples (2²=4). This is often caused by a **nested loop** that iterates over the same collection.
    
- **Example:** Simple sorting algorithms like **Bubble Sort**, where you compare every element in a list to every other element.
    
- **Analogy:** In a room full of people, every person shakes hands with every other person.
    

---

### 6. O(2n) — Exponential Time 💥

This is extremely slow and should be avoided whenever possible. It becomes unusable even for relatively small input sizes.

- **Explanation:** The runtime doubles with every single addition to the input size. This is often seen in recursive algorithms that solve a problem by trying every possible combination.
    
- **Example:** A recursive solution for calculating Fibonacci numbers or trying to "brute-force" a password by trying every possible combination of characters.
    
- **Analogy:** Trying to guess a password by starting with "a", then "b", "c", ... "aa", "ab", "ac", etc., until you've tried every combination.
